Cloud Deployment

Your Ollama agent runs great on your laptop. Now move it to the cloud so it runs 24 / 7, serves your team, and runs 5–10× faster — with the same code. Four concepts: why go cloud, which provider, managed hosted options, and one wrapper that hides them all.

Concept 1 of 4
The Big Idea

Same code, a machine that never sleeps

Local Ollama is perfect for building, but it dies when you close the lid, no teammate can reach it, and a 3 am job finds nothing listening. A cloud GPU VM fixes all three: it runs 24 / 7 and a T4's dedicated 16 GB VRAM delivers ~40 tokens/sec — five times a laptop CPU.

The magic is that nothing about your agent changes. Every call still points at base_url; you just swap localhost for the VM. It's a config change, not a migration.

Concept 1 of 4
The Analogy

The analyst who never sleeps

BEFORE: Picture a brilliant research analyst who only works at the one desk in your home office — your laptop. While you're there during the day, they're fast and helpful.

PAIN: But the moment you shut the office (close the lid), they vanish. A colleague overseas can't knock on your door, the 3 am batch job finds an empty desk, and when three people show up at once they all queue for the same single chair.

MAPPING: A cloud GPU VM hires that same analyst into an office that never closes. They work around the clock, sit behind a locked door only an SSH key opens, and their GPU desk is five times faster. You didn't retrain the analyst — you just gave them a better, always-open room.

Concept 1 of 4
How It Works

Laptop to cloud, step by step

  1. Provision a GPU VMRent a VM with a GPU (e.g. a T4) and install Ollama on it.
  2. Run Ollama as a serviceRegister it so it starts on boot and restarts on crash — always listening.
  3. Open a secure tunnelForward your local port to the VM over an encrypted SSH channel; no public port needed.
  4. Point base_url at itRead the endpoint from an env var. Dev = localhost, prod = the VM. One value flips it.

laptop 8 tok/s → T4 40 tok/s → A100 200 tok/s — the code is identical.

Concept 1 of 4
The Pattern

Pseudocode

# the ONLY thing that changes: the host
base_url = env("OLLAMA_BASE_URL",
  default = "http://localhost:11434/v1")

# dev  -> localhost (unset var)
# prod -> set OLLAMA_BASE_URL to VM tunnel

client = open_ai_client(
  base_url = base_url,
  api_key  = "ollama")

reply = client.chat(model="mistral",
                    messages=[...])
# no if-branch, no adapter, no rewrite
Concept 1 of 4
Wrong Mental Models

Misconceptions

❌
"Moving to the cloud means rewriting my agent."
No. Because you use an OpenAI-compatible base_url, the only change is the hostname — ideally read from one env var. Same model name, same request format, same streaming and tool schema.
❌
"A cloud VM must be exposed to the internet to use it."
The secure pattern is the opposite: bind Ollama to 127.0.0.1 and reach it through an encrypted SSH tunnel. No public port, no firewall hole, no one running inference on your bill.

A cloud GPU VM gives you 24/7 uptime, team access, and 5–10× speed — with byte-for-byte the same agent code.

Read base_url from an env var so dev and prod differ by one value, never a code path.

Concept 2 of 4
The Big Idea

Not all GPU clouds are equal

Once you decide to host, you pick a provider — and they trade off on three axes: cost per hour, inference speed, and operational fit with your existing stack. A Vast.ai RTX 3090 spot instance is ~$0.20/hr and ~80 tok/s; a GCP T4 is ~$0.35/hr and ~40 tok/s; a CoreWeave A100 is ~$2.21/hr and ~200 tok/s.

There's no single "best" — the cheapest box for experiments is rarely the enterprise box for production. You match the provider to the job, not to a leaderboard.

Concept 2 of 4
The Analogy

Renting a car for the trip

BEFORE: Imagine every rental counter offered the exact same car at the same price. You'd just grab whichever line was shortest.

PAIN: Real lots aren't like that. A cheap subcompact is perfect for a solo errand but miserable for moving a family of six; a luxury SUV is overkill (and overpriced) for a quick grocery run. Pick wrong and you either can't fit the load or bleed money.

MAPPING: GPU providers are the rental lot. Vast.ai / RunPod are the cheap subcompact — great for dev and experiments. GCP / AWS are the mid-size sedan your company already has an account with. Lambda / CoreWeave are the heavy-duty haulers for real production throughput. Match the vehicle to the trip.

Which provider should I rent?

IF just experimenting / on a budget:
  → Vast.ai or RunPod (3090 spot)

IF team already uses GCP or AWS:
  → stay native: GCP T4 / AWS g4dn

IF steady production traffic:
  → Lambda A10 or CoreWeave A100

# also weigh: token volume vs a managed
# per-token API (see Concept 3)

Rough crossover: a T4 at 8 hr/day is ~$56/mo — stop the VM when idle or the meter keeps running.

Concept 2 of 4
Wrong Mental Models

Misconceptions

❌
"The cheapest per-hour provider is always the best deal."
Hourly rate is only one axis. A slower box that queues requests, or one outside your team's cloud, can cost more in engineer time and latency than it saves per hour.
❌
"A running VM is free when nobody is using it."
You pay by the hour the instant it's on, idle or not. Stop the VM when you're done — a forgotten T4 left running is a silent monthly bill.

Pick a provider by matching cost, speed, and stack-fit to the job — not by the cheapest headline rate.

Prices change constantly; always check the current pricing page, and stop idle VMs.

Concept 3 of 4
The Big Idea

Someone else runs the GPU for you

You don't have to run a VM at all. Providers like Groq, Together AI, and Fireworks host open-source models and expose them through the same OpenAI-compatible API. You swap the URL and hand over a real API key instead of "ollama" — that's it.

Zero infra to manage, free tiers for development, and specialists like Groq deliver ~50 ms first-token latency on custom hardware. The price is per-token billing and shared rate limits instead of a flat hourly VM.

Concept 3 of 4
The Analogy

Owning a car vs. calling a taxi

BEFORE: Self-hosting a GPU VM is owning a car. Total control, but you buy it, park it, insure it, and it depreciates whether you drive or not.

PAIN: For occasional or bursty trips, ownership is wasteful — the car sits idle burning money, and you're on the hook for maintenance you never wanted.

MAPPING: A managed API is a taxi. You pay only per ride (per token), someone else owns and services the fleet, and a premium service (Groq) shows up almost instantly. You give up control of the vehicle and accept a meter — but for many trips that's exactly the right trade.

Concept 3 of 4
How It Works

Swapping to a managed provider

  1. Sign up & get a keyCreate an account, grab an API key, store it in an env var — never in code.
  2. Swap the base_urlPoint the same OpenAI client at the provider's endpoint instead of localhost.
  3. Use the real keyPass the provider key in place of the "ollama" placeholder.
  4. Fix the model nameEach provider names models differently — check their docs for the exact string.

Groq ~50 ms TTFT, Together / Fireworks ~150–200 ms — all via the same SDK.

Concept 3 of 4
Decision Framework

Managed API or self-hosted?

IF data may leave your infra
   AND usage is bursty / early dev:
  → managed API (Groq / Together / Fireworks)

IF you need the fastest latency, free:
  → Groq (LPU hardware, ~50ms)

IF data must stay in-house (HIPAA/GDPR)
   OR token volume is very high:
  → self-host Ollama on a VM

# crossover ~2-5M tokens/month

Below ~2–5M tokens/month, per-token APIs win; above it, the flat VM rate is cheaper.

Concept 3 of 4
Wrong Mental Models

Misconceptions

❌
"A managed API needs a different SDK than Ollama."
No — they're OpenAI-compatible. Same client, same chat format. Only the base_url, the API key, and the model-name string change.
❌
"Managed APIs are always cheaper than a VM."
Only up to a point. Per-token billing is efficient for bursty, low-volume use; once you push millions of tokens a day, a flat-rate VM you own becomes the cheaper option.

Managed hosted APIs (Groq, Together, Fireworks) are drop-in Ollama replacements — no VM, same SDK, real key.

Choose managed for bursty dev and speed; self-host for privacy and high, steady volume.

Concept 4 of 4
The Big Idea

One dial controls every backend

With four possible backends (local Ollama, Groq, Together, Fireworks), you don't want base_url and key lookups scattered across your code. Centralise them in a single factory — a LocalModelClient that reads one env var, LOCAL_MODEL_PROVIDER, and returns a configured client plus that provider's default model name.

Now switching every agent in the app from Ollama to Groq is one env var, not a code sweep. The factory hides the URL, the key handling, and the provider-specific model string behind a single call.

Concept 4 of 4
The Analogy

A universal power adapter

BEFORE: Imagine every country's wall socket needed you to rewire your laptop charger by hand before you could plug in.

PAIN: You'd carry a box of loose plugs, re-solder at each border, and one wrong wire fries the device. Every new country means touching the hardware again — error-prone and slow.

MAPPING: The wrapper is a universal travel adapter. You flip one selector to the country (set LOCAL_MODEL_PROVIDER) and the same charger works everywhere. Your agents plug into one socket; the adapter quietly routes power from Ollama, Groq, or Together — no rewiring per provider.

Concept 4 of 4
How It Works

Inside the factory

  1. Read the providerTake the name from LOCAL_MODEL_PROVIDER, defaulting to ollama.
  2. Look up its configEach provider has a stored base URL and a default model name.
  3. Validate & fetch the keyReject unknown providers; pull the API key from its env var, erroring early if missing.
  4. Return client + configHand back a ready OpenAI client and the config so callers use the right model.
Concept 4 of 4
The Pattern

Pseudocode

CONFIGS = {
  "ollama":    (localhost_url, "mistral"),
  "groq":      (groq_url,      "llama-3.3-70b"),
  "together":  (together_url,  "Mistral-7B"),
}

FUNCTION create(provider = null):
  name = provider OR env("LOCAL_MODEL_PROVIDER",
                          "ollama")
  IF name NOT IN CONFIGS: FAIL loudly

  url, model = CONFIGS[name]
  key = "ollama" IF name=="ollama"
        ELSE require_env(name + "_API_KEY")

  RETURN client(url, key), model
Concept 4 of 4
Wrong Mental Models

Misconceptions

❌
"Switching providers means editing every OpenAI() call."
That's the problem the factory removes. With a central LocalModelClient, you change one env var and every agent follows — no code edits, no scattered URLs.
❌
"One model name works across all providers."
It doesn't — mistral on Ollama is mistralai/Mistral-7B-Instruct-v0.2 on Together. That's why the factory returns the provider's default model alongside the client.

A provider-agnostic factory turns backend choice into one env var, returning both the client and the correct model name.

Centralise URL, key, and model lookups once; every agent inherits the switch for free.

Quick Quiz

Test the core insight

One question per concept. Tap to reveal the answer.

With an SSH tunnel open, what must change in agent code that used localhost:11434?
Tap to reveal ↓
Nothing. The tunnel transparently forwards requests to localhost:11434 through the encrypted SSH channel to the VM's Ollama. Your code still points at localhost — that's the whole point of the one-env-var promise.
Is the cheapest per-hour GPU provider always the right choice?
Tap to reveal ↓
No. Hourly cost is one of three axes — also weigh inference speed and how well it fits your team's existing stack. A cheap box that queues requests or sits outside your cloud can cost more in latency and engineer time than it saves. And remember: a running VM bills whether or not it's in use.
Which managed provider offers the lowest first-token latency (~50 ms), and why?
Tap to reveal ↓
Groq. Its custom LPU (Language Processing Unit) silicon delivers ~50 ms TTFT, well ahead of GPU-based providers like Together or Fireworks — and it's still reachable through the same OpenAI-compatible SDK.
Your app uses LocalModelClient.create(). How do you make CI use Groq instead of Ollama?
Tap to reveal ↓
Set two env vars — no code changes. LOCAL_MODEL_PROVIDER=groq and GROQ_API_KEY=<key>. The factory reads the provider, returns a Groq client and Groq's default model. Every agent follows the single dial.
