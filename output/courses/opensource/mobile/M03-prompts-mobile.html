Concept 1 of 4
The Big Idea

A prompt is a list of labeled messages

You don't send one blob of text. A prompt is a list of messages, each with a role: system (the rules and persona), user (the request), and assistant (the model's previous replies).

The roles tell the model who is speaking and how to weight each part. System instructions carry the most authority; user turns are the task; assistant turns are the running history. Structure, not just wording, shapes the answer.

Concept 1 of 4
The Analogy

A script with named speakers

BEFORE: Imagine you could only talk to the model by typing one giant paragraph — your rules, your question, and its past answers all mashed together with no labels.

PAIN: The model can't tell your standing instructions from a one-off question, or its own past words from yours. Everything blurs, and behavior drifts.

MAPPING: Roles turn the blob into a script with named speakers: DIRECTOR (system) sets the scene, ACTOR-YOU (user) says a line, ACTOR-MODEL (assistant) replies. Now everyone knows their part — the model reads the play instead of a wall of text.

Concept 1 of 4
How It Works

The three roles

  1. systemDurable behavior: persona, rules, output format, tool policy. Usually the first message.
  2. userThe actual request or the human's turn in the conversation.
  3. assistantThe model's prior replies — included so it can see what it already said.
  4. You assemble the listEach call sends the whole ordered array; the model reads it top to bottom.
Concept 1 of 4
The Pattern

Pseudocode

messages = [
  { role: "system",
    content: "You are a concise ops assistant." },
  { role: "user",
    content: "Summarize this alert: ..." },
  # after the model replies, you append it:
  { role: "assistant", content: "Severity: high..." },
  { role: "user", content: "Who should own it?" },
]
reply = model.chat(messages)
Concept 1 of 4
Wrong Mental Models

Misconceptions

❌
"Roles are just cosmetic labels."
They carry weight. System instructions are treated as higher-authority standing rules; putting a rule in user vs system changes how reliably it's followed.
❌
"I should fake assistant turns to force answers."
The assistant role is for real prior replies. Stuffing invented assistant text can confuse the model about what actually happened. Keep the history honest.

A prompt is an ordered list of role-tagged messages: system, user, assistant. Structure guides the model as much as wording.

Put durable rules in system, the task in user, and real replies in assistant.

Concept 2 of 4
The Big Idea

Reliable prompting is patterns, not luck

Good prompts aren't magic phrases — they're a handful of reusable patterns: give clear, specific instructions; show few-shot examples of the input→output you want; ask for chain-of-thought ("think step by step") on hard reasoning; and specify the exact output format.

Each pattern targets a specific failure. Vague results → add specificity. Wrong format → add an example. Bad reasoning → ask it to show its work. You compose them like tools.

Concept 2 of 4
The Analogy

Briefing a new contractor

BEFORE: Early users had one move: type a question and hope for the best — like telling a new contractor "make it nice" and walking away.

PAIN: "Make it nice" gets you something, but rarely what you pictured. Redo after redo, because you never showed them the target.

MAPPING: Patterns are a proper brief: precise instructions ("2 coats, matte white"), an example photo (few-shot), and "walk me through your plan first" (chain-of-thought). Show the target and the reasoning, and the result matches on the first try far more often.

Concept 2 of 4
How It Works

The core patterns

  1. Be specificState the task, constraints, and audience. Replace adjectives ("concise") with rules ("max 3 bullets").
  2. Few-shot examplesShow 1–3 input→output pairs. Examples beat descriptions for teaching format and style.
  3. Chain-of-thoughtFor multi-step reasoning, ask it to think step by step before answering — accuracy rises.
  4. Specify output formatSay exactly what shape you want (JSON keys, bullet count) so the result is parseable.
Concept 2 of 4
Decision Framework

Match the pattern to the failure

IF output is vague / off-target:
  → add specificity + constraints

IF format / style keeps drifting:
  → add few-shot examples

IF multi-step reasoning is wrong:
  → ask for chain-of-thought

IF you need to parse the result:
  → specify an exact output format

# smaller models need MORE of these

A 7B model like Mistral leans harder on examples and explicit format than a frontier model does.

Concept 2 of 4
Wrong Mental Models

Misconceptions

❌
"Longer prompts are always better."
Length isn't quality. A focused prompt with one good example beats a rambling essay — and it wastes fewer tokens. Add structure, not word count.
❌
"Adjectives like 'be smart' improve answers."
Vague praise does little. Concrete rules and examples do the work — show the target, don't describe a vibe.

Prompting is composable patterns: specificity, few-shot examples, chain-of-thought, explicit format. Each fixes a specific failure.

Show the target with an example rather than describing it — especially for smaller local models.

Concept 3 of 4
The Big Idea

The model forgets between calls

Each API call is stateless: the model remembers nothing from the last one. What feels like "memory" in a chat is an illusion — you resend the entire conversation (all prior messages) on every request.

So a multi-turn chat is really: build the messages list → call → append the reply → add the next user turn → call again with the whole thing. The model re-reads the full history each time, because to it, every call is the first.

Concept 3 of 4
The Analogy

The clerk who forgets you every visit

BEFORE: In a chat app like iMessage, the other person just remembers the conversation — you never re-explain what you already said.

PAIN: The model isn't that person. It's a brilliant clerk with amnesia: helpful in the moment, but the instant you leave the window, it forgets you completely.

MAPPING: So you carry a folder. Each visit you hand the clerk the whole file — every prior exchange — and they answer as if reading it fresh. The "conversation" lives in your folder, not the clerk's head.

Concept 3 of 4
How It Works

One turn of a chat

  1. Send the full historyEvery message so far goes in the request — system, all user and assistant turns.
  2. Get one completionThe model reads it all and returns the next assistant message.
  3. Append itAdd the reply to your list so the next call includes it.
  4. Add the next user turn & repeatThe list grows each turn — which is why context and token budgeting (M02) matter so much.
Concept 3 of 4
The Pattern

Pseudocode

history = [ system_message ]

FUNCTION turn(user_text):
  history.append({ user: user_text })
  reply = model.chat(history)      # send the WHOLE list
  history.append({ assistant: reply })
  RETURN reply

# the model kept no memory —
# 'history' IS the memory, and it lives
# in your code, growing every turn.
Concept 3 of 4
Wrong Mental Models

Misconceptions

❌
"The model remembers our earlier messages."
It doesn't. It only sees what you resend this call. Drop a message from the list and, to the model, it never happened.
❌
"Longer chats are free."
Every turn resends the whole growing history, so tokens (and latency) climb each turn. That's why later modules trim, summarize, and window the history.

The API is stateless — you resend the full conversation every call. "Memory" is your growing messages list, not the model's.

Because history grows each turn, managing it (M08, M11) is a core agent skill, not an afterthought.

Concept 4 of 4
The Big Idea

Set-once behavior programming

The system prompt is where you program the agent's durable behavior once: its persona, its rules, its output format, its tool policy. It sits at the top of every request and colors everything the model does.

It's the highest-leverage text you write — a few careful lines steer thousands of responses. Put anything that should hold across the whole conversation here; keep user messages for the specific task of the moment.

Concept 4 of 4
The Analogy

The employee handbook

BEFORE: Without a system prompt, every user message has to re-explain how the model should behave — "be concise, respond in JSON, stay professional" — over and over.

PAIN: Repeating the rules each turn is wasteful and inconsistent; miss them once and behavior slips. It's like re-training an employee at the start of every task.

MAPPING: The system prompt is the employee handbook: written once, applies to everything. The employee reads it on day one and every task follows it, so each user request can just be the task — not a re-briefing.

Concept 4 of 4
How It Works

What goes in the system prompt

  1. Persona & toneWho the agent is and how it speaks ("a terse ops assistant").
  2. Rules & constraintsWhat it must always/never do, safety limits, refusal policy.
  3. Output contractThe format it should return (JSON shape, structure) when that's constant.
  4. Tool policyWhen to use which tool, and how to handle failures — durable guidance for the loop.
Concept 4 of 4
Decision Framework

System or user message?

IF it should hold for the WHOLE
   conversation (persona, rules,
   format, tool policy):
  → put it in the SYSTEM prompt

IF it's specific to THIS request
   (the actual task, this input):
  → put it in the USER message

# durable = system, one-off = user
Concept 4 of 4
Wrong Mental Models

Misconceptions

❌
"Whatever I put in the system prompt is guaranteed."
It's strong, not absolute. The model is still probabilistic and a clever user turn can pull against it. For hard guarantees, use code-level guardrails (M16/M17), not just the prompt.
❌
"Cram every possible rule into the system prompt."
Bloated system prompts dilute focus and eat context. Keep it tight and durable; move one-off details to the user message.

The system prompt programs durable behavior once — persona, rules, format, tool policy. Highest leverage per token.

Durable rules go in system; the moment's task goes in user. For must-hold guarantees, add real guardrails too.

Why do message roles matter, beyond being labels?
Tap to reveal ↓
They carry authority and structure. The model treats system as higher-priority standing rules, user as the task, and assistant as its own history. The same rule is followed more reliably in system than buried in a user message.
The output format keeps drifting. Which prompt pattern helps most?
Tap to reveal ↓
Few-shot examples (plus an explicit format spec). Showing 1–3 input→output pairs teaches format far better than describing it — especially for a smaller local model, which leans harder on examples than a frontier model does.
How does a stateless model hold a multi-turn conversation?
Tap to reveal ↓
You resend the entire history every call. The model remembers nothing between requests; the "conversation" is your growing messages list. That's also why longer chats cost more tokens each turn.
Where should "always reply in JSON" live — system or user?
Tap to reveal ↓
The system prompt. It's a durable rule that should hold for the whole conversation, so it belongs in the set-once system message. One-off, request-specific details go in the user message. (For a hard guarantee, add code validation too.)
