Context Engineering

Prompt engineering writes the message. Context engineering curates everything the model sees — system prompt, tools, history, retrieved docs — under a finite budget that is brutally tight on local models.

Concept 1 of 5
The Big Idea

Prompting is the tip; context is the iceberg

Prompt engineering is writing one good message: roles, examples, format instructions. That's the visible part. Underneath sits the bigger discipline — context engineering: deciding what content occupies the model's window on each turn, in what order, and how it's compressed or fetched.

Every call assembles a whole stack — system prompt, tools, history, retrieved docs, tool results, your message — and the model attends to all of it. Most learners think only about the last line they typed. The other 95% sets the priors, the constraints, and the failure modes.

Concept 1 of 5
The Analogy

The evidence binder vs. the closing argument

BEFORE: A lawyer hands the jury a thick evidence binder — contracts, photos, prior testimony — then delivers a closing argument. The jury hears the closing last, but they've been reading that binder for hours.

PAIN: Rookie lawyers obsess over the closing and ignore the binder. But the jury's verdict rests mostly on the binder. A brilliant closing on top of a sloppy binder still loses the case.

MAPPING: The closing argument is your prompt. The binder is your context. The model is the jury — it reads everything. If retrieved chunks are irrelevant, tool defs are bloated, or history is full of resolved errors, no clever prompting fixes the verdict.

Concept 1 of 5
How It Works

Two different questions

  1. Prompt engineering asks"What words go in this one message?" A writing problem — roles, examples, format.
  2. Context engineering asks"What gets included at all, in what order, full or summarized?" A budgeting problem.
  3. The window is finiteEverything competes for the same token budget — and the response needs room too.
  4. Local models feel it firstMistral 7B's 32K window fills before turn 20 in a typical research agent. Budgeting isn't optional.
Concept 1 of 5
Decision Framework

Which discipline is this?

IF the answer is worded badly
   but the right facts were present:
  → it's a PROMPT problem
     (fix the message wording)

IF the right facts were missing,
   buried, stale, or crowded out:
  → it's a CONTEXT problem
     (fix what's in the window)

# most "bad model" days are
# actually context problems.

On a 32K Mistral window you hit the budget fast — so the context half is where local-model agents live or die.

Concept 1 of 5
Wrong Mental Models

Misconceptions

❌
"A better prompt fixes any bad answer."
Not if the context is the problem. If the key fact was never retrieved, or was buried under stale history, wording the question better won't summon it. Fix the window first.
❌
"The model only reads my last message."
It reads the entire assembled stack. Your typed message is often under 1% of what shaped the reply — the rest is context you assembled, deliberately or not.

Prompt engineering authors one message; context engineering curates the whole stack under a budget. Prompting is a sub-discipline of context.

Ask "is this a wording problem or a window problem?" — the answer decides which lever you reach for.

Concept 2 of 5
The Big Idea

Every call is six layers, not one message

Before you can engineer context, you have to see what's in it. On every call the model receives a layered stack: system prompt, tool definitions, retrieved docs, conversation history, tool results, and finally your current message.

Most of it isn't in the messages array you passed — it's assembled from parameters. On turn 6 of a Mistral order-tracking agent, the user types 72 tokens but the model receives ~7,300. Ninety-nine percent of what shapes the answer is content you assembled.

Concept 2 of 5
The Analogy

The desk before you start writing

BEFORE: Imagine a researcher sitting down to answer one question. On the desk already: the house style guide, a rack of tools, a stack of pulled reference pages, the meeting notes so far, printouts of earlier lookups — and only then, the sticky note with today's question.

PAIN: If you only think about the sticky note, you forget the desk is already covered. A cluttered desk with the wrong reference pages produces a confident, wrong answer — and you never notice, because you only wrote the sticky note.

MAPPING: The six layers are that desk. Style guide = system prompt; tool rack = tool definitions; reference pages = retrieved docs; meeting notes = history; lookup printouts = tool results; sticky note = current message. Engineer the desk, not just the note.

Concept 2 of 5
How It Works

The stack, top to bottom

  1. System + tools (static)Persona, rules, and every tool's JSON schema — sent every turn even if no tool is called.
  2. Retrieved docs (per-turn)Chunks your RAG pipeline injects for this specific query.
  3. History + tool results (growing)Every prior turn and past tool output — the main driver of overflow in long sessions.
  4. Current message (smallest)Most-attended end position, but shaped by everything stacked above it.
1. System prompt380 tok

Concept 2 of 5
The Pattern

Pseudocode

FUNCTION assemble_context(turn):
  stack = []
  stack.add(system_prompt)      # static
  stack.add(tool_definitions)   # static, always sent
  stack.add(retrieved_docs)     # per-query
  stack.add(history)            # grows each turn
  stack.add(tool_results)       # accumulates
  stack.add(current_message)    # smallest

  used = sum(count_tokens(x) FOR x IN stack)
  # used ~ 7,300 tok — user typed only 72
  RETURN stack, used
Concept 2 of 5
Wrong Mental Models

Misconceptions

❌
"Tool definitions don't count if the model doesn't call them."
They do. All 4 schemas sit in the prompt every turn — ~230 tokens each, ~920 tokens of fixed overhead whether or not a tool fires.
❌
"Mistral's 32K window is plenty."
By turn 20 with active tool use you're at 18–22K. Leave under 10K for the response and answer quality degrades. And Gemma 2 9B gives you 8x less room — it hits the wall at turn 2.

Every call is six layers: system, tools, retrieved docs, history, tool results, current message. The model attends to all of them.

On turn 6, 99% of what shaped the answer was content you assembled — and 22% of Mistral's budget was already gone.

Concept 3 of 5
The Big Idea

Four moves, that's all you get

When the stack gets too big, too noisy, or too stale, every fix reduces to one of four moves: Crop (remove a whole layer), Compress (shorten what stays), Summarize (collapse old history into a dense gist), and Select (retrieve only the relevant docs on demand).

That's the entire toolbox. Every RAG technique, every memory architecture, every multi-agent pattern later in the course is one of these four wearing a different costume. When an agent degrades, the question is simply: which lever do I pull?

Concept 3 of 5
The Analogy

Packing a suitcase that's already full

BEFORE: You're packing for a two-week trip and the suitcase won't close. For any item you have four options, not one.

PAIN: Most people default to cramming more in. The zipper breaks, and something critical — your laptop charger — gets left behind because something had to give at the last second.

MAPPING: The four real options are: throw it out (Crop), use packing cubes so it takes half the space (Compress), ship it ahead as a note-to-self (Summarize), or buy it on arrival only when needed (Select). Those are exactly Crop, Compress, Summarize, Select — the only four moves for curating context.

Concept 3 of 5
How It Works

The four levers

CropRemove an unneeded layer entirely. No tool call this turn? Skip the tool defs.
CompressShorten what stays. Extract 5 fields from a 2K-token JSON tool result.
SummarizeCollapse 12 old turns into a 3-sentence gist that keeps IDs and decisions.
SelectRetrieve only the top-3 relevant docs. Pay 0 tokens for the rest.

Crop is zero-risk when a layer clearly doesn't apply. Summarize is lossy — always instruct it to preserve exact IDs and numbers.

Concept 3 of 5
Decision Framework

Which lever fits the problem?

IF a whole layer doesn't apply
   this turn (no tools, no docs):
  → CROP it out

IF a layer is huge but only a
   few fields matter (big JSON):
  → COMPRESS to those fields

IF history is long and old turns
   are low-relevance:
  → SUMMARIZE old turns

IF the knowledge base is bigger
   than ~3 docs:
  → SELECT via retrieval
Concept 3 of 5
Wrong Mental Models

Misconceptions

❌
"Compress and Summarize are the same thing."
No. Compress is field-extraction on structured data — lossless for the key fields. Summarize is a separate model call that collapses conversation turns — lossy, but preserves the semantics.
❌
"Just Crop the system prompt to save tokens."
Never. The system prompt holds persona, safety rules, and output format — dropping it causes catastrophic behavior. Crop retrieved docs or tool defs instead; they're query-specific and dispensable.

Crop, Compress, Summarize, Select — the only four moves for curating context. Every advanced pattern is one of these in disguise.

When an agent degrades, name the lever before you write code: remove a layer, shorten it, gist it, or fetch on demand.

Concept 4 of 5
The Big Idea

Where you put a fact decides if it's recalled

Even if every byte in your context is high quality, position matters. Models attend far more strongly to content at the start and end of the window than to content in the middle. This is the documented "lost in the middle" effect.

Recall runs roughly ~74% at the start, ~72% at the end, but drops to ~43% dead center. And it's worse on smaller models — Mistral 7B and Gemma 2 9B suffer more sharply than a 70B model, because smaller attention heads spread thinner across the window.

Concept 4 of 5
The Analogy

The 20-bullet meeting agenda

BEFORE: A meeting runs through a 20-bullet agenda. A week later, ask a participant what was decided.

PAIN: They remember bullet 1 (the opening goal), bullet 20 (the action items), and maybe the one heated argument. Bullets 8–14? Gone — even though they heard every word. The most important constraint got put at bullet 11, and now nobody implements it.

MAPPING: The model reads context the same way. Position 1 and the very end are recalled with high fidelity; the middle of a long context, even when literally present, can be effectively invisible to the model's reasoning — especially on smaller local models.

  → put it at the START of the

Concept 4 of 5
Wrong Mental Models

Misconceptions

❌
"If it's in the context, the model will use it."
Not reliably. A fact stranded mid-context can sit at ~43% recall on Mistral — present, but effectively invisible to the reasoning. Presence is not attention.
❌
"This is a bug that'll be patched."
It's an architectural property of smaller attention heads, not a defect. Your only fix is positional: place critical facts at START or END, always.

Recall is a U-curve: strong at the edges, weak in the middle — sharper on small models. Position is a lever, not a detail.

Critical facts go at the start AND the end. On Gemma, treat the middle as a dead zone.

Concept 5 of 5
The Big Idea

Long sessions poison themselves

Long-running agents accumulate junk: tool results from searches that went nowhere, abandoned plans, superseded instructions ("actually, ignore that"), resolved errors. The model dutifully attends to all of it — including the parts that no longer apply.

The result: by turn 20 the agent retries already-failed lookups, contradicts its own corrections, and answers questions you never asked. Critically, context rot is a signal-to-noise problem, not a budget problem — you can hit it at 55% window utilization with plenty of tokens to spare.

Concept 5 of 5
The Analogy

The email forwarded fifteen times

BEFORE: An email thread gets forwarded fifteen times, everyone leaving the full quoted history. The actual decision is buried under "Re: Re: Re: FW: FW:".

PAIN: A new participant joins, reads top-down, and acts on stale info from forward #3 — the old price, the abandoned plan. Every reply makes the thread harder to read, not easier. It becomes net-negative information density.

MAPPING: The same thing happens in your model's window. Each turn appends; nothing self-cleans. By turn 20 on Mistral you're reading a thread that's mostly noise, and a critical constraint from turn 8 is buried under tool-result garbage from turns 9–19.

Concept 5 of 5
How It Works

A compaction pass

tool: track ORD-88421 → ERROR timeout
tool: track ORD-88421 → ERROR timeout
user: actually I meant ORD-88422
tool: track ORD-88421 → {...} [wrong again]
tool: track ORD-88422 → delivered

↓ compact ↓

[summary] ORD-88422 delivered Nov 4. ORD-88421 was a mistake; ignore.
user: also where is ORD-88419?
  1. Detect low signal-to-noiseWatch for stale errors, superseded turns, duplicate results piling up.
  2. Summarize old turnsFold them into one clean case-fact message; keep recent turns verbatim.
  3. Put the question next to the factsNow the current query sits adjacent to what matters, not buried.
Concept 5 of 5
The Pattern

Pseudocode

FUNCTION compact(history, keep_recent):
  IF length(history) <= keep_recent:
    RETURN history        # nothing to do

  old    = history[: -keep_recent]
  recent = history[-keep_recent :]

  # SEPARATE model call to summarize —
  # preserve every ID, number, decision;
  # drop retries, dupes, resolved detours
  gist = summarize(old)

  RETURN [ gist ] + recent

Never ask the main model to summarize in the same call — it can't summarize what it's currently reading.

Concept 5 of 5
Wrong Mental Models

Misconceptions

❌
"If I'm under the token limit, I'm fine."
Rot hits at 55% utilization. Half your window can be stale errors and superseded instructions — plenty of room, but the reasoning still degrades. It's signal-to-noise, not size.
❌
"Compaction just makes the context shorter."
Shorter is a side effect. The real win is cleaner: timeouts gone, the wrong-order mistake folded into a positive fact, the live question next to the facts that answer it.

Context rot is degradation from accumulated stale, contradictory, low-relevance content — a signal-to-noise failure.

Compact proactively with the Summarize lever: fold resolved detours into clean case facts before turn 20, not after the agent breaks.

One question per concept. Tap to reveal the answer.

The right facts were in the window but the answer was still wrong. Prompt problem or context problem?
Tap to reveal ↓
It depends on why. If the facts were present and correct but the wording is off, it's a prompt problem. If they were buried mid-context, crowded out, or stale, it's a context problem — and most "bad model" days are actually context problems. Better wording can't summon a fact the window buried.
You registered 4 tools but this turn calls none. How many tokens do the tool definitions cost?
Tap to reveal ↓
Their full cost — ~920 tokens — every turn. Every tool schema is in the prompt on every call, ~230 tokens each, whether or not a tool fires. The only way to avoid it is the Crop lever: exclude tools when the query clearly doesn't need them.
A 25-page catalog is only occasionally relevant. Which lever?
Tap to reveal ↓
Select. "Occasional facts" is the Select signal: embed the catalog, retrieve only the 2–3 relevant chunks per query. Injecting all 25 pages would eat ~7,500 tokens — ~25% of Mistral's budget — before you've said a word. Select pays 0 tokens until needed. This is what RAG (M09) implements.
Where do you place a must-hold constraint to maximize recall?
Tap to reveal ↓
At the start of the system prompt AND repeated just before the user message. Both are high-recall positions. Middle recall on Mistral 7B can be as low as 43% in a 10-doc context, so 50 tokens of repetition at the two strong positions is cheap insurance.
At 55% window utilization your agent starts contradicting itself. What's wrong?
Tap to reveal ↓
Context rot — a signal-to-noise problem, not a budget problem. You have room to spare, but half the window is stale errors and superseded instructions dragging down the model's reasoning. Fix: apply the Summarize lever and compact old turns into a clean case-fact summary.
