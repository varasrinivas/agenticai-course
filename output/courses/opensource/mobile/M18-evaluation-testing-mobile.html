Concept 1 of 6
The Big Idea

"Seems to work" is not a quality standard

You shipped an agent and it looks fine in the demo. But every prompt tweak, model bump, or new tool is a change that can silently degrade quality. Without a testing harness you have no idea whether 50 small "improvements" quietly eroded the agent.

Eval is the automated regression check that catches this. Google's internal research found ~40% of LLM pipeline changes caused a regression in at least one metric — even changes meant as improvements. A 5-minute eval suite on every PR prevents weeks of production debugging.

Concept 1 of 6
The Analogy

The bridge inspector who checks once

BEFORE: Imagine a bridge inspector who only checks a bridge the day it's built — never after years of traffic, weather, and stress. Day one it looks perfect, everyone drives across, sign-off complete.

PAIN: A hairline crack starts small and propagates silently for three years. Every load felt fine right up until a truck crosses and the span fails — there was no system to detect incremental degradation.

MAPPING: Your agent is the bridge; every prompt change or model bump is a new load cycle. Evals are the structural inspection program — running the same checks over and over so a slow crack in quality shows up before it collapses in production.

Concept 1 of 6
How It Works

How silent regressions happen

  1. A change shipsSomeone edits the system prompt "to improve tone" or bumps the model version.
  2. No eval runsThe demo still looks fine, so the change merges with no automated check.
  3. Quality drifts unseenThe change subtly shifts behavior — e.g. a false-merge rate climbs to 18% (9,000 bad records/day) with nobody watching.
  4. Discovery is expensiveWeeks later an audit finds it; days of debugging trace back to one unmeasured change.
Concept 1 of 6
Decision Framework

IF "it looked fine in the demo":

Concept 1 of 6
Wrong Mental Models

Misconceptions

❌
"It passed the demo, so it works."
A demo is one lucky path. Quality is measured across a set of known cases, not a single happy-path run you eyeballed once.
❌
"Evals are a nice-to-have I'll add later."
Later means after a silent regression has already shipped. A minimal suite that runs in 5 minutes per PR is cheaper than one production incident.

Eval is the structural inspection program that keeps your agent from silently failing. Every change is a load cycle; measure it.

Roughly half of "improvements" secretly break something else. A fast eval suite on every PR turns invisible cracks into visible test failures.

Concept 2 of 6
The Big Idea

Eval is a layered system, not one test

You test at three levels, each catching a different class of failure. Unit tests check individual tools in isolation. Integration tests run the full agent loop against known inputs. LLM-as-judge evals score subjective qualities — reasoning, faithfulness, relevancy — that no deterministic assertion can express.

You need all three because each has a different cost-to-confidence ratio: units are near-free and run every commit, integration runs every PR, judge tests are expensive and run nightly or on major changes.

Concept 2 of 6
The Analogy

Inspecting a car: parts, road test, ride quality

BEFORE: Suppose you judged a whole car with a single test drive around the block and called it "good."

PAIN: A block-long drive misses a worn brake pad (a part fault), a stalling gearbox under load (a system fault), and a jittery, unpleasant ride (a quality fault). One test can't see all three failure types.

MAPPING: So a real inspection uses three layers: bench-test each part (unit tests), a full road test under load (integration), and a rider scoring comfort and smoothness (LLM-as-judge). Each layer catches what the others structurally cannot.

Concept 2 of 6
How It Works

The three levels

  1. Unit testsIndividual tool functions in isolation. Deterministic, no LLM, <10ms each, 100+ cases.
  2. Integration testsThe full agent loop end-to-end against a known input, with a deterministic pass/fail. ~50 cases, seconds each.
  3. LLM-as-judgeA second model scores quality dimensions code can't measure. ~20 cases, ~60s each, expensive.
Judge · ~20 · slow
Integration · ~50 · medium
Unit · 100+ · fast
Concept 2 of 6
Decision Framework

Which level catches this bug?

IF a single tool returns wrong /
   crashes on an edge case:
  → UNIT test

IF the agent calls wrong tools or
   loops / stops incorrectly:
  → INTEGRATION test

IF reasoning is incoherent or the
   answer drifts / hallucinates:
  → LLM-as-JUDGE

# cheap+frequent at the bottom,
# expensive+rare at the top.
Concept 2 of 6
Wrong Mental Models

Misconceptions

❌
"If I have an LLM judge, I don't need unit tests."
The judge is slow and expensive and can't localize a bug to one tool. Units run in milliseconds and pinpoint exactly which function broke.
❌
"Integration tests should assert on exact output text."
Text matching is brittle — a paraphrase breaks it. Assert on structure: which tools ran and the numeric output shape (confidence range, decision).

Three layers — unit, integration, LLM-as-judge — each catch failures the others miss. Run them at different frequencies.

Cheap, deterministic tests run often at the base; expensive quality judgments run rarely at the top.

Concept 3 of 6
The Big Idea

No golden set, no ruler

An eval harness without a good golden test set is a ruler with no markings. A golden set is a curated collection of (input, expected_output) pairs where the correct answer is known and validated — treated as ground truth.

Each case captures the input query, the expected (ordered) tool calls, and pass criteria like a minimum confidence and required keywords. Storing this as data (JSON), separate from test logic, lets domain experts add cases without touching code.

Concept 3 of 6
The Analogy

The teacher's answer key

BEFORE: Picture grading 100 exams with no answer key — just your gut feeling about whether each response "seems right."

PAIN: Your standard drifts by the hour, two graders disagree, and you can't prove a score is correct. There's nothing to measure against.

MAPPING: The golden set is the answer key written by an expert in advance. Now grading is objective and repeatable: compare the agent's answer to the key. Add adversarial and boundary questions to the key so it probes the hard cases, not just the easy ones.

Concept 3 of 6
How It Works

Building the golden set

  1. Define a case schemaEach case: an id, the input, expected tool calls, and pass criteria (min/max confidence, keywords, decision).
  2. Source from real logsStart with actual production inputs so cases reflect true usage.
  3. Add adversarial & boundary casesInclude near-matches that should NOT merge and ambiguous ~0.75-confidence cases.
  4. Size it right30+ for integration, 100+ for unit, 20–30 for judge (each judge case costs an LLM call).
Concept 3 of 6
The Pattern

Pseudocode

# one golden case (stored as data)
case = {
  id:    "ER-001",
  input: "Are 'Acme LLC' and" +
         "'ACME, L.L.C.' the same?",
  expected_tools: ["search", "fuzzy_match"],
  expect: { decision: "merge",
            min_confidence: 0.90 },
}

FUNCTION load_cases(path):
  data = read_json(path)
  IF data.cases is empty:
    fail("add cases before running")
  RETURN data.cases
Concept 3 of 6
Wrong Mental Models

Misconceptions

❌
"A handful of easy cases is enough."
A tiny all-easy set detects nothing. You need ~30 cases minimum for statistical power — and the hard ones (adversarial, boundary) catch the real regressions.
❌
"Thresholds are one-size-fits-all."
A smaller local model scores lower than a frontier one — a 7B judge runs ~0.05 below cloud benchmarks. Set thresholds realistic for your model tier.

The golden set is your answer key — expert-validated (input, expected) pairs stored as data. Separate it from test code.

Seed from real logs, add adversarial and boundary cases, and size it for statistical power (30+ integration, 100+ unit).

Concept 4 of 6
The Big Idea

Tools are pure functions — test them like any code

Agent tools receive inputs and return outputs with no LLM involved. That makes them ideal for ordinary unit tests: fast, deterministic, and zero LLM cost. fuzzy_match("Acme LLC","ACME LLC") should score above 0.9; a search for a nonexistent name should return an empty list, not crash.

Parametrize the tests so one table of cases covers many inputs, and one failing case never aborts the rest. A whole tool suite runs in a fraction of a second on every commit.

Concept 4 of 6
The Analogy

Bench-testing each component before assembly

BEFORE: Imagine building a machine and only ever turning it on fully assembled to see if it runs.

PAIN: When it fails, you have no idea which of 40 parts is at fault — you tear the whole thing apart to find one bad bearing.

MAPPING: Unit tests bench-test each part on its own before assembly: spin the bearing, load the spring, check the gauge. If a part fails, you know exactly which one and why — in milliseconds, before it ever reaches the full machine.

Concept 4 of 6
How It Works

Unit-testing a tool

  1. Pick the tool & inputsList representative inputs plus edge cases: empty string, identical strings, clearly-different pairs.
  2. State the expected rangeFor fuzzy match, a min/max score; for search, a min/max result count.
  3. Assert — and check for NoneTools return None on not-found, they don't raise. Assert against None explicitly or you miss silent failures.
  4. ParametrizeAdd new cases by editing the table, not writing new functions.
Concept 4 of 6
The Pattern

Pseudocode

# table of (a, b, min, max) cases
cases = [
  ("Acme LLC", "ACME, L.L.C.", 0.88, 1.0),
  ("",         "Acme LLC",     0.0,  0.1),
  ("Acme",     "Acme",          1.0,  1.0),
]

FOR EACH (a, b, lo, hi) IN cases:
  result = fuzzy_match(a, b)
  assert result is not None
  assert lo <= result.score <= hi

# not-found returns None, never raises
assert search("no_such_name") == []
Concept 4 of 6
Wrong Mental Models

Misconceptions

❌
"Testing tools needs the LLM running."
No. Tools are pure functions — call them directly with dicts. Zero LLM cost, milliseconds per test, runs on every commit.
❌
"If a tool doesn't crash, it passed."
Silent wrong answers are worse than crashes. A tool returning None on not-found must be asserted against explicitly, or the failure hides.

Tools are pure functions — unit-test them fast, deterministically, and with no LLM. Assert on ranges and explicitly on None.

Parametrize so adding a case is a table edit, and pin edge cases: empty input, identical input, clearly-different pairs.

Concept 5 of 6
The Big Idea

Test the reasoning that connects the tools

An agent is more than its tools — it's the reasoning that sequences them. Integration tests run the full agent loop against a known input and verify the output with a deterministic assertion: the LLM is called, but pass/fail is decided by code.

Assert on structure, not text: which tools were called and the numeric output (confidence range, decision). This survives paraphrasing — refactoring the system prompt won't break a well-written integration test.

Concept 5 of 6
The Analogy

The full road test under load

BEFORE: Every individual car part passed its bench test, so you assume the assembled car drives fine.

PAIN: Good parts can still combine badly — the transmission shifts at the wrong moment, the car stalls turning uphill. No single part is broken; the coordination is.

MAPPING: The integration road test drives the whole car on a known route and checks the outcome: did it get up the hill, in the right gear, within the time? You don't grade the exact engine noise (the text) — you grade that it did the right things (the tool sequence and result).

Concept 5 of 6
How It Works

One integration case, end to end

  1. Run the real agentFeed the golden input; cap iterations and set a timeout so a cold model can't hang CI.
  2. Capture the tool traceRecord which tools were called, in what order.
  3. Assert on structureRequired tools present; confidence within range; decision matches — never exact text.
  4. Skip gracefullyIf the local model server is down, skip rather than fail so other CI jobs aren't blocked.
Input→ Agent→ Tool trace→ Assert ✓
Concept 5 of 6
The Pattern

Pseudocode

FOR EACH case IN golden_set:
  IF model_server down: skip()

  result = run_agent(
    case.input,
    max_iterations = 8,   # no infinite loop
    timeout = 30s)        # fail fast

  # assert on STRUCTURE, not text
  FOR tool IN case.expected_tools:
    assert tool IN result.tools_called
  assert result.decision == case.decision
  assert result.confidence >= case.min_conf
Concept 5 of 6
Wrong Mental Models

Misconceptions

❌
"Assert the agent's exact answer string."
The model paraphrases every run. Exact-text assertions are flaky. Assert on the tool trace and numeric output shape instead.
❌
"No iteration cap or timeout needed."
An agent can loop forever or a cold model can hang. Cap iterations and set a timeout so one bad run doesn't block the whole CI suite.

Integration tests run the full loop and assert on structure — tools called, confidence range, decision — not exact text.

Cap iterations, set timeouts, and skip gracefully when the model server is down. (The same structure feeds RAG metrics like Ragas faithfulness.)

Concept 6 of 6
The Big Idea

Use a second model to score what code can't

Some quality dimensions — reasoning coherence, faithfulness to context, evidence use, confidence calibration — can't be checked by a deterministic assertion. The LLM-as-judge pattern feeds the agent's output to a second model that scores each dimension 0–1.

The judge is only as good as its prompt. Define criteria explicitly, mitigate position bias (randomize order when comparing) and length bias (tell it not to reward length), and run the judge at temperature 0 for stable scores. This is exactly what frameworks like DeepEval and Ragas do internally.

Concept 6 of 6
The Analogy

The judge with a scoring rubric

BEFORE: Picture a diving competition where the judge just shouts a gut number after each dive — no rubric, no criteria.

PAIN: Scores swing with mood, the judge favors the diver who went first, and a big flashy splash outscores a clean technical dive. Nobody can trust or reproduce the result.

MAPPING: Give the judge an explicit rubric — entry, execution, difficulty, each scored separately — plus rules like "ignore crowd noise" and "order doesn't matter." An LLM judge works the same way: named criteria and anti-bias instructions turn a gut number into a reproducible score.

Concept 6 of 6
How It Works

Building a good judge

  1. Give the judge the evidencePass the question, the agent's answer, and the retrieved context it had access to.
  2. Define criteria explicitlyScore named, measurable dimensions: reasoning, faithfulness, evidence sufficiency, confidence calibration.
  3. Add anti-bias rules"Do not reward longer answers"; randomize order when comparing candidates.
  4. Score at temperature 0Deterministic scores; average over a few runs if you need high precision on a small model.
Concept 6 of 6
The Pattern

Pseudocode

prompt = """You are an impartial judge.
QUESTION: {q}   ANSWER: {a}
CONTEXT:  {ctx}
Score 0-1 each:
 reasoning, faithfulness,
 evidence_sufficiency, calibration.
Do NOT reward longer answers.
Return ONLY JSON."""

reply = judge.chat(prompt, temp=0)
scores = parse_json(reply)   # strip ``` fences
passed = scores.overall >= 0.70
Concept 6 of 6
Wrong Mental Models

Misconceptions

❌
"'Score the quality' is a good judge prompt."
Too vague — scores won't correlate with real quality. Name measurable criteria: "used at least two independent pieces of evidence," not "quality."
❌
"The judge is objective by default."
LLM judges favor the first answer (position bias) and longer answers (length bias). You must randomize order and explicitly tell it to ignore length.

An LLM judge scores subjective quality — but only with explicit criteria, anti-bias rules, and temperature 0.

Per-dimension scores help you diagnose: if reasoning drops while faithfulness holds, that's a different root cause than faithfulness dropping alone. DeepEval and Ragas automate this pattern.
