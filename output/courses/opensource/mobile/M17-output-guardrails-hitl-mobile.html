Output Guardrails & Human-in-the-Loop

Validate what your agent says, control what it costs, know when to hand off to a human, and stop cascading failures. Four concepts — output validation, cost controls, human-in-the-loop gates, and the circuit breaker pattern.

Concept 1 of 4
The Big Idea

Check the answer before the user sees it

Input guardrails protect your system from users. Output guardrails protect users from your system. They intercept every agent response before it reaches the user and run three checks.

Hallucination detection verifies each factual claim against the source documents. Toxicity filtering screens for harmful or inappropriate content. Format validation confirms the output matches the expected structure — and it's free, since it's just local parsing, no model call.

Concept 1 of 4
The Analogy

The quality inspector on the line

BEFORE: Imagine a factory where products go straight from the machines to the customer, with nobody checking them on the way out the door.

PAIN: Most products are fine, but occasionally a defective one slips through — a car with a faulty brake line, a medicine with the wrong dose. The machine that made it never knew it erred.

MAPPING: Output guardrails are the quality inspector at the END of the line. They don't build the product; they catch the defects manufacturing missed. Your model generates a response, and the guardrail catches the hallucinated fact or malformed output before it ships to the user.

Concept 1 of 4
How It Works

Three checks, cheapest first

  1. Format check (free)Parse locally: valid JSON? All required fields present? Values in range? Catches the most common failures with no model call.
  2. Hallucination checkA separate model call compares each claim to the source docs and labels it supported, unsupported, or contradicted.
  3. Toxicity checkA model-as-judge rates content severity (1–5) and blocks anything over the threshold.
  4. Decide the verdictAny contradicted claim or over-threshold toxicity → block. Otherwise pass it to the user.
Response → Format → Halluc.
Toxicity → Pass → User / Fail → Block
Concept 1 of 4
The Pattern

Pseudocode

FUNCTION validate(response, sources):
  # cheapest check first — no model call
  IF NOT valid_format(response):
    RETURN block("malformed")

  claims = judge_facts(response, sources)
  IF any(c.status == "contradicted"):
    RETURN block("hallucination")

  score = judge_toxicity(response)
  IF score > THRESHOLD:
    RETURN block("toxic")

  RETURN pass(response)
Concept 1 of 4
Wrong Mental Models

Misconceptions

❌
"Output guardrails are unnecessary — the model is already safe."
Safety training catches most harmful content but isn't infallible, and it does nothing about hallucinations. A model can state a wrong fact with total confidence.
❌
"The model can tell you how confident it is."
Self-reported confidence ("I'm 85% sure") is not calibrated. Use programmatic criteria — source-document matching, structured validation — not the model's self-assessment.

Output guardrails are the last checkpoint before a response reaches a user: format, hallucination, toxicity. Run the free format check first.

A hallucinated code or dropped field can cost thousands; a $0.003 check is trivially cheap by comparison.

Concept 2 of 4
The Big Idea

Cap the spend before a bug drains it

Your agent loop works fine in testing — 3–4 iterations, a couple of cents per request. But an edge case in production can trigger 50 iterations, each chewing through a 100K-token document, turning one request into $15.

Cost controls put a hard ceiling on spend. A middleware layer wraps every model call, tracks cumulative tokens and cost, and before each call checks whether the next one would blow the budget. If so, it short-circuits and returns a graceful fallback instead of continuing to spend.

Concept 2 of 4
The Analogy

The teenager's phone bill

BEFORE: Parents hand a teenager a phone on an unlimited plan and never think about it again.

PAIN: Then a $2,000 bill arrives — the teen discovered international calling. The phone worked perfectly; nothing stopped reasonable use from escalating into catastrophic cost.

MAPPING: A budget ceiling is the prepaid card. Each request gets a balance; once it hits zero, the card declines and the agent returns a fallback. Now a runaway loop caps out at a few cents instead of burning the whole monthly budget in an afternoon.

Concept 2 of 4
How It Works

Four levels of control

  1. Per-request budgetCap the tokens or dollars for one agent invocation. Exceed it → stop and return a fallback.
  2. Per-user budgetDaily or monthly limits per user, so no single power user eats the whole allocation.
  3. Loop detectionSpot the same tool being called repeatedly with no progress, and break the cycle.
  4. Execution time limitA wall-clock timeout that kills a run stuck in a low-token reasoning loop that never ends.
Concept 2 of 4
Decision Framework

Which control to add

IF one request can blow up:
  → per-request budget ceiling

IF one user hogs resources:
  → per-user daily / monthly cap

IF same tool fires over and over:
  → loop detection

IF run hangs with few tokens:
  → wall-clock time limit

# middleware sits BETWEEN agent
# and API — logic stays budget-blind

A $0.50 per-request cap allows normal 3–4 iteration flows but stops runaway loops around 8–10 iterations.

Concept 2 of 4
Wrong Mental Models

Misconceptions

❌
"It ran cheap in testing, so it'll run cheap in production."
Testing hits the happy path. Production hits the long tail — one edge case with a huge document or a stuck loop can be 100× the typical cost.
❌
"I'll bake budget checks into the agent logic."
Better to wrap calls in middleware. It tracks cost and enforces limits without your agent code knowing budgets exist — cleaner and reusable.

Cost controls operate at four levels: per-request, per-user, loop detection, and time limits. Middleware enforces them transparently.

At 1,000 requests/day, uncapped loops can mean $1,400+/day. A per-request ceiling can cut that to roughly a third.

Concept 3 of 4
The Big Idea

Pause and hand control to a human

Human-in-the-loop (HITL) lets your agent handle routine work autonomously but pause at predefined decision points for a human to review, approve, or modify before proceeding. The human is part of the workflow, not just watching.

There are three gate patterns. Approval gates pause before irreversible actions (send a payment, deploy code). Modification gates present a draft the human can edit. Escalation gates fire when the agent hits its competence boundary and routes to a specialist.

Concept 3 of 4
The Analogy

Autopilot and the pilot

BEFORE: Picture a flight where every second demands active human control — no automation to hold altitude, speed, or heading.

PAIN: That's exhausting and error-prone for the routine parts, yet fully removing the human is worse: some moments genuinely need judgment.

MAPPING: Modern autopilot flies the routine hours; the pilot takes over for takeoff, landing, and anything unexpected. HITL works the same way — the agent handles routine requests, but at irreversible or high-stakes points it hands control to a human through a clean, designed handoff.

Concept 3 of 4
How It Works

A gate as a state machine

  1. Pause executionAt the gate, the agent stops and stores the pending action in a queue.
  2. Notify the humanSend the full context: proposed action, why, and one-click options (approve / deny / modify).
  3. Wait for the decisionState sits at waiting_for_human. A timeout can auto-escalate if no one responds.
  4. Resume with the answerThe agent continues using the human's decision — execute, use the edited draft, or route onward.
Agent runs → Pause / gate → Human ✓ → Execute

   (email, report, letter):
  → MODIFICATION gate (edit draft)

Concept 3 of 4
Wrong Mental Models

Misconceptions

❌
"Human-in-the-loop means the AI is unreliable."
The opposite. Even great employees need manager sign-off on big transactions. HITL is risk management and good design, not an admission of weakness.
❌
"Escalate whenever the customer is angry."
Escalate on policy gaps, capability limits, or business thresholds — not sentiment. An angry customer with a simple request needs no human; a calm one hitting a policy gap does.

Three HITL gates — approval, modification, escalation — hand control to a human at the right moment. Each is a state machine that pauses and resumes.

Give the human the action, full context, and one-click options: the agent does 95% of the work, the human adds the final 5% of judgment.

Concept 4 of 4
The Big Idea

Trip the switch when failures pile up

When failures pile up — API 500s, rate limits, repeated hallucination detections, timeouts — a circuit breaker trips and routes all requests to a safe fallback instead of hammering a failing service.

It has three states. Closed (normal): requests flow, failures counted. Open (tripped): all requests get a fallback, no API calls, a cooldown timer runs. Half-Open (testing): after cooldown, one test request goes through — success closes it, failure re-opens with a longer cooldown.

Concept 4 of 4
The Analogy

The breaker in your fuse box

BEFORE: Imagine a house wired with no circuit breaker — just wires running straight from the panel to every outlet.

PAIN: An overload from a faulty appliance or too many devices overheats the wiring and can start a fire. One bad appliance could burn the house down.

MAPPING: The breaker watches the current and TRIPS at dangerous levels, cutting power instantly; you fix the fault and flip it back on. An agent circuit breaker watches failures, trips to a fallback, then tests once before restoring traffic — so one failing dependency can't take everything down.

Concept 4 of 4
How It Works

The three-state cycle

  1. Closed — count failuresRequests flow normally. Each failure increments a counter; a success resets it.
  2. Trip on thresholdHit the limit (e.g. 3 consecutive) and the circuit opens; a cooldown timer starts.
  3. Open — block & fall backEvery request gets an instant fallback. No API calls, no retries, no wasted tokens.
  4. Half-Open — test onceAfter cooldown, allow one test request. Success → close. Failure → re-open with a longer cooldown.
CLOSED → OPEN → HALF-OPEN ↶ CLOSED
Concept 4 of 4
The Pattern

Pseudocode

FUNCTION call(request):
  IF state == "open":
    IF cooldown_expired():
      state = "half_open"   # test once
    ELSE:
      RETURN fallback()      # no API call

  result = try_api(request)

  IF result.failed:
    failures += 1
    IF failures >= THRESHOLD:
      state = "open"; start_cooldown()
    RETURN fallback()

  failures = 0; state = "closed"
  RETURN result
Concept 4 of 4
Wrong Mental Models

Misconceptions

❌
"Circuit breakers are overkill for AI agents."
Without one, a downstream outage makes every request fail, burn tokens on errors, and trigger retries that compound the problem. A breaker saves thousands during a 30-minute outage.
❌
"All failure types should share one threshold."
Tune per type. You might tolerate 5 transient rate-limit errors but trip on just 2 consecutive hallucinations, which hint at a deeper context problem.

A circuit breaker cycles Closed → Open → Half-Open, short-circuiting to a fallback once failures cross a threshold. The half-open test verifies recovery before resuming.

It costs nothing to add and can save thousands in wasted API calls during an outage.

Quick Quiz

Test the core insight

One question per concept. Tap to reveal the answer.

Which output check is the cheapest, and why run it first?
Tap to reveal ↓
Format validation. It's just local parsing — no model call — so it's effectively free, and it catches the most common failures (bad JSON, missing fields, out-of-range values) before you spend a model call on hallucination or toxicity checks.
Where should cost enforcement live so agent logic stays clean?
Tap to reveal ↓
In middleware between the agent and the API. It tracks cumulative tokens and cost and checks the budget before each call, returning a fallback if the next call would exceed it — without your agent code needing to know budgets exist.
Should you escalate to a human because a customer is angry?
Tap to reveal ↓
No — escalate on policy gaps, capability limits, explicit requests, or business thresholds. An angry customer with a simple request doesn't need a human; a calm customer hitting a policy gap does. Use programmatic criteria, not sentiment or the model's self-confidence.
What does the Half-Open state of a circuit breaker do?
Tap to reveal ↓
It lets exactly one test request through after the cooldown. If that request succeeds, the breaker closes and normal traffic resumes; if it fails, the breaker re-opens with a longer cooldown (exponential backoff) — so you verify recovery before flooding a still-broken service.
