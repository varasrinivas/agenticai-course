Wrapping an Agent as an HTTP Service

Before → Pain → Mapping

Before: Your agent is a brilliant colleague locked in a private office. They can solve any problem you slide under the door, but only you can reach them. Your React frontend, the mobile app, and the automation pipeline all need that colleague's brain — but none of them know how to knock on that specific door, let alone wait for the answer.

Pain: Without a service layer, every new consumer must embed the agent code directly, manage its dependencies, and restart it when it crashes. You end up with five copies of the same agent running in five different processes, each with its own model loaded into memory, burning RAM five times over. Updates require coordinating five deployments. A single change to the agent logic must be applied in five places.

Mapping: The API is the intercom. A single HTTP endpoint wraps the agent, exposes it behind a stable contract, and lets any consumer — browser, mobile, cron job, webhook — interact with it through a protocol everyone already understands. One agent process, one model in RAM, one deployment to update. The API layer also adds authentication, rate limiting, and observability at the boundary, so the agent code stays clean.

Three Design Principles

Definition: Stateless Endpoints

A stateless endpoint is one where the server holds no per-session memory between requests. All context needed to process the request must arrive in the request body. This means the client tracks session state (conversation history, previous results) and submits it on each call. Stateless services can be horizontally scaled trivially: any server replica can handle any request because none of them are the "right" server for a given user.

  • Stateless endpoints: session state travels in the request body (session_id + history). No per-user memory on the server.
  • Streaming for long-running agents: agents that take 10–30 seconds must stream intermediate steps. Users tolerate wait time; they do not tolerate silence.
  • Idempotency keysIdempotency Key — a client-supplied unique ID (UUID) sent on each request. The server records completed responses keyed by this ID. If the same key arrives twice (network retry), the server returns the cached result instead of re-running the agent. Prevents double-charging, double-processing, and duplicate tool calls.: clients supply a UUID per request; the server deduplicates retries safely.
Why It Matters: Real Numbers

A ReAct entity resolution agent on Mistral-7B processes a typical query in 8–25 seconds depending on tool call depth. A synchronous JSON response on a 25-second request means the user stares at a spinner with zero feedback. With SSE streaming, the first data: {"type":"thought"} event arrives in under 1 second. User-perceived latency drops by ~90% for the same underlying compute. This is not a UX nice-to-have — it is the difference between "broken" and "acceptable."

Streaming Responses with SSE

Definition: Server-Sent Events (SSE)

Server-Sent Events is an HTTP-based protocol where the server holds the connection open and pushes newline-delimited data: ... lines to the client. Each event ends with two newlines (\n\n). Unlike WebSockets, SSE is one-directional (server to client only) and works through standard HTTP proxies and CDNs without configuration. The browser's built-in EventSource API reconnects automatically on disconnect. For agent streaming, SSE is almost always the right choice over WebSockets.

The agent loop yields intermediate events: thoughts, tool calls, and the final result. We convert the ReAct loop into a Python generator, then wrap it with FastAPI's StreamingResponse.

WHAT — Three SSE event types: thought (reasoning step), tool_call (function invoked), result (final answer). WHY — Typed events let the client render each differently: show thoughts in a collapsible trace, highlight tool calls with icons, render the result prominently. GOTCHA — Each yield must end with \n\n (two newlines) or the SSE spec is violated and the browser’s EventSource silently drops events.
# agent_api/streaming.py
import json
from fastapi import HTTPException, Depends
from fastapi.responses import StreamingResponse
from .main import app, require_api_key, AgentRequest, client, MODEL

def make_sse_event(event_type: str, data: dict) -> str:
    """Format a single SSE event. MUST end with double newline."""
    payload = json.dumps({"type": event_type, **data})
    return f"data: {payload}\n\n"

def agent_event_stream(query: str):
    """
    Generator that wraps the ReAct loop and yields SSE events.
    Converts each loop iteration into a typed event.
    """
    messages = [
        {"role": "system", "content": "You are an entity resolution agent..."},
        {"role": "user", "content": query},
    ]
    # ── Tool definitions (abbreviated for clarity) ──────────────────────────
    tools = [
        {
            "type": "function",
            "function": {
                "name": "search_filings",
                "description": "Search UCC filings by entity name",
                "parameters": {
                    "type": "object",
                    "properties": {
                        "name": {"type": "string"},
                        "fuzzy": {"type": "boolean", "default": True},
                    },
                    "required": ["name"],
                },
            },
        }
    ]

    iteration = 0
    max_iterations = 10

    while iteration < max_iterations:
        iteration += 1

        # ── Yield thought event: agent is "thinking" ─────────────────────────
        yield make_sse_event("thought", {
            "content": f"Iteration {iteration}: calling Mistral...",
            "iteration": iteration,
        })

        response = client.chat.completions.create(
            model=MODEL, messages=messages, tools=tools
        )
        choice = response.choices[0]

        # ── Check for tool calls ──────────────────────────────────────────────
        if choice.finish_reason == "tool_calls":
            for tc in choice.message.tool_calls:
                args = json.loads(tc.function.arguments)
                yield make_sse_event("tool_call", {
                    "tool": tc.function.name,
                    "args": args,
                    "call_id": tc.id,
                })
                # Execute the tool (stubbed here)
                tool_result = execute_tool(tc.function.name, args)
                messages.append(choice.message)
                messages.append({
                    "role": "tool",
                    "tool_call_id": tc.id,
                    "content": json.dumps(tool_result),
                })

        # ── Final answer ──────────────────────────────────────────────────────
        elif choice.finish_reason == "stop":
            yield make_sse_event("result", {
                "content": choice.message.content,
                "iterations": iteration,
            })
            yield "data: [DONE]\n\n"
            return

    # Max iterations reached
    yield make_sse_event("error", {"content": "Max iterations reached"})
    yield "data: [DONE]\n\n"

// src/streaming.ts
import { Request, Response } from "express";
import OpenAI from "openai";

const client = new OpenAI({ baseURL: "http://localhost:11434/v1", apiKey: "ollama" });
const MODEL = "mistral";

function sseEvent(type: string, data: Record<string, unknown>): string {
  return `data: ${JSON.stringify({ type, ...data })}\n\n`;
}

export async function streamAgent(req: Request, res: Response): Promise<void> {
  const { query } = req.body as { query: string };

  // ── SSE headers ─────────────────────────────────────────────────────────────
  res.setHeader("Content-Type", "text/event-stream");
  res.setHeader("Cache-Control", "no-cache");
  res.setHeader("X-Accel-Buffering", "no");  // disable nginx buffering
  res.flushHeaders();

  const messages: OpenAI.Chat.ChatCompletionMessageParam[] = [
    { role: "system", content: "You are an entity resolution agent..." },
    { role: "user", content: query },
  ];

  const tools: OpenAI.Chat.ChatCompletionTool[] = [
    {
      type: "function",
      function: {
        name: "search_filings",
        description: "Search UCC filings by entity name",
        parameters: {
          type: "object",
          properties: { name: { type: "string" } },
          required: ["name"],
        },
      },
    },
  ];

  for (let i = 0; i < 10; i++) {
    res.write(sseEvent("thought", { content: `Iteration ${i + 1}: calling Mistral...`, iteration: i + 1 }));

    const response = await client.chat.completions.create({ model: MODEL, messages, tools });
    const choice = response.choices[0];

    if (choice.finish_reason === "tool_calls") {
      for (const tc of choice.message.tool_calls ?? []) {
        const args = JSON.parse(tc.function.arguments);
        res.write(sseEvent("tool_call", { tool: tc.function.name, args, call_id: tc.id }));
        const toolResult = await executeTool(tc.function.name, args);
        messages.push(choice.message);
        messages.push({ role: "tool", tool_call_id: tc.id, content: JSON.stringify(toolResult) });
      }
    } else if (choice.finish_reason === "stop") {
      res.write(sseEvent("result", { content: choice.message.content, iterations: i + 1 }));
      res.write("data: [DONE]\n\n");
      res.end();
      return;
    }
  }

  res.write(sseEvent("error", { content: "Max iterations reached" }));
  res.write("data: [DONE]\n\n");
  res.end();
}

Client-Side EventSource Consumer

WHAT — Browser JS that connects to /agent/stream via EventSource and renders each event type differently. WHY — The browser's built-in EventSource handles reconnection automatically. For POST requests (which EventSource doesn't support natively), use the @microsoft/fetch-event-source library. GOTCHA — Always close the EventSource in the [DONE] handler; leaked connections pile up and exhaust server file descriptors.
// Use @microsoft/fetch-event-source for POST with SSE
import { fetchEventSource } from "@microsoft/fetch-event-source";

async function callAgentStream(query) {
  const log = document.getElementById("agent-log");

  await fetchEventSource("http://localhost:8000/agent/stream", {
    method: "POST",
    headers: {
      "Content-Type": "application/json",
      "X-API-Key": "sk-local-dev-key-1234",
    },
    body: JSON.stringify({ query }),

    onmessage(event) {
      if (event.data === "[DONE]") return;  // stream complete, connection closes

      const msg = JSON.parse(event.data);

      if (msg.type === "thought") {
        // Show collapsible trace step
        log.innerHTML += `<div class="trace-step">💭 ${msg.content}</div>`;
      } else if (msg.type === "tool_call") {
        // Highlight tool usage
        log.innerHTML += `<div class="tool-call">🔧 ${msg.tool}(${JSON.stringify(msg.args)})</div>`;
      } else if (msg.type === "result") {
        // Render final answer prominently
        log.innerHTML += `<div class="result">✅ ${msg.content}</div>`;
      } else if (msg.type === "error") {
        log.innerHTML += `<div class="error">❌ ${msg.content}</div>`;
      }
    },

    onerror(err) {
      console.error("SSE connection error:", err);
      throw err; // re-throw to stop automatic reconnection
    },
  });
}

SSE covers agents that complete in under 30 seconds. For deeper research tasks that might take minutes, we need the async queue pattern — submit, get a job ID, poll for completion.

Async Job Queue for Long Agents

Definition: 202 Accepted

HTTP 202 Accepted means "I received your request and I will process it, but I haven’t finished yet." The response body includes a job_id the client uses to poll GET /jobs/{id}. This is the correct status code for async operations — not 200 (which implies the work is done) and not 201 (which implies a resource was synchronously created).

WHAT — Two endpoints: POST /agent/run-async returns 202 + job_id immediately. GET /jobs/{id} returns status + result when ready. WHY — Client timeouts and proxy timeouts (typically 30–60s) make synchronous handling impossible for long agents. The async pattern decouples submission from execution. GOTCHA — In-memory job storage is fine for a single-process dev server; switch to Redis for multi-process or multi-node deployments where any replica must be able to serve the status check.
# agent_api/async_queue.py
import asyncio
import uuid
import time
from fastapi import BackgroundTasks, HTTPException, Depends
from .main import app, require_api_key, AgentRequest

# ── In-memory job store (swap for Redis in production) ────────────────────────
_jobs: dict[str, dict] = {}

async def _run_agent_background(job_id: str, query: str):
    """Background task that runs the agent and writes result to job store."""
    _jobs[job_id]["status"] = "running"
    start = time.monotonic()
    try:
        from agent import run_react_agent
        result, iterations, tool_calls = run_react_agent(query)
        _jobs[job_id].update({
            "status": "done",
            "result": result,
            "iterations": iterations,
            "tool_calls": tool_calls,
            "latency_ms": int((time.monotonic() - start) * 1000),
        })
    except Exception as exc:
        _jobs[job_id].update({
            "status": "failed",
            "error": str(exc),
        })


@app.post("/agent/run-async", status_code=202)
async def run_agent_async(
    req: AgentRequest,
    background_tasks: BackgroundTasks,
    api_key: str = Depends(require_api_key),
):
    # Idempotency: if the same key is resubmitted, return the existing job
    if req.idempotency_key and req.idempotency_key in _jobs:
        return {"job_id": req.idempotency_key, "status": "already_submitted"}

    job_id = req.idempotency_key or str(uuid.uuid4())
    _jobs[job_id] = {"status": "queued", "query": req.query, "submitted_at": time.time()}
    background_tasks.add_task(_run_agent_background, job_id, req.query)
    return {"job_id": job_id, "status": "queued", "poll_url": f"/jobs/{job_id}"}


@app.get("/jobs/{job_id}")
async def get_job(
    job_id: str,
    api_key: str = Depends(require_api_key),
):
    if job_id not in _jobs:
        raise HTTPException(status_code=404, detail="Job not found")
    job = _jobs[job_id]
    return {
        "job_id": job_id,
        "status": job["status"],              # queued | running | done | failed
        "result": job.get("result"),
        "error": job.get("error"),
        "iterations": job.get("iterations"),
        "latency_ms": job.get("latency_ms"),
    }

// src/asyncQueue.ts
import { Request, Response } from "express";
import { randomUUID } from "crypto";
import { runReactAgent } from "./agent";

type JobStatus = "queued" | "running" | "done" | "failed";
interface Job {
  status: JobStatus;
  query: string;
  result?: string;
  error?: string;
  iterations?: number;
  latency_ms?: number;
  submitted_at: number;
}

// In-memory store — swap for Redis (ioredis + bull/bullmq) in production
const jobs = new Map<string, Job>();

async function runAgentBackground(jobId: string, query: string): Promise<void> {
  const job = jobs.get(jobId)!;
  job.status = "running";
  const start = Date.now();
  try {
    const { result, iterations } = await runReactAgent(query);
    Object.assign(job, {
      status: "done",
      result,
      iterations,
      latency_ms: Date.now() - start,
    });
  } catch (err) {
    Object.assign(job, { status: "failed", error: String(err) });
  }
}

export function runAgentAsync(req: Request, res: Response): void {
  const { query, idempotency_key: key } = req.body as {
    query: string;
    idempotency_key?: string;
  };

  // Idempotency check
  if (key && jobs.has(key)) {
    res.status(202).json({ job_id: key, status: "already_submitted" });
    return;
  }

  const jobId = key ?? randomUUID();
  jobs.set(jobId, { status: "queued", query, submitted_at: Date.now() });

  // Fire and forget
  runAgentBackground(jobId, query).catch(console.error);

  res.status(202).json({
    job_id: jobId,
    status: "queued",
    poll_url: `/jobs/${jobId}`,
  });
}

export function getJob(req: Request, res: Response): void {
  const job = jobs.get(req.params.id);
  if (!job) {
    res.status(404).json({ error: "Job not found" });
    return;
  }
  res.json({
    job_id: req.params.id,
    status: job.status,
    result: job.result,
    error: job.error,
    iterations: job.iterations,
    latency_ms: job.latency_ms,
  });
}

Request Validation & Rate Limiting

Pydantic catches structural validation automatically. But we also need semantic validation (e.g., query length, character whitelist) and rate limiting to prevent a single API key from saturating the Ollama model.

WHAT — Custom Pydantic validator for query sanitization + a token bucket rate limiter keyed by API key. Returns HTTP 422 for invalid input and 429 for rate limit breaches, both with machine-readable error bodies. WHY — Returning generic 400s without detail makes debugging impossible for API consumers. Structured error bodies (RFC 7807 Problem Details style) let clients handle errors programmatically. GOTCHA — The in-memory token bucket is per-process. Behind multiple Gunicorn workers, each worker has its own bucket. For true cross-process rate limiting, use Redis with the redis-py sliding window script.
# agent_api/rate_limit.py
import time
import re
from collections import defaultdict
from fastapi import HTTPException, Header
from pydantic import BaseModel, Field, field_validator

QUERY_MAX_LEN = 2000
ALLOWED_PATTERN = re.compile(r"^[\w\s.,;:'\"\-&@#()/\[\]{}+=!?%$]+$")

class AgentRequestValidated(BaseModel):
    query: str = Field(..., min_length=1, max_length=QUERY_MAX_LEN)
    session_id: str | None = None
    idempotency_key: str | None = None

    @field_validator("query")
    @classmethod
    def query_must_be_printable(cls, v: str) -> str:
        if not ALLOWED_PATTERN.match(v):
            raise ValueError(
                "Query contains disallowed characters. "
                "Use printable ASCII: letters, digits, basic punctuation."
            )
        return v.strip()


# ── Token bucket rate limiter ─────────────────────────────────────────────────
RATE_LIMIT = 10          # requests per window
WINDOW_SECONDS = 60      # rolling window

_buckets: dict[str, dict] = defaultdict(lambda: {"tokens": RATE_LIMIT, "last_refill": time.monotonic()})

def _refill(bucket: dict) -> dict:
    now = time.monotonic()
    elapsed = now - bucket["last_refill"]
    refill = (elapsed / WINDOW_SECONDS) * RATE_LIMIT
    bucket["tokens"] = min(RATE_LIMIT, bucket["tokens"] + refill)
    bucket["last_refill"] = now
    return bucket

async def rate_limit_by_key(x_api_key: str = Header(...)):
    bucket = _refill(_buckets[x_api_key])
    if bucket["tokens"] < 1:
        raise HTTPException(
            status_code=429,
            detail={
                "error": "rate_limit_exceeded",
                "message": f"Max {RATE_LIMIT} requests per {WINDOW_SECONDS}s. Retry-After: {WINDOW_SECONDS}s.",
                "retry_after_seconds": WINDOW_SECONDS,
            },
            headers={"Retry-After": str(WINDOW_SECONDS)},
        )
    bucket["tokens"] -= 1
    return x_api_key

// src/rateLimit.ts
import { Request, Response, NextFunction } from "express";

const RATE_LIMIT = 10;
const WINDOW_MS = 60_000;

interface Bucket { tokens: number; lastRefill: number; }
const buckets = new Map<string, Bucket>();

function refill(key: string): Bucket {
  const now = Date.now();
  let bucket = buckets.get(key) ?? { tokens: RATE_LIMIT, lastRefill: now };
  const elapsed = now - bucket.lastRefill;
  bucket.tokens = Math.min(RATE_LIMIT, bucket.tokens + (elapsed / WINDOW_MS) * RATE_LIMIT);
  bucket.lastRefill = now;
  buckets.set(key, bucket);
  return bucket;
}

export function rateLimitMiddleware(req: Request, res: Response, next: NextFunction): void {
  const key = req.headers["x-api-key"] as string;
  if (!key) { res.status(401).json({ error: "Missing API key" }); return; }

  const bucket = refill(key);
  if (bucket.tokens < 1) {
    res.status(429)
       .header("Retry-After", String(WINDOW_MS / 1000))
       .json({
         error: "rate_limit_exceeded",
         message: `Max ${RATE_LIMIT} requests per 60s.`,
         retry_after_seconds: 60,
       });
    return;
  }
  bucket.tokens -= 1;
  next();
}

// ── Input validation middleware ───────────────────────────────────────────────
const ALLOWED = /^[\w\s.,;:'"\\-&@#()/\[\]{}+=!?%$]+$/;

export function validateQuery(req: Request, res: Response, next: NextFunction): void {
  const { query } = req.body as { query?: string };
  if (!query || query.length === 0 || query.length > 2000) {
    res.status(422).json({ error: "query must be 1–2000 characters" });
    return;
  }
  if (!ALLOWED.test(query)) {
    res.status(422).json({ error: "query contains disallowed characters" });
    return;
  }
  next();
}

🦎 Open Source Note: Ollama as a Docker Sidecar

Ollama can run as a Docker sidecar — no GPU required for Mistral-7B-Q4 on a 8 GB VPS. The quantized model loads into CPU RAM and serves inference at ~5–8 tokens/second on a Hetzner CX31 (€8.49/month). This is fast enough for a real production API handling moderate traffic. Set OLLAMA_HOST=0.0.0.0 so the container listens on all interfaces, not just localhost.

WHAT — Multi-stage Dockerfile: stage 1 installs Python deps, stage 2 copies only the installed packages into a slim runtime image. WHY — A naive single-stage build that includes build tools (gcc, pip, wheel) typically weighs 1.2 GB. Multi-stage cuts this to ~220 MB because build tools stay in the intermediate layer that is never shipped. GOTCHA — ENTRYPOINT sets the executable; CMD sets the default arguments. Override CMD at runtime without changing the image. Use ENTRYPOINT for the server binary, CMD for its flags so they can be overridden in Compose without rebuilding.

Graceful Shutdown

When Docker stops a container it sends SIGTERM, waits 10 seconds, then sends SIGKILL. A graceful shutdown handler lets in-flight requests complete before the process exits.

# agent_api/lifespan.py
from contextlib import asynccontextmanager
from fastapi import FastAPI

@asynccontextmanager
async def lifespan(app: FastAPI):
    # ── Startup ──────────────────────────────────────────────────────────────
    print("Starting up: warming Ollama connection...")
    # Optionally pre-load the model so the first request isn't cold
    yield
    # ── Shutdown (runs after SIGTERM, before SIGKILL) ─────────────────────────
    print("Shutting down: draining in-flight requests...")
    # asyncio event loop is still running; await pending jobs here

app = FastAPI(lifespan=lifespan)

// src/index.ts
import { app } from "./app";
import http from "http";

const server = http.createServer(app);
server.listen(3000, () => console.log("API listening on :3000"));

// ── Graceful shutdown ──────────────────────────────────────────────────────────
// Docker sends SIGTERM → we stop accepting new connections → drain active ones
process.on("SIGTERM", () => {
  console.log("SIGTERM received: closing server...");
  server.close(() => {
    console.log("All connections drained. Exiting.");
    process.exit(0);
  });
  // Force exit if drain takes too long
  setTimeout(() => process.exit(1), 9_000);
});
