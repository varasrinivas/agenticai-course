M03: skill.md Files

Stop retyping the same long prompts. Write them once as a .md file, give them a name, and invoke them with a single slash command — in any project, from any shell, even inside CI pipelines.

Learning Objectives

  • Explain what a skill.md file is and why it replaces manual prompt retyping.
  • Read and write the two-part structure: frontmatter + prompt body.
  • Use template variables to pass arguments into a skill body.
  • Create project-level and global skills and know which takes precedence.
  • Invoke skills interactively with tab completion and non-interactively from scripts.
  • Build a personal toolkit of 5+ reusable global skills.
Before writing any skill, you need a mental model for why they exist — and what the pre-skills world looked like.

What Is a skill.md File?

Everyday Analogy

BEFORE: Imagine you work in a bank, and every time you process a wire transfer you must fill out a 14-field form from memory — account numbers, routing, beneficiary, memo, compliance code — or risk rejection. You do this a dozen times a day, and each attempt has slightly different wording.

PAIN: One afternoon you realize every wire goes through the same four verification steps, the memo always says the same thing, and your re-typed prompts are drifting — yesterday you forgot "auth bypass" from the security checklist, today you forgot the IBAN format. Inconsistency compounds into real bugs.

MAPPING: A bank teller eventually grabs a laminated cheat-sheet and pins it to their desk — one authoritative version, always right, always at hand. A skill.md is that cheat-sheet for Gemini CLI: you write the full prompt once, give it a name, and from that moment /security-review @src/auth.js expands into the entire 14-field form — correctly, consistently, every time.

Technical Definition

A skill.md is a Markdown file placed in a .gemini/skills/ directory (project-level) or ~/.gemini/skills/ (global). It contains optional YAML frontmatter declaring the skill's name, description, and named arguments, followed by a Markdown body that is the prompt Gemini will execute. The name: field becomes the slash command; {{argument-name}} placeholders in the body are replaced with resolved values at invocation time.

On startup, Gemini CLI scans both directories and registers each skill as a /skill-name command. Type / in the REPL to see the full list, including built-ins and your custom skills side by side.

Why It Matters

Teams that standardize code-review prompts catch 3–5x more security issues than those who free-form it each time (because the checklist stays complete). Skills enforce that consistency. They also travel with the repo — a teammate who clones your project gets all project-level skills immediately, no setup step needed.

Where Skills Live

.gemini/ # project-level (check into git) └── skills/ ├── security-review.md ├── pr-description.md └── test-gen.md ~/.gemini/ # global (personal toolkit) └── skills/ ├── explain.md └── commit-msg.md
Tip: Scope Priority

When both a project skill and a global skill share the same name:, the project-level skill wins. This lets you override a personal default for specific projects without touching your global toolkit.

Anatomy of a skill.md File

A skill file has two sections separated by nothing but a blank line after the closing ---. Here is a full, annotated example:

.gemini/skills/security-review.md 
---
name: security-review
description: Review code for OWASP Top 10 vulnerabilities
arguments:
  - name: file
    description: The file to review
    required: true
---

You are a security expert. Review the code in {{file}} for these vulnerability classes:

1. **SQL Injection** — look for string concatenation in queries
2. **XSS** — unescaped user input rendered to HTML
3. **Auth bypass** — missing authentication checks
4. **Path traversal** — user-controlled file paths
5. **Secrets exposure** — hardcoded API keys, passwords

For each finding:
- Severity: Critical / High / Medium / Low
- Location: file:line
- Description: what the vulnerability is
- Fix: exact code change to remediate

Output as a structured markdown report.

WHAT — The frontmatter block

Lines between the two --- fences are YAML. name: is the slug that becomes /security-review. description: appears in tab-completion hints so teammates know what the skill does. arguments: is an array; each entry declares a named placeholder used in the body.

WHY — Arguments vs. free text

Declaring arguments as named entries (not just free text after the command) lets Gemini CLI provide per-argument hints during tab completion and validate that required arguments are present before running. An undeclared argument silently passes as a raw string; a declared-required argument that is missing produces an error early, not a broken prompt.

WHAT — The body / prompt

Everything after the closing --- is the prompt Gemini receives. It is plain Markdown — headings, bullets, bold text all work — and is sent as the user turn in the conversation. The {{file}} token is replaced with the resolved argument value at invocation time.

GOTCHA — Template variable syntax

The delimiters are double curly braces: {{argument-name}}. The name must exactly match the name: key in the frontmatter arguments array. Typos silently pass the literal string {{typo}} to the model, which is confusing but not an error.

What Just Happened?

You read a complete skill file. The frontmatter registered a slash command /security-review with one required argument file. The body is a structured security checklist. When you run /security-review @src/auth.js, Gemini resolves {{file}} to the contents of src/auth.js and runs the full prompt.

Now that you understand the file format, let’s build five practical skills that cover the most common developer workflows.

Creating Your First Skills

Start by creating the skills directory. Run the commands for your OS:

# Create project-level skills directory
New-Item -ItemType Directory -Force ".gemini\skills"

# Create global skills directory
New-Item -ItemType Directory -Force "$env:USERPROFILE\.gemini\skills"
# Create project-level skills directory
mkdir -p .gemini/skills

# Create global skills directory
mkdir -p ~/.gemini/skills

Skill 1 — code-review.md

A comprehensive code review covering correctness, style, performance, and security. This is the skill you’ll use most often.

.gemini/skills/code-review.md 
---
name: code-review
description: Comprehensive code review for correctness, style, performance, and security
arguments:
  - name: file
    description: The file or diff to review
    required: true
---

Review the code in {{file}} across four dimensions:

## 1. Correctness
- Off-by-one errors, null/undefined dereferences
- Incorrect logic or edge cases (empty input, concurrent access)
- Unhandled exceptions or error paths

## 2. Style & Readability
- Variable/function names that obscure intent
- Functions longer than 30 lines (split suggestion)
- Missing or misleading comments

## 3. Performance
- Unnecessary loops inside loops (O(n²) patterns)
- Missing indexes on database queries
- Large allocations inside hot paths

## 4. Security
- User input used without sanitization
- SQL or shell injection vectors
- Overly permissive access controls

For each issue, output:
**[SEVERITY: Critical|High|Medium|Low]** `file:line` — description + suggested fix

End with a one-paragraph summary: overall quality, top priority fix.
@'
---
name: code-review
description: Comprehensive code review for correctness, style, performance, and security
arguments:
  - name: file
    description: The file or diff to review
    required: true
---

Review the code in {{file}} across four dimensions...
'@ | Out-File -FilePath ".gemini\skills\code-review.md" -Encoding utf8
cat > .gemini/skills/code-review.md << 'EOF'
---
name: code-review
description: Comprehensive code review for correctness, style, performance, and security
arguments:
  - name: file
    description: The file or diff to review
    required: true
---

Review the code in {{file}} across four dimensions...
EOF

Invocation: /code-review @src/auth.js

Expected output snippet:

[SEVERITY: High] src/auth.js:42 — User-supplied `username` concatenated directly into SQL query. Fix: use parameterized query `db.query("SELECT * FROM users WHERE id = ?", [username])`. [SEVERITY: Medium] src/auth.js:67 — Function `validateToken()` is 58 lines. Extract JWT decode, expiry check, and scope validation into separate helpers. Summary: Overall quality is fair. The SQL injection at line 42 is the critical fix — ship nothing else until that’s resolved...

Skill 2 — pr-description.md

Generates a pull request description from staged git diff — no argument needed because the skill reads the diff itself.

.gemini/skills/pr-description.md 
---
name: pr-description
description: Generate a pull request description from the current git diff
---

Run `git diff --cached` to see what is staged. Then write a PR description with:

- **What changed**: 2–3 bullet points describing the changes
- **Why**: motivation behind the change or ticket reference
- **Testing**: how to verify the change works
- **Screenshots**: [if UI changes, note where to add them]

Keep it under 200 words. Be specific — avoid vague phrases like "various improvements".
Use present tense imperative: "Add X", "Fix Y", "Remove Z".

Invocation: /pr-description (no arguments — the model reads the staged diff directly)

Skill 3 — test-gen.md

.gemini/skills/test-gen.md 
---
name: test-gen
description: Generate unit tests for a given function or file
arguments:
  - name: file
    description: The source file to generate tests for
    required: true
  - name: framework
    description: Test framework to use (jest, pytest, vitest, mocha)
    required: false
    default: "jest"
---

Read {{file}} and generate a complete test suite using {{framework}}.

Requirements:
1. One `describe` block per exported function/class
2. Cover: happy path, edge cases (empty, null, large input), error cases
3. All tests must be self-contained — no global state between tests
4. Use realistic fixture data, not "foo"/"bar" placeholders
5. For async functions, test both resolved and rejected paths

Write ONLY the test file. Do not include explanations outside the code.

Invocation: /test-gen @src/utils/parser.js or with framework: /test-gen @src/api.py pytest

Skill 4 — changelog-entry.md

.gemini/skills/changelog-entry.md 
---
name: changelog-entry
description: Write a CHANGELOG.md entry from recent git commits
arguments:
  - name: version
    description: The version number for this release (e.g. 2.1.0)
    required: true
---

Run `git log --oneline -20` to see the last 20 commits.

Write a CHANGELOG.md entry for version {{version}} using Keep a Changelog format:

## [{{version}}] - YYYY-MM-DD

### Added
- New features (commits with feat: or add prefix)

### Fixed
- Bug fixes (commits with fix: prefix)

### Changed
- Modifications to existing behavior

### Removed
- Deletions or deprecations

Group commits by type. Skip chore/ci/refactor commits unless they affect users.
Use present tense. Replace today’s date for YYYY-MM-DD.

Invocation: /changelog-entry 2.4.0

Skill 5 — explain-error.md

.gemini/skills/explain-error.md 
---
name: explain-error
description: Explain an error message with root cause and fix
arguments:
  - name: error
    description: The error message or stack trace to explain
    required: true
---

Explain this error:

> {{error}}

Structure your answer as:
1. **What it means** — plain English explanation, no jargon
2. **Root cause** — why this error occurs (the underlying mechanism)
3. **Most common trigger** — the code pattern that causes it most often
4. **Fix** — the exact change to make, with before/after code if applicable
5. **How to prevent it** — guard pattern or lint rule to avoid in future

Assume the reader is a mid-level developer who knows the language but hasn’t seen this specific error before.

Invocation: /explain-error "TypeError: Cannot read properties of undefined (reading 'map')"

Checkpoint

You now have 5 skill files in .gemini/skills/. Restart Gemini CLI (or type /refresh if supported) and type / — you should see all five listed alongside built-in commands.

Calling Skills

Skills are invoked by typing /skill-name at the Gemini CLI prompt. There are three invocation patterns:

Invocation patterns 
# 1. Basic call — no arguments (skill reads context itself)
/pr-description

# 2. With a required argument — @file resolves to file contents
/code-review @src/auth.js

# 3. Chained with additional context
@src/feature-branch-changes.diff /pr-description

# 4. With explicit string argument (no @-file resolution)
/explain-error "TypeError: Cannot read properties of undefined"

# 5. Multiple arguments
/test-gen @src/parser.js pytest

WHAT — The @-file prefix

Prefixing a path with @ tells Gemini CLI to read that file and inject its contents in place of the path token. Without @, the literal string src/auth.js is passed, which is useful when your skill prompt explicitly says "check whether this file exists" rather than wanting its contents.

GOTCHA — Arguments after the skill name

Arguments are positional in the order they are declared in the frontmatter. The first token after /skill-name maps to the first declared argument. If you have two required arguments, supply both: /compare-implementations @v1.js @v2.js.

Tab Completion

After typing /, Gemini CLI shows a dropdown of all available skills — built-in commands first, then your custom skills in alphabetical order. Arrow keys navigate the list; Enter selects. The description: field from your frontmatter appears as a hint next to each entry.

Global Skills Library

Skills placed in ~/.gemini/skills/ are available in every project on your machine. Build a personal productivity toolkit once and carry it everywhere — unlike project skills, global skills never need to be checked into version control.

Here is a recommended global skills library that covers the most frequent developer tasks:

/explain
Explain a concept as if I’m a beginner — no assumed knowledge
/summarize
Summarize a long document into 5 bullet points
/translate-docs
Translate a README or doc file to another language
/daily-standup
Generate standup notes from recent git log
/refactor-clean
Clean up code without changing observable behavior
/commit-msg
Generate a conventional commit message from staged diff
~/.gemini/ └── skills/ ├── explain.md # Explain a concept to a beginner ├── summarize.md # Summarize long document → 5 bullets ├── translate-docs.md # Translate README to another language ├── daily-standup.md # Generate standup from recent git log ├── refactor-clean.md # Clean up code, no behavior change └── commit-msg.md # Conventional commit from staged diff

Set up the global directory and a starter commit-msg skill:

# Create global skills directory
New-Item -ItemType Directory -Force "$env:USERPROFILE\.gemini\skills"

# Write commit-msg skill
@'
---
name: commit-msg
description: Generate a conventional commit message from the staged diff
---

Run `git diff --cached` to see what is staged.

Write a conventional commit message:
- Format: `type(scope): short summary` (max 72 chars)
- Types: feat, fix, docs, style, refactor, perf, test, chore
- Scope: the module/package affected (optional)
- Body: why the change was made (not what — that is in the diff)
- Footer: `Closes #123` if this fixes a known issue

Output ONLY the commit message, nothing else.
'@ | Out-File -FilePath "$env:USERPROFILE\.gemini\skills\commit-msg.md" -Encoding utf8

Write-Host "Global skills directory ready at $env:USERPROFILE\.gemini\skills"
# Create global skills directory
mkdir -p ~/.gemini/skills

# Write commit-msg skill
cat > ~/.gemini/skills/commit-msg.md << 'EOF'
---
name: commit-msg
description: Generate a conventional commit message from the staged diff
---

Run `git diff --cached` to see what is staged.

Write a conventional commit message:
- Format: `type(scope): short summary` (max 72 chars)
- Types: feat, fix, docs, style, refactor, perf, test, chore
- Scope: the module/package affected (optional)
- Body: why the change was made (not what — that is in the diff)
- Footer: `Closes #123` if this fixes a known issue

Output ONLY the commit message, nothing else.
EOF

echo "Global skills directory ready at ~/.gemini/skills"

Arguments & Template Variables

Skills can declare multiple arguments with optional defaults. Here is an advanced skill that takes two required files and one optional criteria string:

.gemini/skills/compare-implementations.md 
---
name: compare-implementations
description: Compare two implementations and recommend the better one
arguments:
  - name: file1
    description: First implementation file
    required: true
  - name: file2
    description: Second implementation file
    required: true
  - name: criteria
    description: Evaluation criteria (comma-separated)
    required: false
    default: "readability, performance, maintainability"
---

Compare the two implementations:

**Implementation A:** {{file1}}
**Implementation B:** {{file2}}

Evaluate on: {{criteria}}

For each criterion:
1. Score each implementation 1–5
2. Explain the score with a specific code example from each file
3. Declare a winner for that criterion

Final recommendation:
- Overall winner and confidence level (High / Medium / Low)
- The one change to Implementation B that would close the gap most
- If A and B are roughly equal, say so — don’t force a winner

Invocation: /compare-implementations @src/v1/parser.js @src/v2/parser.js

Or with custom criteria: /compare-implementations @v1.js @v2.js "type safety, bundle size, test coverage"

Advanced: Default Values

A default: key in the argument definition is used when the argument is not supplied at invocation time. In the example above, if you call /compare-implementations @v1.js @v2.js without a third argument, {{criteria}} resolves to "readability, performance, maintainability". This makes skills ergonomic for the common case while still allowing customization.

Running Skills Non-Interactively

Skills are not limited to interactive sessions. The --no-interactive flag (also written -n) puts Gemini CLI into non-interactive mode, making it scriptable from CI/CD pipelines, pre-commit hooks, and shell scripts.

# Run security review on all files changed in the current PR
# Outputs JSON so downstream tools can parse findings

$changedFiles = git diff --name-only HEAD~1 HEAD

foreach ($file in $changedFiles) {
    if ($file -match "\.(js|ts|py|go|rb)$") {
        Write-Host "Reviewing $file..."
        gemini -p "/security-review @$file" `
               --no-interactive `
               --output-format json `
            | Out-File -Append -FilePath "security-report.json"
    }
}

# Pre-commit hook: block commit if critical issues found
$report = Get-Content "security-report.json" | ConvertFrom-Json
$criticals = $report | Where-Object { $_.severity -eq "Critical" }
if ($criticals.Count -gt 0) {
    Write-Error "BLOCKED: $($criticals.Count) critical security issue(s) found."
    exit 1
}
#!/usr/bin/env bash
# Run security review on all files changed in the current PR
# Outputs JSON so downstream tools can parse findings

set -euo pipefail

REPORT_FILE="security-report.json"
: > "$REPORT_FILE"   # truncate/create report file

git diff --name-only HEAD~1 HEAD | while read -r file; do
    if [[ "$file" =~ \.(js|ts|py|go|rb)$ ]]; then
        echo "Reviewing $file..."
        gemini -p "/security-review @$file" \
               --no-interactive \
               --output-format json \
            >> "$REPORT_FILE"
    fi
done

# Pre-commit hook: block commit if critical issues found
CRITICAL_COUNT=$(jq '[.[] | select(.severity == "Critical")] | length' "$REPORT_FILE")
if [[ "$CRITICAL_COUNT" -gt 0 ]]; then
    echo "BLOCKED: $CRITICAL_COUNT critical security issue(s) found." >&2
    exit 1
fi

echo "Security review passed — no critical issues found."

WHAT — --no-interactive flag

Disables the REPL. Gemini reads the -p prompt string, executes it (including any @file resolutions and skill invocations), writes the response to stdout, and exits. The process exit code is 0 on success, non-zero on error, so scripts can branch on failure.

WHY — --output-format json

By default, Gemini writes prose. --output-format json wraps the response in a JSON envelope, making it parseable by jq, PowerShell’s ConvertFrom-Json, or any language with a JSON library. This turns a free-form model response into structured pipeline data.

GOTCHA — Token costs in CI

Running skills on every changed file in CI can add up. Gate on file extension (as shown above) and consider caching results by file hash to skip files that haven’t changed. Most teams run skill-based CI checks on PRs only, not on every push.

Warning: API Key in CI

Gemini CLI reads GEMINI_API_KEY from the environment. Store it as a CI secret (GitHub Actions: secrets.GEMINI_API_KEY; GitLab CI: masked variable). Never hardcode it in scripts or commit it to the repository.

What Just Happened?

You saw how skills compose with the --no-interactive flag to become first-class CI tools. The same skill body that runs in your local REPL now runs headlessly on a build server, with structured JSON output that downstream scripts can parse and act on.

Summary

You now have everything you need to build and deploy a personal skills library:

  • A skill.md file has two parts: YAML frontmatter (name, description, arguments) and a Markdown prompt body with {{template-variables}}.
  • Project skills live in .gemini/skills/ and travel with the repo. Global skills live in ~/.gemini/skills/ and apply everywhere. Project-level wins on name collisions.
  • Arguments can be required or optional with defaults. The @file prefix in an invocation injects file contents into the resolved argument.
  • Tab completion after / shows your custom skills alongside built-ins, using the description: as a hint.
  • Combine --no-interactive and --output-format json to use skills in CI pipelines and pre-commit hooks.
