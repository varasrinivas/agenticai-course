System Design & Architecture

You have a PRD. Now you need to turn it into something engineers can build from. This module walks through using Gemini CLI to generate system architecture, Mermaid diagrams, OpenAPI contracts, database schemas, and Architecture Decision Records — all referencing the @docs/ artifacts from M05 so every design decision traces back to a requirement.

System Design from PRD

Analogy — The Blueprints Before the Bricks

An architect doesn't hand a builder a paragraph describing the desired house — they provide blueprints: floor plans, elevation drawings, electrical schematics. Each drawing targets a different audience (structural engineer, electrician, plumber) and each reveals constraints invisible in prose. System design does the same thing: it translates "a task manager for remote teams" into service boundaries, data flows, and interface contracts that different engineers can build independently.

The pain without design artifacts: two engineers build the same feature from the same PRD and produce incompatible data shapes, requiring a rewrite at integration time. The mapping to Gemini CLI: your PRD already contains implicit design decisions — Gemini surfaces them explicitly, turns them into diagrams, and exposes the ones you haven't made yet.

Mermaid Diagrams

Technical Definition — Mermaid

MermaidA JavaScript-based diagramming tool that renders diagrams from text definitions. Supported natively by GitHub, GitLab, Notion, and VS Code. Diagrams are version-controlled as text, making them diffable and reviewable like code. is a text-to-diagram tool embedded in GitHub Markdown, GitLab, Notion, and VS Code. Write diagram code as text, render as a visual. Because it's plain text, diagrams live in your repo alongside the code they describe, and every change shows up in git diff. The three types Gemini generates most reliably for SDLC are: flowchart (component views), sequenceDiagram (request/response flows), and erDiagram (database schemas).

Diagrams communicate structure. OpenAPI contracts make that structure executable — let's define the API surface area.

API Contracts — OpenAPI 3.0

An OpenAPI specA machine-readable API contract in YAML or JSON format. Defines endpoints, HTTP methods, request/response schemas, authentication, and error codes. Tools like Swagger UI, Redoc, and openapi-ts can generate documentation and clients from it automatically. is the contract between frontend and backend teams. Generated from your PRD, it prevents the "I thought the response would include X" conversations that happen when both sides implement from prose alone.

Gemini CLI prompt

Five Endpoints — TaskPulse API

OpenAPI Endpoints — Animated Reveal
GET /api/tasks List tasks for authenticated team, filterable by status/assignee
POST /api/tasks Create a new task; returns task object with generated ID
GET /api/tasks/{id} Fetch a single task with status history and latest update
PATCH /api/tasks/{id}/status Post a status update; triggers realtime push + notification job
GET /api/teams/{id}/digest Return the async standup digest grouped by status for a team

OpenAPI YAML (partial)

docs/api-contracts/openapi.yaml (excerpt)
openapi: "3.0.3"
info:
  title: TeamPulse API
  version: "1.0.0"
  description: Async team status board API
servers:
  - url: https://api.teampulse.dev/v1

components:
  securitySchemes:
    BearerAuth:
      type: http
      scheme: bearer
      bearerFormat: JWT
  schemas:
    Task:
      type: object
      required: [id, title, status, assigneeId, teamId]
      properties:
        id: { type: string, format: uuid }
        title: { type: string, maxLength: 200 }
        status:
          type: string
          enum: [todo, in_progress, blocked, done]
        assigneeId: { type: string, format: uuid }
        teamId: { type: string, format: uuid }
        updatedAt: { type: string, format: date-time }
    StatusUpdateRequest:
      type: object
      required: [status, note]
      properties:
        status:
          type: string
          enum: [todo, in_progress, blocked, done]
        note: { type: string, maxLength: 500 }
    Error:
      type: object
      required: [code, message]
      properties:
        code: { type: string }
        message: { type: string }

paths:
  /tasks:
    get:
      summary: List team tasks
      security: [{ BearerAuth: [] }]
      parameters:
        - name: status
          in: query
          schema:
            type: string
            enum: [todo, in_progress, blocked, done]
        - name: assigneeId
          in: query
          schema: { type: string, format: uuid }
      responses:
        "200":
          description: Paginated task list
          content:
            application/json:
              schema:
                type: object
                properties:
                  tasks:
                    type: array
                    items: { $ref: "#/components/schemas/Task" }
                  total: { type: integer }
        "401":
          description: Unauthorized
          content:
            application/json:
              schema: { $ref: "#/components/schemas/Error" }
WHAT: A complete OpenAPI 3.0 spec with reusable schemas, security scheme, and standardised error shapes.
WHY: With this file in place, you can run npx openapi-ts to generate a fully-typed TypeScript client for your frontend — no hand-writing fetch wrappers.
GOTCHA: Gemini may use OpenAPI 3.1 syntax (type: [string, null]) which is not yet supported by all tooling. Ask explicitly for "OpenAPI 3.0.3 compatible" format.

Database Schema — PostgreSQL & Prisma

Gemini CLI prompt
gemini "@docs/diagrams/data-model.mmd Design the PostgreSQL database schema for this data model. Generate CREATE TABLE statements with: UUID primary keys, appropriate indexes for query patterns in @docs/prd.md, foreign key constraints, and created_at/updated_at timestamps. Include comments on each table."
Generated PostgreSQL (tasks table)
-- Tasks: core work unit for TeamPulse
CREATE TABLE tasks (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  team_id      UUID NOT NULL REFERENCES teams(id) ON DELETE CASCADE,
  assignee_id  UUID REFERENCES users(id) ON DELETE SET NULL,
  title        VARCHAR(200) NOT NULL,
  description  TEXT,
  status       VARCHAR(20) NOT NULL DEFAULT 'todo'
                 CHECK (status IN ('todo','in_progress','blocked','done')),
  due_date     TIMESTAMPTZ,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Index for the team digest endpoint (GET /api/teams/:id/digest)
CREATE INDEX idx_tasks_team_status ON tasks(team_id, status);
-- Index for assignee workload view
CREATE INDEX idx_tasks_assignee ON tasks(assignee_id) WHERE status != 'done';

-- Auto-update updated_at on every change
CREATE TRIGGER set_tasks_updated_at
  BEFORE UPDATE ON tasks
  FOR EACH ROW EXECUTE FUNCTION update_updated_at_column();
WHAT: Gemini inferred the query patterns from the PRD user journeys and pre-created the indexes for them — no DBA required for the initial schema.
WHY: The partial index (WHERE status != 'done') keeps the assignee index small — only active tasks are indexed, matching the most common query pattern.

Prisma Schema Equivalent

Gemini CLI follow-up prompt

model Task {
  id          String   @id @default(uuid())
  teamId      String
  assigneeId  String?
  title       String   @db.VarChar(200)
  description String?  @db.Text
  status      TaskStatus @default(todo)
  dueDate     DateTime?
  createdAt   DateTime @default(now())
  updatedAt   DateTime @updatedAt

  team         Team           @relation(fields: [teamId], references: [id], onDelete: Cascade)
  assignee     User?          @relation(fields: [assigneeId], references: [id], onDelete: SetNull)
  statusUpdates StatusUpdate[]
  notifications Notification[]

  @@index([teamId, status])
  @@index([assigneeId], name: "idx_tasks_assignee")
}

Schema is defined. Now let's document why you made the key choices — and generate an ADR that future team members will actually read.

Architecture Decision Records

Technical Definition — ADR

An Architecture Decision RecordA short, immutable document that captures one significant architectural decision: what was decided, why, what alternatives were considered, and what the consequences are. ADRs are numbered sequentially (ADR-001, ADR-002...) and never edited — a changed decision gets a new ADR that supersedes the old one. captures the "why" behind a technology choice so that future engineers (including you, six months from now) don't reverse decisions without understanding their context. The best ADRs are short (one page), specific (reference actual requirements), and honest (list the negatives, not just the positives).

Gemini CLI prompt
gemini "@docs/prd.md @docs/tech-stack.md Write an ADR for choosing PostgreSQL over MongoDB for this project. Format: Title, Number (ADR-001), Status (Accepted), Context (why this decision was needed, reference specific PRD sections), Decision (what and why), Consequences (list positive AND negative), Alternatives Considered (MongoDB + one other). Use markdown."

Generated ADR

ADR-001: Use PostgreSQL as the Primary Database
Accepted
Context

The PRD (§5 NFR-01) requires sub-200ms response times and (§4 FR-09) real-time team digest aggregation across up to 300 records. We need ACID guarantees for status update consistency. The team has 2 engineers with strong SQL backgrounds. The approved tech stack uses Supabase, which provides PostgreSQL with built-in realtime subscriptions.

Decision

Use PostgreSQL 15 via Supabase. The digest aggregation query (JOIN across tasks + status_updates + team_members) maps cleanly to relational algebra. The Supabase Realtime layer uses PostgreSQL logical replication, meaning we get push updates without a separate message broker. Prisma ORM provides type-safe queries and migration management.

Consequences
+ACID transactions guarantee status update consistency across tasks, updates, and notification records
+Single data platform (Supabase) provides DB + Realtime + Auth Storage — reduces ops surface area
+Prisma migrations are version-controlled and support rollbacks
−Schema migrations require planning; no schema-free flexibility if data model changes frequently in early iterations
−Supabase free tier limits to 500MB storage and pauses after 1 week of inactivity — production must use paid plan
Alternatives Considered

MongoDB (Atlas): Flexible schema suits early iteration but lacks the row-level realtime subscriptions we need from Supabase. Aggregation pipelines for the digest query are significantly more complex than a SQL JOIN. Rejected: operational complexity without matching benefit for our query patterns.

PlanetScale (MySQL): Excellent horizontal scalability but foreign key constraints are disabled by default — incompatible with our data integrity requirements. Rejected: schema enforcement is not optional at our correctness requirements.

Design Review — Multi-File Consistency Check

The most powerful use of @ mentions in the design phase is loading all design artifacts simultaneously and asking Gemini to reason across them. A solo reviewer misses inconsistencies that a fresh reader of the whole document set catches immediately.

Gemini CLI prompt
gemini "@docs/prd.md @docs/api-contracts/ @docs/adr/ @docs/diagrams/ Review all design artifacts for: 1) Gaps (requirements in the PRD not covered by the API or schema), 2) Inconsistencies (entity names, field types, or status values that differ between artifacts), 3) Missing error cases in the OpenAPI spec. List each finding as: [GAP|INCONSISTENCY|MISSING] — location — description — recommendation."
WHAT: Loading directories (@docs/api-contracts/) injects all files in that directory. Gemini sees the PRD, all YAML contracts, all ADRs, and all diagrams in one context.
WHY: Context windows exist for exactly this: multi-document reasoning that's impossible for a human to hold in working memory simultaneously.
GOTCHA: Loading four directories can push you past your context budget on large projects. Prioritize: PRD + OpenAPI + ERD diagram is the highest-signal triad. Add ADRs if budget permits.
Design Review Findings — Sample Output
GAP
docs/api-contracts/openapi.yaml → PRD §4 FR-04: PRD requires team members to be able to "unassign" a task. There is no DELETE /api/tasks/{id}/assignee endpoint or PATCH body field for assigneeId: null. Recommendation: Add PATCH /api/tasks/{id} with optional assigneeId field in request schema.
INCONSISTENCY
openapi.yaml vs data-model.mmd: OpenAPI StatusUpdateRequest uses status values in-progress (hyphen), ER diagram uses in_progress (underscore). Recommend: standardise on underscore to match PostgreSQL CHECK constraint and Prisma enum.
GAP
openapi.yaml → PRD §4 FR-09 (Digest): The GET /api/teams/{id}/digest endpoint is defined but its response schema only shows task IDs, not the full status note text. PRD §4 requires "latest status note" to be visible in the digest. Recommendation: Expand DigestTask schema to include latestNote: string.
MISSING
openapi.yaml — Error cases: POST /api/tasks has no 409 Conflict response for duplicate task titles within a team (PRD §5 NFR-03 requires unique names per team). Add 409 response with code: "DUPLICATE_TASK_TITLE".
Why It Matters

Four inconsistencies found in 30 seconds of prompt time. Each one would have surfaced as a bug, a blocked PR, or a heated Slack thread if caught at implementation time instead of design time. Design review with Gemini is the cheapest bug fix in the SDLC: the fix is editing a YAML file, not rewriting a service.
