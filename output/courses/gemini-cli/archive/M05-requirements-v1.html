The 5-Phase SDLC Pipeline

Analogy — The Relay Race

Think of a software project as a relay race with five legs: Requirements, Design, Implementation, Testing, and Deployment. Each runner receives the baton from the previous one. If the first runner — Requirements — drops it, every subsequent team member runs a slightly different race. The baton in our analogy is shared understanding: what we're building, why, and for whom.

The pain without clear requirements: developers build the right system to the wrong spec, QA finds gaps at the last moment, and stakeholders say "that's not what I meant" at demo day. The mapping to Gemini CLI: in under five minutes you can have a PRD, user stories, and acceptance criteria that all align — because they were generated from the same source prompt in a single session.

Technical Definition — SDLC

The Software Development Life Cycle (SDLC) is a structured process for planning, creating, testing, and deploying software. It turns vague ideas into shippable systems by enforcing checkpoints at each phase. Modern SDLC is iterative — you may loop through phases multiple times per sprint — but the phase sequence stays the same. Each phase produces a documented artifact that feeds the next.

Why phases matter for Gemini CLI: Each phase uses different prompt patterns. Requirements prompts are exploratory ("generate," "list," "expand"). Design prompts are structural ("diagram," "define contracts"). Implementation prompts are operational ("write," "implement," "refactor"). Knowing which phase you're in tells you which prompts to reach for.

PRD Generation — From Vague Idea to Structured Spec

A vague ideaAn informal description of a product concept — typically a sentence or two written by a founder, PM, or developer. It captures intent but lacks detail about users, scope, constraints, or success metrics. Gemini's job is to surface what's missing. is what most projects actually start with. The trick is not to sit on it — it's to extract all the implicit assumptions before a single line of code is written.

Step 1 — Write your idea file

Create a plain-text file idea.txt with as little or as much as you have:

idea.txt
A task manager app for remote dev teams. People forget what everyone
else is working on, standups are painful, and there's no single place
to see what's blocked. Maybe some kind of async status board.

Step 2 — Generate the PRD

New-Item -ItemType Directory -Force docs | Out-Null
gemini "@idea.txt Generate a complete PRD. Include: 1) Problem Statement, 2) Target Users with personas, 3) Goals and Success Metrics (with numbers), 4) Functional Requirements (must-haves), 5) Non-Functional Requirements (performance, security, scale), 6) Out of Scope, 7) Open Questions. Use markdown headers." | Out-File docs/prd.md -Encoding utf8
mkdir -p docs
gemini "@idea.txt Generate a complete PRD. Include: 1) Problem Statement, 2) Target Users with personas, 3) Goals and Success Metrics (with numbers), 4) Functional Requirements (must-haves), 5) Non-Functional Requirements (performance, security, scale), 6) Out of Scope, 7) Open Questions. Use markdown headers." > docs/prd.md
WHAT: Gemini reads your idea.txt and generates a structured PRD in markdown, piped directly to docs/prd.md.
WHY: The explicit section list prevents Gemini from omitting critical sections. Without it, you get a summary — not a spec.
GOTCHA: Gemini will invent plausible-sounding success metrics. Review every number — "99.9% uptime" and "sub-200ms response time" are defaults, not your actual requirements.

You have a PRD. Now let's extract the user-facing behaviors into Gherkin stories that QA can verify and GitHub can track.

User Stories in Gherkin Format

Analogy — The Recipe Card

A PRD tells you what the dish should taste like. A Gherkin scenario is the recipe card: "Given these ingredients, when you follow these steps, then the dish looks and tastes like this." Anyone — chef, reviewer, health inspector — can verify the outcome without understanding the kitchen internals.

The pain without structured stories: "The user can log in" becomes five different implementations depending on who writes the code. The mapping to Gemini: the Given/When/Then format forces specificity. Gemini won't write "the user sees success" — it writes "the user is redirected to /dashboard and sees 'Welcome, Sam.'"

Technical Definition — Gherkin

GherkinA plain-English DSL (domain-specific language) used by Cucumber and similar BDD frameworks. It structures test scenarios as Feature/Scenario/Given/When/Then blocks that both humans and automated testing tools can read. The .feature file format is the standard output. is the BDDBehavior-Driven Development — a software development approach where system behavior is described in terms of business outcomes before implementation begins. BDD bridges the gap between technical and non-technical stakeholders. scenario language. A Feature is a product capability. A Scenario describes one specific path through it. Given sets preconditions, When describes the action, and Then asserts the outcome. Gherkin scenarios can be executed directly by Cucumber, Playwright, or Behave — making them both documentation and executable tests.

Generating Gherkin Scenarios

Gemini CLI prompt
gemini "@docs/prd.md Generate 8 Gherkin user stories for the top functional requirements. Use Feature/Scenario/Given/When/Then format. Include: happy path, error case, and edge case for each major feature. Format as .feature file syntax."

User stories describe behavior. Acceptance criteria make that behavior verifiable — here's how Gemini generates criteria that QA engineers can actually use.

Acceptance Criteria — QA-Verifiable Conditions

Technical Definition — Acceptance Criteria

Acceptance criteriaA set of conditions that a feature must satisfy before it can be considered complete. Unlike user stories (which describe intent), acceptance criteria are binary: each one is either satisfied or not. They form the definition of "done" for a ticket. are the explicit, binary conditions that define "done" for a feature. Good criteria are testable (a human or script can verify them without ambiguity), complete (cover the happy path, error paths, and edge cases), and scoped (they describe observable system behavior, not implementation details).

Generating Criteria That Feed Test Generation

The key insight: if you phrase acceptance criteria the right way now, you can paste the output directly into a later "generate unit tests" prompt. The format matters.

Gemini CLI prompt
gemini "@docs/user-stories.feature For each scenario, generate acceptance criteria using this format:
- AC-[feature]-[number]: [observable condition]
Focus on: UI state changes, API response codes, data persistence, notification delivery, and error messages.
Output as a markdown checklist. Mark which criteria are automatable vs require manual QA."
WHAT: The numbered AC-prefix (e.g., AC-STATUS-01) makes criteria referenceable across PRD, tickets, and test files.
WHY: "Automatable vs manual QA" tagging saves sprint planning time — your QA lead instantly knows the test pyramid shape before a ticket is opened.
GOTCHA: Watch for criteria like "the system should be fast." Push Gemini: "Replace any criterion containing 'should be fast', 'user-friendly', or 'secure' with a measurable alternative."
✅

Checkpoint — Criteria Quality Test

For each acceptance criterion, ask: "Can a junior QA engineer verify this in under 5 minutes with no additional context?" If the answer is no, ask Gemini: "Rewrite AC-STATUS-01 to be more specific and testable."

Why It Matters

Teams that write acceptance criteria before code cut their QA feedback cycles by ~40% (Atlassian research, 2024). The reason: defects are caught at spec time rather than test time. With Gemini generating criteria from your own PRD, this discipline becomes a 2-minute step instead of a 2-hour meeting.

You have requirements. Now let's stress-test them — because Gemini's most valuable skill isn't generating ideas, it's poking holes in yours.

Gemini as Critic — Challenging Your Assumptions

Requirements written by the person who had the idea have a structural flaw: they reflect what the author already believes. Gemini can play a role no team member wants to play — the skeptic who asks the uncomfortable questions before it's too late to change course.

Devil's Advocate — Top 5 Risks

Gemini CLI prompt
gemini "@docs/prd.md Play devil's advocate. What are the 5 biggest risks to this product succeeding? For each risk: describe the failure mode, estimate the probability (high/medium/low), suggest a mitigation. Be specific — reference actual sections of the PRD."
Gemini Devil's Advocate — Output
1.
Notification fatigue kills adoption. Your PRD (§3) targets 70% WAU at 60 days, but the Slack integration in §4 FR-07 sends per-task notifications. Teams with 10+ active tasks will receive 50+ pings/day. Probability: HIGH. Mitigation: Add a "digest mode" toggle to FR-07, batch notifications to 2/day max.
2.
No mobile client blocks IC adoption. §5 NFR-02 says "available on mobile" but §6 Out of Scope lists "native mobile app." Responsive web on mobile is not the same UX. If devs can't update status from their phone during a meeting, they won't do it. Probability: MEDIUM. Mitigation: Clarify "mobile" — define minimum PWA requirements.
3.
GitHub/Linear overlap creates adoption resistance. The PRD doesn't mention integration with existing task systems. Teams already using Linear will see this as a duplicate. Probability: HIGH. Mitigation: Add explicit "import from Linear/Jira" as a Day 1 requirement, not a v2 feature.
4.
Real-time requirements are underspecified. "Sub-200ms response time" (NFR-01) is achievable, but the digest page requires aggregation across all team members. At 15 team members × 20 tasks = 300 records per render. No caching strategy is defined. Probability: MEDIUM. Mitigation: Add explicit caching requirements to NFR section.
5.
Single-user onboarding breaks team adoption. §2 assumes the Dev Lead drives onboarding, but if even one IC doesn't update, the digest is useless for everyone. There's no social accountability mechanic defined. Probability: HIGH. Mitigation: Add "last updated" staleness badges and team completion % as a core FR.

What Just Happened?

Gemini cross-referenced specific PRD sections (§4 FR-07, §5 NFR-01), identified internal contradictions between requirements and "Out of Scope" decisions, and flagged adoption risks that aren't visible from inside the idea. Each finding includes a section reference — making it actionable, not just critical.

MVP vs v2 Prioritization

Gemini CLI prompt — after critic review
gemini "@docs/prd.md Given the risks identified, reprioritize the functional requirements into: MVP (must-ship to validate core hypothesis), v1.1 (adds within 60 days if MVP succeeds), v2 (nice-to-have). Limit MVP to what a 2-engineer team can ship in 6 weeks. Output a markdown table with columns: Feature | Priority | Rationale | Risk if cut."
Warning — Scope Creep in the Prompt

Without the "2-engineer, 6-week" constraint, Gemini will rationalize everything as MVP. Be explicit about your constraints. The tighter the constraint, the more ruthless — and useful — the prioritization.

Tech Stack Decisions

Tech stack decisions made in week one shape the project for years. The cost of a wrong choice isn't just refactoring — it's the hiring pipeline, the ops tooling, and the mental model every new team member needs. Use Gemini to make this decision deliberately, not by habit.

Gemini CLI prompt (uses web search)
gemini --web "@docs/prd.md Suggest a production-grade tech stack for this product. Constraints: 2-engineer team, 6-month timeline, target 10,000 DAU at launch, deploy on a single cloud provider. Generate a comparison table of 2–3 options per layer (frontend, backend, database, realtime, auth, hosting). Columns: Layer | Option | Pros | Cons | Recommended. Explain the winning recommendation in 3 sentences."
WHAT: The --web flag enables Gemini's web search, so it checks current library versions, recent community sentiment, and 2024–2025 production usage data.
WHY: Stack decisions made from static training data miss ecosystem shifts. React Server Components, Bun, Drizzle ORM — these changed the calculus in the last 18 months.

Gotcha — The "Recommended" Column

Gemini's recommendation reflects the constraints you gave it. Change the constraint ("self-hosted only," "no vendor lock-in," "must run on existing AWS account") and the recommendation changes. Always regenerate the table when constraints change. Save each version to docs/tech-stack-v1.md, v2.md, etc.

ADR Template with Gemini

An ADRArchitecture Decision Record — a short document that captures an important architectural decision, the context that led to it, the options considered, and the consequences. ADRs are immutable — you never edit an old one; you write a new ADR that supersedes it. (Architecture Decision Record) documents every non-obvious technology choice. Generate one now for your database selection:

New-Item -ItemType Directory -Force docs/adr | Out-Null
gemini "@docs/tech-stack.md Write an ADR for the database selection. Use this format: Title, Status (Proposed/Accepted/Deprecated), Context (why this decision was needed), Decision (what was chosen and why), Consequences (positive and negative), Alternatives Considered. Be specific about trade-offs." | Out-File docs/adr/ADR-001-database.md -Encoding utf8
