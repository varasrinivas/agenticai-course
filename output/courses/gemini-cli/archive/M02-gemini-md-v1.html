GEMINI.md & Settings
Persistent Context for Every Session

Write your project context once and have Gemini read it automatically at the start of every session — no more repeating your stack, conventions, or preferences.

GEMINI.md Model Selection Settings Hierarchy Token Caching

What Is GEMINI.mdA Markdown file that Gemini CLI reads automatically at the start of every session. It acts as persistent context, telling the model about your project's tech stack, coding conventions, and preferences — without you having to re-explain each time.?

The contractor briefing document you leave on the desk every morning — except you only write it once.

Here is the problem it solves. You open a new Gemini CLI session to work on your TypeScript API. You ask for help with an error handler. The model returns a perfectly valid answer — but it uses any types, throws exceptions from route handlers, and names the file with camelCase instead of kebab-case. Every answer is generic because the model has no idea what your project looks like.

The BEFORE / PAIN / MAPPING:
BEFORE GEMINI.md exists: you paste "we use TypeScript strict mode, Zod for validation, kebab-case filenames..." into the chat at the start of every session — and still forget things.
PAIN: The model gives you correct-in-isolation code that breaks conventions, uses patterns you've banned, and ignores your folder structure. You spend more time editing than prompting.
MAPPING: GEMINI.md is loaded by Gemini CLI automatically before your first message, filling the context window with your project knowledge. The model reads it the same way a new teammate reads an onboarding doc on their first day.

Two Scopes: Project vs. Global

GEMINI.md works at two levels, and both are loaded together at session start:

Project-Level
./GEMINI.md

Loaded only when you run gemini inside this directory. Put project-specific conventions, file structure, and banned patterns here.

Global
~/.gemini/GEMINI.md

Loaded in every session, regardless of directory. Put your personal preferences, language choice, and general coding habits here.

Load order matters: The global ~/.gemini/GEMINI.md is injected first, then the project-level file. If both define a "model" preference, the project setting wins. You'll see why this matters in the Settings Hierarchy section.

Anatomy of a GEMINI.md File

A well-structured file does one thing per section, uses H2 headings to separate concerns, and states what NOT to do as clearly as what to do.

Below is a complete, annotated example for a TypeScript/Node.js API project. Read the annotations after each chunk — they explain what the section does, why it's written that way, and common mistakes to avoid.

# Project: Order Management API

## Tech Stack
- Runtime: Node.js 20 (TypeScript 5.x)
- Framework: Express 4 + Zod for validation
- Database: PostgreSQL via Prisma ORM
- Testing: Vitest + Supertest

## Coding Conventions
- All functions must have JSDoc comments
- Use `const` over `let` unless mutation is required
- Error handling: always return `{ error: string }` on failure, never throw from route handlers
- File naming: kebab-case for files, PascalCase for classes

## What NOT to do
- Never use `any` TypeScript type — use `unknown` and narrow it
- Never commit `.env` files
- Don't add console.log in production paths — use the `logger` utility

## Project Structure
src/
  routes/      # Express route handlers
  services/    # Business logic (no Express imports)
  models/      # Prisma schema types
  utils/       # Shared utilities

## Commands
- `npm run dev`     — start with hot reload
- `npm test`        — run all tests
- `npm run db:migrate` — run Prisma migrations

WHAT — Tech Stack section List exact versions, not just names. "Node.js" tells the model nothing. "Node.js 20 (TypeScript 5.x)" tells it to avoid deprecated APIs, use modern fetch, and write .ts files with strict types. Include the ORM (Prisma vs. TypeORM vs. Drizzle) because each has completely different query patterns.
WHAT — Coding Conventions section This is where context pays for itself. Specifying "return { error: string } on failure, never throw from route handlers" prevents an entire class of suggestions that would cause a generic Express error handler to swallow your custom errors. State the rule AND the reason in one sentence.
WHAT — What NOT to Do section Negative constraints are the highest-ROI lines in your file. Models are trained on millions of code examples where any is used freely. Without an explicit ban, the model will happily emit it. Write prohibitions in the imperative: "Never X" beats "prefer not to X."
GOTCHA: Don't put security-sensitive information (secrets, internal hostnames, private data) in GEMINI.md — it's a plain text file that will be included in every API request payload. Think of it as code, not config.
WHAT — Commands section Listing the exact dev/test/migration commands means you can ask "run the tests" and Gemini will use npm test rather than guessing or suggesting a different test runner. It also prevents the model from suggesting commands your project doesn't have.

Model Selection & Routing

Three ways to set the model, each with a different scope. Pick the right level and avoid surprises when switching projects.

Why model choice matters here: GEMINI.md lets you set a project-level model default, which means different projects on your machine can use different models automatically. Your lightweight documentation project uses Flash for speed; your complex reasoning project uses Pro — and you never have to remember to switch.

Method 1 — Command Flag (one-off override)

# Overrides any GEMINI.md or settings.json for this one session only
gemini --model gemini-2.5-pro

# Use Flash for quick iteration tasks
gemini --model gemini-2.5-flash "summarize this PR description"
# Overrides any GEMINI.md or settings.json for this one session only
gemini --model gemini-2.5-pro

# Use Flash for quick iteration tasks
gemini --model gemini-2.5-flash "summarize this PR description"

Method 2 — GEMINI.md (project-level default)

## Model
model: gemini-2.5-pro

# This project always uses Pro because it involves
# multi-file refactoring and complex architecture decisions

Method 3 — Environment Variable (persists across all sessions)

# Set for current session only (lost when terminal closes)
$env:GEMINI_MODEL = "gemini-2.5-pro"

# Persist permanently for your Windows user account
[System.Environment]::SetEnvironmentVariable(
  "GEMINI_MODEL",
  "gemini-2.5-pro",
  "User"   # "Machine" requires admin rights
)

# Verify the change
[System.Environment]::GetEnvironmentVariable("GEMINI_MODEL", "User")
# Output: gemini-2.5-pro
# Set for current session only
export GEMINI_MODEL="gemini-2.5-pro"

# Persist permanently (add to your shell profile)
echo 'export GEMINI_MODEL="gemini-2.5-pro"' >> ~/.zshrc
source ~/.zshrc

# Verify
echo $GEMINI_MODEL
# gemini-2.5-pro

Plan Mode Routing

When you use /plan mode (activated with /plan in the chat), Gemini CLI applies smart routingPlan Mode uses a more capable model for the planning step (forming a step-by-step approach) and a faster model for execution (implementing each step). This gets you Pro-quality planning at near-Flash execution speed and cost.: it uses the Pro model for the planning step (forming a multi-step approach) and Flash for the execution steps (implementing each step in sequence). You get Pro-quality planning without paying Pro prices for every token.

Rule of thumb: Start with gemini-2.5-flash for day-to-day work. Switch your project's GEMINI.md to gemini-2.5-pro when you're doing large refactors, designing new systems, or hitting reasoning limits. Use /plan mode for multi-file changes regardless of model — the routing is automatic.

The settings.json File

Both the global and project-level settings files use the same JSON structure. Here is a complete example with annotations:

{
  "model": "gemini-2.5-flash",
  "theme": "dark",
  "autoApprove": [
    "git status",
    "git diff",
    "npm test"
  ],
  "tools": {
    "allowShell":     true,
    "allowFileWrite": true,
    "allowWebSearch": true
  }
}
# Global settings (applies to all sessions)
%USERPROFILE%\.gemini\settings.json
# e.g. C:\Users\vara\.gemini\settings.json

# Project settings (applies when running in this directory)
.\gemini-settings.json
# e.g. D:\work\my-api\gemini-settings.json

# Create global settings file via PowerShell
New-Item -Path "$HOME\.gemini" -ItemType Directory -Force
New-Item -Path "$HOME\.gemini\settings.json" -ItemType File
# Global settings (applies to all sessions)
~/.gemini/settings.json

# Project settings (applies when running in this directory)
./gemini-settings.json

# Create global settings file
mkdir -p ~/.gemini
touch ~/.gemini/settings.json
WHAT — model Sets the default model for this scope. Overridden by GEMINI.md model: field if both exist at the same scope level. Overridden by CLI --model flag or GEMINI_MODEL env var at runtime.
WHAT — autoApprove A list of shell commands that Gemini CLI will run without asking for your confirmation. Keep this list short and limited to read-only or reversible commands. git status is safe; rm -rf is not.
GOTCHA: autoApprove in the project gemini-settings.json overrides the global list entirely — it does not merge. If your global file approves npm test and your project file only lists git diff, the project scope will require approval for npm test.
WHAT — tools Toggles what Gemini CLI is allowed to do on your machine for this scope. Setting allowFileWrite: false in a project scope prevents the model from writing files in that directory — useful for read-only audit or documentation sessions.
✓ What Just Happened?
You now have a mental model of the four-level hierarchy. When a setting "isn't working," check this order from top to bottom: Is a CLI flag or env var overriding it? Is a project-level file conflicting with your global file? Is there an enterprise policy in place? The answer is almost always at a higher priority level than where you made the change.

Token Caching

GEMINI.md is resent with every request. Google's API automatically caches identical prefixes — so stable instructions in your GEMINI.md are free after the first call.

Every request to the Gemini API includes your GEMINI.md content as part of the context. On a busy day you might make hundreds of requests — resending a 2,000-token file each time would add up fast. This is where token cachingGoogle's API stores a hash of the "prefix" portion of your request (system prompt + GEMINI.md). If the next request sends an identical prefix, the API returns a cached version instead of processing the tokens again — reducing cost and latency. helps.

Rules for a Cache Hit

≡
Identical Content
GEMINI.md must be byte-for-byte identical between requests. One character edit busts the cache.
≥
Minimum Size
~1,024 tokens minimum before caching activates. A 10-line file won't trigger it.
5m
TTLTime To Live — how long a cached entry remains valid. After 5 minutes of no requests, the cache entry expires and the next request pays full price to re-warm the cache.
Cache entry expires 5 minutes after last use. Stays warm for active sessions.

What Goes Where: Stable vs. Dynamic Context

The golden rule: Put stable instructions in GEMINI.md (cached). Put dynamic context in your prompt (not cached). A file path, a function name, or the contents of a specific file should always go in the prompt — not in GEMINI.md — because they change per-request and would bust the cache every time.

Savings Calculator

Example savings: 1,000 requests per day × 2,000-token GEMINI.md = 2,000,000 tokens/day in potential cache savings. At Flash pricing ($0.075/1M tokens), that is $0.15/day saved — roughly $55/year from GEMINI.md caching alone on Flash. On Pro ($1.25/1M), the same usage saves $2.50/day ($912/year). Keep your GEMINI.md stable between editing sessions.

Global vs. Project Memory: What Goes Where

Global GEMINI.md is for who you are as a developer. Project GEMINI.md is for the project you are currently working on. Conflating the two makes both less useful.

Global GEMINI.md — Your Developer Identity

# Personal Preferences

- Always give PowerShell commands for Windows
- I prefer concise explanations — skip obvious parts
- When writing tests, use the Arrange-Act-Assert pattern
- Always add error handling to generated code
- When in doubt about a pattern, ask before implementing

## Communication Style
- If the task is ambiguous, ask one clarifying question before writing code
- Flag security risks with a ⚠ prefix
- Add a brief "why this approach" comment above non-obvious decisions

## My Stack Defaults
# These apply unless the project GEMINI.md overrides them
- Default language: TypeScript
- Default runtime: Node.js 20
- Default test runner: Vitest
# Open global GEMINI.md in VS Code
code "$HOME\.gemini\GEMINI.md"

# Create directory and file if they don't exist
New-Item -Path "$HOME\.gemini" -ItemType Directory -Force
New-Item -Path "$HOME\.gemini\GEMINI.md" -ItemType File -Force
# Open global GEMINI.md in VS Code
code ~/.gemini/GEMINI.md

# Create directory and file if they don't exist
mkdir -p ~/.gemini
touch ~/.gemini/GEMINI.md

Project GEMINI.md — Your Project's Context

What belongs in project GEMINI.md: tech stack specifics · coding conventions for this codebase · exact commands (dev server, test runner, migration) · file/folder structure · banned patterns · domain vocabulary (e.g., what "order", "fulfillment", "SLA" mean in this codebase).

What does NOT belong here: personal communication preferences (those go in global) · secrets or tokens · auto-generated content that changes frequently · anything you'd be comfortable committing to a public repository (because that is exactly where this file should live).

Merge Behavior

Both files are loaded and concatenated — global first, project second. If both files define a model: or ## Coding Conventions section, the model does not "merge" them. It sees both, and the project-level instruction typically wins for that specific topic because it appears later in the context window (recency bias in transformers favors later context).

Best practice: Do not repeat information across both files. If your global file says "use TypeScript," your project file does not need to repeat it unless this project overrides it (e.g., "this project uses Python, not TypeScript"). Duplication wastes tokens and creates inconsistencies when you update one but forget the other.

# Project: [Your Project Name]

## Tech Stack

- Never commit `.env` files or hardcode credentials
- Don't use `console.log` in production paths — use the `logger` utility

## Project Structure
src/

  utils/       # Shared utilities: logger, error helpers, date utils

  unit/        # Vitest unit tests (services and utils)

Python Data Science / ML Project ▼
GEMINI.md 
# Project: [Your Project Name]

## Tech Stack
- Language: Python 3.11
- ML Framework: PyTorch 2.x
- Data: pandas 2.x, polars for large datasets
- Experimentation: MLflow for run tracking
- Testing: pytest + pytest-cov
- Linting: ruff + black

## Coding Conventions
- Type hints on all function signatures (PEP 484)
- Docstrings in Google style: Args, Returns, Raises sections
- All data transformations must be reproducible (set random seeds)
- Use `pathlib.Path` for file paths — never `os.path`
- Configuration via Pydantic Settings (`pydantic-settings`), not raw `os.environ`

## What NOT to Do
- Never load entire datasets into memory without sampling checks first
- Don't use mutable default arguments in functions (Python anti-pattern)
- Don't use wildcard imports (`from module import *`)
- Avoid `pickle` for model serialization — use `safetensors` or `joblib`

## Project Structure
src/
  data/        # Data loading, preprocessing, feature engineering
  models/      # Model definitions and training loops
  evaluation/  # Metrics, plots, result analysis
  utils/       # Config, logging, seed helpers
notebooks/     # Exploration only — no production code here
tests/         # pytest tests for data and model utilities
artifacts/     # .gitignored — saved models, experiment outputs

## Commands
- `python -m pytest`              — run tests
- `python src/train.py`           — train model with default config
- `mlflow ui`                     — view experiment runs
- `ruff check . --fix`            — lint and auto-fix

## Data Notes
- Raw data lives in `data/raw/` — never modify these files directly
- Processed data in `data/processed/` — always regenerable from raw
Full-Stack React + FastAPI Project ▼
GEMINI.md 
# Project: [Your Project Name]

## Architecture
- Frontend: React 18 + TypeScript, Vite, Tailwind CSS, React Query v5
- Backend: FastAPI (Python 3.11), SQLModel for ORM, Alembic for migrations
- Database: PostgreSQL
- Auth: JWT (backend) + Zustand for client state
- Testing: Vitest + Testing Library (FE), pytest (BE)

## Frontend Conventions
- Component files: PascalCase (`UserCard.tsx`)
- Hooks: camelCase prefixed with `use` (`useOrderStatus.ts`)
- All API calls go through React Query hooks — no raw `fetch` in components
- Keep components under 150 lines — extract to hooks or sub-components if larger
- Never store sensitive data in `localStorage`

## Backend Conventions
- Route files: one file per resource domain (`routes/orders.py`)
- Service layer: all business logic in `services/` — routes only handle HTTP
- Always use Pydantic models for request/response schemas
- Async all the way: use `async def` for all route handlers

## What NOT to Do
- Don't put business logic in React components — use custom hooks or the service layer
- Never use `any` in TypeScript
- Don't bypass the service layer in routes (no direct DB calls in route handlers)
- Avoid mixing `sync` and `async` database calls in FastAPI

## Project Structure
frontend/src/
  components/   # Reusable UI components
  pages/        # Route-level page components
  hooks/        # Custom React hooks (API calls, state)
  store/        # Zustand stores
  types/        # Shared TypeScript types
backend/
  routes/       # FastAPI routers
  services/     # Business logic
  models/       # SQLModel table definitions
  schemas/      # Pydantic request/response models

## Commands
# Frontend
- `npm run dev`       — Vite dev server (localhost:5173)
- `npm test`          — Vitest
# Backend
- `uvicorn main:app --reload`   — FastAPI dev server (localhost:8000)
- `pytest`                      — run backend tests
