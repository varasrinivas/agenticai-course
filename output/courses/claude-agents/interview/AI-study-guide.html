M01

LLM Mental Model

Track 1: Foundations
Core Analogy — The World's Most Well-Read Autocomplete

Your phone's autocomplete only read your messages. Claude read billions of books, papers, and conversations. It still just predicts the next token — but from patterns rich enough to handle any task.

Token Generation Loop (inside the model)

Token Generation Loop pseudocode 
# INSIDE Claude: one token at a time
WHILE not done:
    probs = model.predict_next(tokens)      # vocab-wide probability distribution
    next  = SAMPLE(probs, temp, top_p, top_k)
    tokens.append(next)
    done  = (next == STOP) OR reached max_tokens

# Reading (prefill) is PARALLEL — all input tokens at once.
# Generation (decode) is SEQUENTIAL — one token per forward pass.

Two Phases of Inference

PhaseWhat happensSpeed driverOptimization
PrefillAll input tokens processed in parallel, KV cache builtPrompt length (O(N²) but parallel)Prompt caching — collapses TTFT on repeat prompts
DecodeOne token per pass, reads KV cacheOutput length (O(1) per token)Cap max_tokens; shorter answers = faster

Temperature, Top-p, Top-k

SettingEffectWhen to use
temp = 0Always pick top token — predictable, auditableAgents, routing, extraction, compliance
temp 0.3–0.5Natural variation, still groundedSummarization, rewriting
temp 0.7–1.0Surprising choices, creativeBrainstorming, fiction, marketing
top-p = 0.9Trim the long tail of weird tokensUse only when temp alone misbehaves
top-k = NKeep only N most-likely tokensRarely needed for Claude
⚠ Default for agents: temperature = 0

An agent routing 5,000 emails at temp 0.8 produces 150–400 unpredictable routing decisions per day. Reproducibility, debuggability, and auditability beat surprise.

"Claude looks up facts in a database"
No lookup step. Claude generates tokens. Correct facts emerge from training patterns — which is exactly why it can produce convincing nonsense.
"Bigger model = factually accurate"
Bigger models reason better but still hallucinate — sometimes more convincingly. Scale fixes capability, not truth. That's why guardrails and tools exist.
"Streaming is faster than non-streaming"
Same total wall-clock. Streaming shows tokens as they decode. Use streaming for perceived UX; non-streaming when you need the full response first (JSON parsing).
"temperature=0 is fully deterministic"
Mostly. Server-side batching and GPU float non-determinism still produce tiny variations. Build tests to tolerate variation, don't pretend you eliminated it.
M02

Tokens

Track 1: Foundations
Analogy — Tokens are the kWh of AI

Pricing, latency, and the 200K context window all use one unit: tokens. Once you start counting, every product decision becomes arithmetic: "Sonnet at 2K input + 500 output, 50K calls/day = ~$700/day — can we trim 20%?"

Key Numbers

  • ~4 chars/token in English (not 1:1 with words or chars)
  • Emojis/CJK = 2–3 tokens each
  • 200K window = system + tools + history + message + reply
  • Output is 3–5× more expensive than input per tier
  • $0.014 × 50K calls/day = $700/day — 20% trim = $4,200/month saved

Where to Cut Tokens (in order)

  • 1st — Cap output (highest $ per token; add "answer in <200 words")
  • 2nd — Trim system prompt (sent every call; compounds fast)
  • 3rd — Manage history (summarize at 60–70%, not 95%)
  • 4th — Use RAG for large documents (retrieve only the slice)
  • 5th — Tier down (Sonnet → Haiku if quality holds)
⚠ Context Window Budget (200K Claude)

System prompt: ~1K · Tool definitions: ~2K · History: ~100K · User message: ~5K · Response reserve: ~8K · Safety cushion: ~84K. Summarize at 60–70%, never wait for 95% — summarization itself needs context room.

"Input and output tokens cost the same"
Output is 3–5× more expensive on every Claude tier. Generation is autoregressive — each token requires a full forward pass.
"Claude remembers previous conversations"
Every API call is stateless. Your app must re-send full history every turn. No history = no memory. Memory is YOUR job, not Claude's.

🔑 Context Engineering — "Lost in the Middle"

Attention is not uniform. Claude attends strongly to the beginning (system prompt) and end (latest user message) of context. Critical facts buried in the middle of a 150K-token context get less attention. Put critical instructions at start or end — never in the middle of a long history.

M05

Function Calling (Tool Use)

Track 2: Tool Use
Analogy — The Brilliant Assistant in a Windowless Room

Claude can reason brilliantly but has no clock, no internet, no database. Function calling hands it a panel of labeled buttons — get_weather(), search_filings(), predict_delinquency(). Claude pushes the button; YOUR code runs the function and slides the result back.

The 6-Step Round-Trip

  • 1
    User asks — "What's Acme's lien exposure?"
  • 2
    You send message + tools array to Claude API
  • 3
    Claude returns tool_use block: {name: "search_filings", input: {company: "Acme"}} + stop_reason: "tool_use"
  • 4
    YOUR code validates, executes the function, captures result
  • 5
    You send back tool_result tagged with matching tool_use_id
  • 6
    Claude writes final answer — stop_reason: "end_turn"
Universal Agent Loop pseudocode 
# THE UNIVERSAL AGENT LOOP — every agent is a variation of this
messages   = [user_question]
iterations = 0

WHILE iterations < MAX_ITERS:
    response = CALL Claude(tools=tool_list, messages=messages)
    messages.append({role: "assistant", content: response.content})

    IF response.stop_reason == "end_turn":
        RETURN final_text(response)               ← happy path ✓

    results = []
    FOR block IN response.content:
        IF block.type == "tool_use":
            out = RUN(block.name, block.input)
            results.append({tool_use_id: block.id, content: out})

    messages.append({role: "user", content: results})  ← BOTH sides required
    iterations += 1

RAISE "max iterations exceeded"                       ← safety rail fires
⚠ The #1 Bug: Forgetting to Append BOTH Sides

You must append the assistant response AND the tool_results before the next API call. Forget either one and the API rejects the request. Also: each tool_result's tool_use_id must exactly match the tool_use's id.

Writing Tool Descriptions That Work

ElementBad ✗Good ✓
namesearchsearch_ucc_filings
description"Search stuff""Search UCC filings by debtor name across all 50 states. Returns filing ID, collateral type, lapse date, and risk score. Use for lien exposure queries, NOT for company credit history."
param description"name""Debtor's exact legal name, e.g. 'Acme Corporation'. Try DBA variants separately."
🔑 Tool Description = The Steering Wheel

Claude doesn't pick tools by name — it reads the description semantically. Cap toolset at 4–6 per request. Selection accuracy: 97% at 3 tools → 61% at 18 tools. Beyond 6 tools, split into specialized subagents.

"Claude executes the function"
Claude returns a JSON block saying "I'd like to call this function." YOUR code runs it, decides whether to honor it, and sends back the result. Claude decides; you execute.
"Never trust stop_reason — parse Claude's text"
stop_reason is the ONLY reliable signal. "end_turn" = done. "tool_use" = run tools. Parsing natural language text for "I'm done" is fragile and breaks across model versions.

⚠ Empty Result ≠ Error — Critical Distinction

{results: []} tells Claude "I checked, nothing matched" — it stops looking. {isError: true, errorCategory: "access_denied"} tells Claude "I never even ran" — it asks for help. Conflating them causes catastrophic decisions.

Error Handling Pattern

Safe Tool Call — Error Handling Pattern pseudocode 
FUNCTION safe_tool_call(name, args):
    TRY:
        validate(args)
        result = TOOL[name](**args)
        RETURN {isError: false, data: result}

    EXCEPT ValidationError AS e:
        RETURN {isError: true, errorCategory: "bad_args",      isRetryable: true,  context: e.message}
    EXCEPT TimeoutError:
        RETURN {isError: true, errorCategory: "timeout",       isRetryable: true}
    EXCEPT AuthError:
        RETURN {isError: true, errorCategory: "access_denied", isRetryable: false}
    EXCEPT Exception AS e:
        RETURN {isError: true, errorCategory: "internal",      context: str(e)[:200]}

# Every branch RETURNS — nothing raises. Loop keeps running.
# isRetryable tells Claude whether to try again or escalate.
M07

MCP — Model Context Protocol

Track 2: Tool Use
Analogy — USB-C for AI

Before USB-C: every device had its own cable (N×M integrations). After: one plug, any device (N+M). MCP does the same for AI: write once, every compatible host benefits tomorrow.

ConceptDetails
Wire protocolJSON-RPC 2.0 over stdio (local subprocess) or HTTP+SSE (remote)
Three primitivesResources (read-only data, URI-addressed) · Tools (actions with side effects) · Prompts (reusable workflow templates)
LifecycleInitialize (handshake) → Discover (tools/list, resources/list) → Operate (tools/call, resources/read) → Shutdown
The model's roleClaude NEVER opens a socket. Host translates tool_use blocks to MCP calls, runs them, returns tool_result. Host is the bridge.
MCP vs A2AMCP = agent ↔ tool (vertical). A2A = agent ↔ agent (horizontal). Real systems use BOTH.
⚠ Safety Boundary is Non-Negotiable

MCP server runs with the OS privileges of whoever launched it. Without a path allowlist or read-only DB role, a single prompt-injected message can read ~/.ssh/id_rsa. Always validate inputs against an explicit allowlist before doing anything.

Memory, Conversation & RAG

Track 3: Memory & Context
Memory TypeWhat it isHow it works
In-context (Working)Current conversation, tool results, retrieved chunksRe-send every API call; summarize at 60–70% utilization
External (Episodic)Past conversation summaries, user facts, preferencesVector DB or key-value store; retrieve top-k by similarity
External (Procedural)How-to templates, workflows, domain rulesLoaded as part of system prompt for relevant task types
RAGPrivate documents, real-time data, domain knowledgeEmbed, store in vector DB, retrieve relevant chunks per query

RAG Pipeline

  • 1
    Ingest — chunk documents (512–1024 tokens), embed each chunk, store in vector DB
  • 2
    Query — embed the user question, find top-k most similar chunks (cosine similarity)
  • 3
    Augment — inject retrieved chunks into system prompt before Claude call
  • 4
    Generate — Claude answers grounded in retrieved context, not training hallucinations
  • 5
    Verify — check each factual claim is supported by a retrieved source (M17 hallucination check)
🔑 Hybrid Search beats Pure Vector

Combine dense retrieval (semantic similarity via embeddings) with sparse retrieval (keyword BM25). Dense wins on concept matching; sparse wins on exact terms (filing IDs, entity names). Re-rank with a cross-encoder for best results.

"Memory means the LLM remembers things between sessions"
Every API call is stateless. "Memory" means YOUR code stores history (conversation, RAG chunks) and replays it into the next prompt. The LLM is amnesic; the system around it has memory.
M12

The ReAct Loop

Track 4: Agent Architectures
ReAct = Reason → Act → Observe — The Methodical Detective

Reason: Claude writes a thought trace explaining what it knows and what to do next. Act: Claude emits a tool_use block. Observe: Your code runs the tool, sends back tool_result. Repeat until stop_reason: "end_turn".

5 Stop Conditions — Use All Five

RailWhat it catchesTypical value
Natural completion (stop_reason = "end_turn")The ONLY signal meaning "task succeeded"N/A — the happy path
Max iterationsInfinite loops, confused agents5–15 for most tasks; 25 for research
Token / cost budgetExpensive Opus loopsTrack cumulative tokens; set dollar ceiling
Error thresholdDownstream API down; retrying foreverStop after 2–3 consecutive tool failures
Wall-clock timeoutInfinite reasoning loops generating few tokens30s for UX; 2min for research tasks
ReAct Loop with 5 Stop Rails pseudocode 
FUNCTION run_agent(question):
    messages = [{role: "user", content: question}]
    iters, tokens, errors = 0, 0, 0

    WHILE True:
        # ── 5 stop rails — checked before every Claude call ──────
        IF iters   >= MAX_ITERS:       RETURN partial_result("max iterations")
        IF tokens  >= TOKEN_BUDGET:    RETURN partial_result("budget exhausted")
        IF errors  >= ERROR_THRESHOLD: RETURN partial_result("too many failures")

        response = CALL Claude(system, tools, messages)
        messages.append({role: "assistant", content: response.content})
        tokens += response.usage.total

        # ── natural completion — the ONLY success signal ─────────
        IF response.stop_reason == "end_turn":
            RETURN final_text(response)                  ← happy path ✓

        # ── tool execution ────────────────────────────────────────
        results = []
        FOR block IN response.content:
            IF block.type == "tool_use":
                TRY:   out = RUN(block.name, block.input); errors = 0
                CATCH: out = error_result();                 errors += 1
                results.append({tool_use_id: block.id, content: out})

        messages.append({role: "user", content: results})
        iters += 1
🔑 Why Thought Traces Matter

The act of generating reasoning text improves Claude's next decision — don't suppress thought traces to save tokens. They also provide audit logs for healthcare/finance use cases. In long agents, summarize old entries rather than storing the full trace forever.

"ReAct needs LangChain or CrewAI"
No. Claude's Messages API already produces ReAct: text blocks = Reason, tool_use blocks = Act, tool_result messages = Observe. You need a while loop and tool execution — that's it.
"max_iterations is the primary control"
max_iterations is a safety net, not the main termination logic. Let the agent stop naturally via stop_reason. The cap catches runaway loops; it doesn't define "done."

Intent Classification → Route to Right Strategy

Intent Classification Router pseudocode 
FUNCTION classify(user_message):
    # Use Haiku — fast, cheap, accurate for 3 labels
    result = CALL Claude(
        system = "Return JSON only: {intent, complexity, entities}",
        user   = user_message
    )
    RETURN parse_json(result)   # intents: simple_question | single_tool | multi_step

FUNCTION handle(user_message):
    c = classify(user_message)

    IF   c.intent == "simple_question": RETURN direct_answer(user_message)
    ELIF c.intent == "single_tool":    RETURN react_loop(user_message)
    ELSE:                              RETURN dag_execute(decompose(user_message))

# ~60–70% of requests are simple — skipping planning saves the most tokens.
# Route first, reason second.
⚠ Plan-Execute vs ReAct — Cert Exam Trap

Plan-Execute: commits to a plan up front — reliable when steps are known, brittle when reality differs. ReAct: discovers the plan as it goes — adapts to surprises. Choose by whether the steps can be known BEFORE any tool runs.

Subagent Pattern — Isolation is the Feature

Subagent Pattern — Isolation is the Feature pseudocode 
# Each subagent: fresh context, specialist role, small toolset, returns JSON
FUNCTION run_subagent(spec, task_string):
    # Blank slate — no shared history with coordinator or sibling agents
    ctx = [{system: spec.role, user: task_string}]

    FOR turn IN 1..spec.max_turns:
        reply = CALL Claude(ctx, tools=spec.tools)

        IF reply.stop_reason == "tool_use":
            FOR call IN reply.tool_uses:
                ctx.append(tool_result(call.id, run_tool(call.name, call.input)))
            CONTINUE

        IF reply.stop_reason == "end_turn":
            RETURN parse_json(reply.text) or {summary: reply.text}

    RETURN {error: "max turns reached"}   ← coordinator handles this

# Coordinator tools = delegation calls, not DB queries.
# Coordinator routes and synthesises; specialists search and act.
# Subagents NEVER call each other directly — always via coordinator.
M16

Input Guardrails

Track 5: Guardrails & Safety

5 Layers — Run Cheapest First

1
Rate LimitToken bucket per user. ~0.1ms. Stops scrapers and runaway loops before anything else runs.
~0.1ms · $0
2
PII Detect & RedactRegex (SSN, card, email, phone) + Luhn validation + NER for names/addresses. Replace with typed placeholders [REDACTED_SSN].
~1ms · $0
3
Injection ClassifierSeparate Claude call in a CLEAN context. Unicode NFKC normalize + base64 decode. Session risk score for multi-turn drift. Canary tokens in system prompt.
~200ms · $0.002/call
4
Schema ValidationPydantic / Zod: type check → constraint check (len, range, enum) → semantic check (start_date < end_date). Custom validator for whitespace-only strings.
~0ms · $0 (no API)
5
Allow / Deny / LogPipeline short-circuits on first hard block. Fail CLOSED on errors. Log every decision for audit.
Always: fail closed, never fail open
"System prompt 'be safe' is enough"
System-prompt rules are advisory, not enforced. A clever injection can talk Claude out of them. Real guardrails run OUTSIDE the model — programmatic checks the user input physically cannot influence.
"Regex catches all PII"
Regex catches structured PII (SSN, card, email). It misses unstructured PII like names, street addresses, medical conditions. "John Smith lives at 42 Oak Lane" needs NER or Claude-as-classifier.

Circuit Breaker — 3 States

StateBehaviorTransition
CLOSED (normal)Requests flow through. Count failures.N failures in window → OPEN

⚠ Tier Thresholds by Failure Type

429 rate limit (transient) → tolerate ~5 with backoff. 500 server error → trip after 3. Hallucination block → trip after 2 (model is drifting). Same threshold for every failure is wrong.

"HITL means the AI is unreliable"
The opposite. Even best employees need manager approval for large transactions. HITL is good system design — "this action is too important to fully automate," not "this AI doesn't work." Tier on blast radius and reversibility, not confidence score.
M18

Evaluation & Testing

Track 5: Guardrails & Safety
Why Agent Testing is Different — Vending Machine vs New Hire

A vending machine: press B7, assert Snickers drops. Pass/fail in milliseconds. A new hire: did they solve the problem? Was the approach efficient? Was the tone right? You need a multi-dimensional rubric, not assertEqual.

MetricWhat it measuresWhy it matters
Task completion rateDid the agent achieve the stated goal?Headline "did this work?" number
Tool accuracyRight tools with right parameters?Catches agents that get right answer via wrong path — expensive and brittle
Response quality (1–5)Claude-as-judge on clarity, completeness, toneThe subjective dimension binary tests can't see
EfficiencyTokens consumed, tool calls made, latency4.0 quality / 2K tokens beats 4.2 / 18K tokens for production
⚠ Always Stratify by Category — Don't Trust the Aggregate

Aggregate 4.2/5 looks fine. Per-category: Tracking 4.8, Refunds 4.5, Shipping 2.1, Accounts 4.9. The 2.1 shipping category was masked by the aggregate. Tag every case; compute per-category scores. The aggregate is the dashboard; the per-category view is the truth.

"temperature=0 makes tests deterministic"
Reduces variation but doesn't eliminate it. Different hardware, SDK versions, and API batching still produce different outputs. Build tests to tolerate variation, don't pretend you eliminated it.
"If the final answer is right, the test passes"
An agent that calls 15 tools for a 2-tool job is broken — expensive, slow, one API change from total failure. Evaluate the full TRAJECTORY (tools, params, intermediate steps), not just the final answer.

Cost Optimization — Priority Order

  • Prompt caching — collapses TTFT on repeated system prompt prefix; up to 90% reduction on cached portion
  • Model tiering — Haiku for routing/classification, Sonnet for general, Opus only for hard reasoning
  • Cap max_tokens — output is 3–5× more expensive than input; tight ceiling = biggest savings
  • Dynamic tool registry — filter tools per request; 20 tools × ~350 tokens each = 7K wasted tokens per call
  • History summarization — at 60–70% window utilization; drop stale tool results

🔑 Long-Horizon Agents — A Different Shape

One-shot agents (M12): run for seconds, answer a question, done. Long-horizon agents (Claude Code, Aider, Devin): live in a repo for minutes to hours, plan across dozens of files, run tests, fix what they broke, check work in. Buy for repository-scoped coding work. Build when the domain isn't code (data-pipeline triage, legal review, clinical charts).

CARDS

30 Interview Flash Cards

Review these before the call
Q: What is a true AI agent? (technical definition)
A program combining: (1) an LLM as reasoning engine, (2) tools to interact with the world, and (3) a loop that keeps it thinking and acting until the task is complete. The loop is the entire agent.
Q: The single question separating agents from workflows
"Who decides what happens next — your code, or Claude?" Level 3 = Claude decides at runtime which tool, which args, when to stop. Your code provides tools; Claude provides the brain.
Q: The litmus test for a true agent
Replace the LLM with hardcoded responses. If the program still works — NOT an agent. Level 3 breaks because Claude's runtime decisions can't be hardcoded. That fragility IS the proof.
Q: What are the two phases of LLM inference?
Prefill: all input tokens processed in parallel; drives TTFT; scales with prompt length. Decode: one token at a time; drives TPS; roughly constant per model. Prompt caching collapses repeated prefill.
Q: Default temperature for agents and why
temperature=0. At temp 0.8, an agent routing 5,000 emails/day produces 150–400 unpredictable routing decisions. Reproducibility, debuggability, and auditability beat surprise in agentic systems.
Q: Where to cut tokens — priority order
1) Cap max_tokens (output is 3–5× more expensive). 2) Trim system prompt (sent every call — compounds). 3) Summarize history at 60–70% utilization. 4) Use RAG instead of full docs. 5) Tier down to Haiku.
Q: The universal agent pattern (pseudocode)
messages = [question]. WHILE True: response = CALL Claude(messages, tools). IF end_turn → RETURN text. FOR each tool_use → run tool, append result. LOOP. Plus 5 stop rails (iters, tokens, errors, time, natural).
Q: The #1 tool-use bug to watch for
Forgetting to append BOTH the assistant response AND the tool_results before the next API call. Also: each tool_result's tool_use_id must exactly match the tool_use's id. Off-by-one = "agent froze."
Q: How many tools per request? Why?
Cap at 4–6. Selection accuracy: 97% at 3 tools → 61% at 18 tools. Each schema burns 200–500 input tokens. Beyond 6 tools, split into specialized subagents (M14) rather than one giant tool list.
Q: Tool description — what must it include?
WHAT it does (strong verb + concrete object). WHEN to use it vs. sibling tools. WHAT it returns (shape, size, format). Each property also needs its own description with an example value.
Q: Empty result vs error — why does it matter?
{results:[]} = "I checked, nothing matched" — Claude stops looking. {isError:true} = "I couldn't even check" — Claude asks for help. Conflating them causes catastrophic decisions.
Q: MCP vs A2A — one sentence each
MCP = agent ↔ tool (vertical, Anthropic Nov 2024): standardizes how one agent connects to its tools. A2A = agent ↔ agent (horizontal, Google → Linux Foundation 2025): standardizes cross-org agent delegation. Real systems use BOTH.
Q: The 5 stop conditions for a ReAct loop
1) Natural completion (stop_reason="end_turn") — the ONLY signal meaning success. 2) Max iterations (5–15). 3) Token/cost budget. 4) Error threshold (2–3 consecutive failures). 5) Wall-clock timeout (30s–2min).
Q: Why thought traces (Reason step) matter
The ACT of generating reasoning text improves Claude's next decision by 20–30% on multi-step tasks. Don't suppress to save tokens. Do summarize old entries in long sessions. Also provides audit log for compliance.
Q: Plan-Execute vs ReAct — when to use each
Plan-Execute: steps can be known before ANY tool runs (IKEA instructions → commit to plan → execute). ReAct: steps emerge from results (detective → new clue → pivot). Plan-Execute is brittle when reality differs from the plan.
Q: 8 agent patterns in order of complexity
P1 Single-Turn · P2 ReAct · P3 Plan-Execute · P4 Router · P5 Fan-Out · P6 Pipeline · P7 Supervisor+Workers · P8 Auto+HITL. Pattern choice can swing your API bill 10–50× in production. Start at P1.
Q: What makes a subagent different from a sub-prompt?
A subagent is a separate agent invocation: own system prompt, own small toolset, blank context window, returns structured JSON. Isolation is the feature. Subagents call back to coordinator — never directly to each other.
Q: The coordinator's 4 jobs
1) Route — decide which subagent(s) to call. 2) Brief — self-contained task string (resolve pronouns). 3) Collect — receive structured result, handle errors. 4) Synthesize — combine into one user-facing answer. Coordinator owns history; subagents don't.
Q: Input guardrails — 5 layers in order
1) Rate limit (0.1ms, $0). 2) PII detect & redact (regex + Luhn + NER). 3) Injection classifier (separate Claude call, clean context). 4) Schema validation (Pydantic/Zod, $0). 5) Allow/deny/log. Cheapest first. Fail CLOSED on errors.
Q: Why prompt injection is like SQL injection
SQL injection: data and instructions share one untrusted channel — attacker crafts data that becomes instructions. Prompt injection: same problem for LLMs. Fix: external classifier in CLEAN context. Also scan every tool result (indirect injection).
Q: Output guardrails — 3 checks, cheapest first
1) Format (local parse, $0) — valid JSON, required fields, values in range. 2) Hallucination (separate verifier + source docs, ~$0.003) — claim contradicted → block and retry. 3) Toxicity (Claude-as-judge, ~$0.005) — severity ≥ 4 → block.
Q: 3 HITL gate types and when to use each
Approval: irreversible actions (refund, delete, email sent). Modification: output needs human voice (customer email, legal doc). Escalation: policy gap, capability limit, ambiguity. Tier on blast radius and reversibility — NOT transaction volume or model confidence.
Q: Circuit breaker — 3 states and transitions
CLOSED (normal) → N failures → OPEN (all requests get fallback, cooldown 60s) → cooldown expires → HALF-OPEN (ONE probe) → success → CLOSED. Fail → OPEN with 2× backoff. Different thresholds per failure type.
Q: Why assertEqual doesn't work for agent testing
3 structural breaks: non-determinism (same prompt → different output), trajectory matters not just answer (15 tools for a 2-tool job = broken), quality is a spectrum not binary. Use rubric scoring on curated golden dataset, stratified by category.
Q: 4 evaluation metrics for agents
Task completion rate (binary/partial). Tool accuracy (right tool, right params, fuzzy match). Response quality 1–5 (Claude-as-judge per rubric). Efficiency (tokens, tool calls, latency). ALWAYS stratify by category — aggregate hides broken subcategories.
Q: RAG pipeline — 5 steps
1) Ingest (chunk 512–1024 tokens, embed, store). 2) Query (embed question, top-k cosine similarity). 3) Augment (inject chunks into system prompt). 4) Generate (Claude answers grounded in context). 5) Verify (check each claim against sources). Hybrid search (dense + sparse) beats pure vector.
Q: "Lost in the middle" — what is it?
Claude's attention is strongest at the start (system prompt) and end (latest user message) of context. Facts buried in the middle of a long history get less attention. Put critical instructions at START or END — never in the middle of a long document.
Q: Token bucket rate limiting — how does it work?
Bucket holds N tokens; each request consumes 1; refills at R/second. Burst-friendly (bucket was full = fast burst). Sustained overuse gets rejected. Implement per user, per endpoint. Use sliding window not fixed window (exploitable boundary). Back with Redis in production.
Q: Observability — print statements vs. production
Print statements vanish on restart. Production observability = structured JSON logs + distributed traces + dashboards. Use trace_id linking every API call in a session. Key: answer "why did Claude pick tool X on request Y at 3:14pm last Tuesday?"
Q: The 60-second "whole arc" talking point
"Transformers (2017) enabled understanding. GPT-3 (2020) enabled generating. ChatGPT (2022) mainstream. LLMs alone are chatbots — they respond, don't ACT. Agentic AI (2024) adds tool-use, memory, loop, 240× cost drop. I build agents combining ML models, RAG, tools, guardrails, observability. That's the full stack."
