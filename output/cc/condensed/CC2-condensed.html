CC2: Prompt Engineering for Claude Code

Five techniques to make Claude do the right thing reliably: clarity, specificity, XML structure, examples, thinking.

The Big Idea

Every line you write in Claude Code—CLAUDE.md, skill descriptions, subagent prompts, slash commands—is a prompt. Bad prompts waste tokens and erode trust; good prompts steer Claude reliably on the first try. Five core techniques (clarity, specificity, XML structure, examples, thinking triggers) apply across all surfaces. A well-written prompt can produce 50% accuracy gains without changing the model.

Analogy

Tell a contractor "make the kitchen nicer" and you'll get whatever they think nice means. Tell them "replace laminate counters with quartz, leave cabinets, repaint walls Benjamin Moore Cloud White" and you get exactly that. The same with Claude: vague prompts get different answers each time; direct, specific prompts get the same reliable answer, parsed correctly.

How It Works

  1. Be clear & direct: Use imperatives ("Find...", "Output..."). State the format up front. Eliminate ambiguity.
  2. Be specific: Specific inputs with context. Locked output format (parseable). Hard constraints (word counts, enums).
  3. Structure with XML tags: Wrap regions like <rules>, <input>, <example> and refer to them by name in instructions.
  4. Provide examples: 3 few-shot examples (typical, ambiguous, known-failure case) teach the shape of correct answers better than rules.
  5. Trigger thinking: For hard tasks, ask Claude to reason step-by-step or use extended thinking (Claude 4.x) with "think hard" phrases.

Pseudocode

// Step 1: Start with a vague prompt
"Review this code and tell me what's wrong."

// Step 2: Add clarity and specificity
"Find only security issues: SQLi, XSS, secrets, auth bypass, IDOR.
Output as bullet list.
Each bullet: filename:line — severity (critical/high/medium).
Skip style issues."

// Step 3: Add XML structure
<rules>
- Find: SQLi, XSS, secrets, auth bypass, IDOR
- Ignore: style, formatting
</rules>

<output_format>
VERDICT: clean | issues
FINDINGS:
- file:line — severity — description
</output_format>

// Step 4: Add a few-shot example
<example>
<input>
SELECT * FROM users WHERE id = $userId; // $userId from URL
</input>
<output>
VERDICT: issues
FINDINGS:
- auth.sql:1 — critical — SQLi: $userId passed unsanitized into query
</output>
</example>

// Result: Claude follows the exact shape, outputs are parseable and consistent.

Common Misconceptions

  • Myth: "Please" and "thank you" matter. Reality: Politeness adds tokens, not accuracy. Claude doesn't need butter-up; direct imperatives are clearer and shorter.
  • Myth: A better model fixes vague prompts. Reality: Clarity and specificity produce 50%+ accuracy gains—often cheaper and faster than upgrading.
  • Myth: All examples should go in CLAUDE.md. Reality: Examples are token-heavy. Put them in skill bodies (loaded on invocation) not CLAUDE.md (loaded every turn).

Key Takeaway

Prompt engineering is not philosophy—it's a set of five learnable techniques: be clear and direct, be specific (inputs, format, constraints), use XML tags, provide 3 examples for classification tasks, and trigger thinking for hard problems. Apply them to every surface: CLAUDE.md (tight rules), skill bodies (structured + examples), subagent prompts (role + format + thinking), and slash commands (locked output). Bad prompts look like Claude is ignoring your rules; usually the rule was too vague to parse.

Quick Quiz

Q1. Your CLAUDE.md says "review code carefully." Reviews come back inconsistent. Best fix?

A) Switch to Opus.
B) Replace "carefully" with specific categories: "Look for SQLi, XSS, secrets. Output bullet list."
C) Add "please be thorough" three times.
D) Lower temperature.

Answer: B — "Carefully" is unmeasurable. Specific categories + locked output format make Claude consistent. Vagueness is the bottleneck, not the model.

Q2. You want a skill body to apply rules to input. Best structure?

A) Plain prose: "Apply the following rules to the data..."
B) XML tags: <rules>...</rules> and <input>...</input> with instruction "Apply <rules> to <input>."
C) JSON: {rules: [...], input: ...}
D) Markdown headers: # Rules / # Input

Answer: B — Claude is specifically trained to respect XML tag structure. You can refer to sections by name in instructions, improving instruction-following measurably.

Q3. Your subagent does classification with 0 examples and a vague description. Best first improvement?

A) Add 20 examples.
B) Add 3 examples covering typical, ambiguous, and a known-failure case.
C) Add a "please be accurate" sentence.
D) Switch model from Haiku to Opus.

Answer: B — Three is the sweet spot for few-shot learning. More than 5 hits diminishing returns and inflates token cost. Pick examples covering edge cases, not volume.
