CC7 — Automation

CC7: Hooks

Programmatic control over tool calls. Auto-format, block, route policy, inject context.

The Big Idea

Hooks are thin layers that intercept Claude's tool calls before and after they run. Instead of Claude executing a Bash command directly, your hook runs first, checks policy, logs the call, formats output, or blocks it entirely. Think of them as middleware for agent behavior: same Claude, same tools, but with guardrails and automation you control. The 9 hook events (SessionStart, SessionEnd, UserPromptSubmit, PreToolUse, PostToolUse, Stop, SubagentStop, PreCompact, Notification) let you enforce policy across the entire lifecycle. Configuration lives in .claude/settings.json.

Analogy

Every hotel room has card readers instead of traditional locks. Why? Because the front desk revokes access without fishing for keys, logs every entry centrally, and updates rights when guests extend their stay—all without changing the door itself. Hooks in Claude Code are exactly this: a thin layer around tool calls that runs your code first. Claude doesn't know it's there; you control whether the call proceeds, what gets logged, or whether the output is reformatted.

How It Works

  1. Event fires: Claude is about to use Bash (PreToolUse) or just finished an Edit (PostToolUse).
  2. Hook runs: Your command, HTTP endpoint, or LLM prompt executes with the tool call JSON on stdin.
  3. Decision returned: Hook exits 0 (allow), 2 (block), or returns JSON with permissionDecision: "allow" | "deny" | "ask" | "defer".
  4. Claude acts: If blocked, Claude sees the rejection and tries something else. If allowed, the tool runs. If deferred, the session parks until a slow decision lands.
  5. Output handled: After tool completion, PostToolUse hooks can lint, format, or inject system reminders back to Claude.

Pseudocode

Configuration in .claude/settings.json {
  hooks: {
    PreToolUse: [          // event: before tool runs
      {
        matcher: "Bash",   // only Bash tool calls
        hooks: [
          {
            type: "command",           // run shell script
            command: "check-dangerous-flags.sh"
          }
        ]
      }
    ],
    PostToolUse: [         // event: after tool runs
      {
        matcher: "Edit|Write",
        hooks: [
          {
            type: "http",              // POST to policy server
            url: "https://policy.internal/lint",
            async: true                // fire and forget
          }
        ]
      }
    ]
  }
}

Hook script (check-dangerous-flags.sh) reads stdin:
  tool_name = "Bash"
  tool_input.command = "rm -rf /"
  hook_event_name = "PreToolUse"

  If tool_input.command contains "rm -rf":
    exit 2                          // block signal
    print to stderr: "Dangerous"
  Else:
    exit 0                          // allow
    optionally return JSON with changes to tool_input

Common Misconceptions

  • Myth: "Hooks run instead of the tool." Reality: PreToolUse runs before the tool; PostToolUse runs after. Only PreToolUse can block. PostToolUse's exit 2 is feedback to Claude, not a block.
  • Myth: "I need a different hook script for each developer." Reality: Use type: "http" to centralize policy at one endpoint. One server, one audit log, one source of truth. Update policy once; it applies to everyone.
  • Myth: "Hooks are for permissions only." Reality: Hooks automate formatting (prettier post-Edit), run tests (post-Write), inject context (prompt classification), and manage approval workflows (permissionDecision: "defer" for Slack approvals).

Key Takeaway

Hooks let you automate and govern Claude's tool calls without touching the tools themselves. Start with a simple PostToolUse hook to auto-format files, then graduate to HTTP-based centralized policy for orgs. Five handler types (command, http, mcp_tool, prompt, agent) give you options from cheap-and-fast to deep-and-semantic. Remember: exit 2 to block on PreToolUse; exit 0 or JSON to communicate on PostToolUse.

Quick Quiz

Q1. You want to auto-format every file Claude edits. Which hook event?

A) PreToolUse with matcher: Edit|Write
B) PostToolUse with matcher: Edit|Write
C) SessionEnd
D) UserPromptSubmit

Answer: B — PostToolUse fires after the edit completes, perfect for formatting. PreToolUse fires before the file exists in its new state.

Q2. You want to block any Bash call containing rm -rf. What exit code?

A) exit 1 — standard error
B) exit 2 — with stderr explaining why
C) exit 0 with empty output
D) exit 127 — command not found

Answer: B — Exit 2 is the special blocking signal. On blockable events (like PreToolUse), Claude Code respects it and feeds stderr back to the model so it knows why and can retry.

Q3. Your team needs one audit log, one policy server, shared enforcement. Which handler type?

A) command — shell script per dev
B) http — POST to a central policy endpoint
C) prompt — ask Haiku each time
D) agent — subagent for each call

Answer: B — HTTP hooks centralize policy in one server with one audit trail. Command means N copies on N machines. Don't forget allowedHttpHookUrls and httpHookAllowedEnvVars in settings.
