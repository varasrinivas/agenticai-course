CC4: Permissions & Sandbox

Two independent safety layers: ask for permission, enforce boundaries with OS-level jail.

The Big Idea

Claude Code has two independent safety mechanisms stacked on top of each other. Permission modes are advisory—they tell Claude to ask you before executing certain tools or commands. The sandbox is OS-enforced—it's an operating-system-level jail that prevents any process from reading or writing outside the paths you allow, regardless of what Claude or bash tries to do. Together, they create defense in depth: permission modes handle day-to-day UX (you control when you're prompted), and the sandbox catches mistakes the permission layer misses.

Analogy

A research lab uses two layers: posted procedures ("wear gloves, work in the fume hood") and physical engineering (the fume hood actually exists, the gas valve is locked). The procedure is advisory; the engineering is mandatory. If you only have the procedure, a careless person ignores it. If you only have the engineering, every routine task feels locked down. You need both, with engineering catching what procedure misses.

How It Works

  1. You define permission modes (plan, default, acceptEdits, bypassPermissions) per session, controlling whether Claude prompts you before running bash, editing files, or fetching URLs.
  2. You define permission rules (allow, ask, deny) in settings.json to pre-approve specific commands (Bash(npm test:*)), force prompts for others (Bash(git push:*)), or block them entirely (Bash(rm:*)).
  3. You optionally enable the sandbox, an OS-level jail that whitelists filesystem paths Claude can write to and network domains it can reach. Even if Claude misbehaves, the OS enforces the boundary.
  4. Rules are layered: user-level settings apply globally, project-level settings override them for one repo, and sandbox is independent and can work alone or in combination with either.
  5. Precedence is deny > ask > allow: if a command matches a deny rule, it's blocked; if it matches ask, you're prompted; if only allow, it runs without prompting.

Pseudocode

// Settings.json structure
{
  "permissions": {
    "defaultMode": "default",      // plan | default | acceptEdits | bypassPermissions
    "allow": [
      "Bash(npm test:*)",           // Auto-run test commands
      "Bash(git diff:*)",           // Auto-run git diffs
      "Read(./**)"                  // Auto-read files in project
    ],
    "ask": [
      "Bash(git push:*)",           // Prompt before pushing
      "Edit(package.json)"          // Prompt before editing package.json
    ],
    "deny": [
      "Bash(rm:*)",                 // Block rm commands entirely
      "Read(~/.ssh/**)",            // Block reading SSH keys
      "Read(./.env)"                // Block reading .env file
    ]
  },
  "sandbox": {
    "enabled": true,
    "filesystem": {
      "allowWrite": ["./", "~/.cache/claude"],   // Only write here
      "denyRead": ["./.env", "~/.ssh", "~/.aws"] // Never read these
    },
    "network": {
      "allowedDomains": ["api.github.com", "registry.npmjs.org"],
      "deniedDomains": ["*"]  // Default-deny, then whitelist
    }
  }
}

Common Misconceptions

  • Myth: I should use bypassPermissions on my dev machine for speed. Reality: Never. One hallucination or typo runs rm -rf with no prompt. Use bypassPermissions only in disposable containers (Docker, GitHub Actions, throw-away VMs) where the blast radius is bounded by the container itself.
  • Myth: Permission modes and sandbox do the same thing. Reality: Permissions are advisory (Claude cooperates); sandbox is OS-enforced (the operating system blocks the action). Permissions handle UX; sandbox handles security. Use both for defense in depth.
  • Myth: If I allow a broad tool like Bash, deny rules won't help. Reality: Deny beats allow. "allow": ["Bash"] paired with "deny": ["Bash(rm:*)"] blocks rm even though Bash is allowed. Pair broad allows with narrow denies.

Key Takeaway

Permission modes and sandbox are independent safety layers. Use permission modes to tune your day-to-day workflow (what prompts you), and use the sandbox to enforce hard boundaries that the OS itself enforces. Never use bypassPermissions on your dev machine. Layer both for defense in depth: the permission layer stops careless mistakes; the sandbox catches what permission layer misses.

Quick Quiz

Q1. You're about to refactor authentication across 12 files. Which mode?

A) acceptEdits — speed matters
B) plan — read-only, get a written plan first
C) bypassPermissions — you're experienced
D) default — just answer prompts as they come

Answer: B — Plan mode lets you read and think but not write or execute. You get a full plan first, review it for architectural issues, then drop into default mode to execute. Fastest way to catch big mistakes before code is written.

Q2. Your settings have "allow": ["Bash"] and "deny": ["Bash(rm:*)"]. Claude tries rm -rf node_modules. What happens?

A) Auto-runs — matches allow first
B) Blocked — deny beats allow
C) Prompts — rules conflict
D) Error returned to Claude without telling you

Answer: B — Precedence is deny > ask > allow. Pair broad allows with narrow denies for destructive patterns. This is how you safely allow Bash for tests while blocking rm.

Q3. You enable the sandbox with filesystem.allowWrite: ["./"]. A script tries to write to /tmp/cache. What happens?

A) Writes succeed — /tmp is special-cased
B) Write fails (EACCES) — /tmp is outside allowlist
C) Claude prompts you to allow
D) It's redirected silently into the project

Answer: B — Sandbox is OS-enforced. Only paths in allowWrite are writable; everything else returns an OS error (EACCES). If you need /tmp/cache, add it to allowWrite explicitly. This is what makes sandbox different from permission modes: it's not advisory, it's mandatory.
