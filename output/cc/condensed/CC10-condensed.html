CC10: Claude Features — Thinking, Caching, Citations, Files

Extended reasoning, cost-cutting caching, document input, citations, and sandboxed code execution

The Big Idea

Claude 4.x ships five production-grade features that make apps faster, cheaper, and more trustworthy. Extended thinking gives you a hidden reasoning trace for hard problems. Prompt caching cuts input costs 90% on stable prefixes. Citations grounds answers in source documents automatically. Image/PDF input lets Claude analyze visual content. Code execution runs sandboxed Python. Each solves a real pain point; knowing when to use each is what separates prototype from production.

Analogy

Extended thinking is like asking a senior engineer a hard question and watching them think aloud for two minutes before giving a confident answer—the reasoning happens before the response, invisible but real. Prompt caching is like a tax accountant keeping your filing on their desk for five minutes instead of re-reading it each time you ask "what's box 14b?"—same answer, fraction of the cost. Citations work like a legal brief with footnotes that actually point to the right page, auto-generated, no parsing needed.

How It Works

  1. Enable extended thinking per request with a budget_tokens parameter; Claude emits hidden thinking blocks before its visible answer.
  2. Mark stable content (system prompt, tools, large documents) with cache_control metadata; subsequent identical requests reuse the cache at 10% input cost.
  3. Pass images or PDFs in message content blocks; Claude analyzes them as part of normal reasoning.
  4. Enable citations on document blocks; Claude automatically annotates its answer with source spans.
  5. Call the code-execution tool; Claude writes Python, the sandbox runs it, and returns output to embed in the answer.

Pseudocode

// Extended thinking for hard reasoning
response = call_claude(
  messages: [user_query],
  thinking: { enabled: true, budget_tokens: 8000 }
)
// response.content has [thinking_block, text_block]

// Prompt caching: mark the stable prefix
response = call_claude(
  system: [
    { type: "text", text: LONG_SYSTEM_PROMPT, cache_control: "ephemeral" }
  ],
  messages: [current_query]
)
// First call: cache_creation_input_tokens filled
// Second call (within 5 min): cache_read_input_tokens filled, 90% savings

// Image and PDF input
response = call_claude(
  messages: [{
    content: [
      { type: "image", source: { type: "base64", data: image_b64 } },
      { type: "text", text: "What's in this image?" }
    ]
  }]
)

// Citations on documents
response = call_claude(
  messages: [{
    content: [
      { type: "document", source: { type: "base64", data: pdf_b64 }, citations: true },
      { type: "text", text: "Summarize this policy." }
    ]
  }]
)
// response.content[0].citations = array of {cited_text, start_char, end_char}

// Code execution
response = call_claude(
  tools: [{ type: "code_execution", name: "code_execution" }],
  messages: [{ content: "Generate a histogram of [1,1,2,3,3,3,4,5,5,5,5,7]" }]
)
// Claude writes Python, sandbox runs it, returns figure or file

Common Misconceptions

  • Myth: "Extended thinking always makes answers better." Reality: Only on hard reasoning (architecture, refactoring, ambiguous specs). On lookups or classification, thinking wastes tokens. Save it for tasks worth an Opus call.
  • Myth: "Caching always saves money." Reality: Cache writes cost 25% more than normal input. You only profit if you get cache hits later. One-shot calls lose money with caching enabled.
  • Myth: "My cached prefix is broken—Anthropic's API is buggy." Reality: Caches match byte-for-byte. One space, one newline, one timestamp difference and you bust the cache. Keep the prefix static between calls.

Key Takeaway

These five features are how you ship Claude at scale: thinking for hard reasoning, caching for cost, images/PDFs for rich input, citations for trustworthiness, and code-execution for automation. Each one has a gotcha (budget limits, cache invalidation, file size caps, network isolation), but once you know them, they're the difference between a chatbot and a production system.

Quick Quiz

Q1. You're building a file-save hook that needs a fast allow/block decision. Should you enable extended thinking?

A) Yes, better decisions are always worth it.
B) No, thinking adds latency and cost; quick verdicts don't need it.
C) Only on Haiku.
D) Always at max budget.

Answer: B — Hooks need speed. Extended thinking adds seconds of latency and real token cost. Save thinking for hard reasoning, not snap verdicts.

Q2. Your one-shot CLI tool calls Claude once per run, no follow-up. Should you cache the system prompt?

A) Yes, caching is always cheaper.
B) No, you pay the write premium with no second call to amortize it.
C) Yes, with 1-hour TTL.
D) Yes, but only on Opus.

Answer: B — Cache writes cost more than normal input. They pay off only if you get hits later. One-shots get no benefit, so caching loses you money.

Q3. You're caching a system prompt but sometimes get cache hits and sometimes don't. Most likely cause?

A) API outage.
B) You're concatenating a timestamp or request ID into the prefix.
C) You changed the model.
D) Caching is non-deterministic.

Answer: B — Caches match prefix-exactly. Any varying token in the cached region (timestamps, IDs, random data) busts the cache. Move all dynamic content after the cache breakpoint.
