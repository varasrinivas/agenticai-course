CC3: CLAUDE.md & Memory

How Claude Code remembers things across sessions, repos, and machines via configuration cascades and memory shortcuts.

The Big Idea

CLAUDE.md is a markdown file that holds all the conventions, rules, and domain knowledge for a project. Claude Code reads up to five different CLAUDE.md files (user-level, project-level, directory-level, and org-managed) and merges them in priority order. The cascade solves the problem: "why does Claude follow rule X on my machine but not my teammate's?" Answer: that rule lives in your personal CLAUDE.md, not the project file. Learn where each layer lives, how to write a lean 25-line minimum-viable file, and how to use the # and @ shortcuts to manage memory without leaving your session.

Analogy

Think of how a chef inherits cooking style: the world has general culinary norms (don't cross-contaminate), the restaurant has a house style (we plate French), the kitchen station has its own rules (grill preheats to 500°F), and the chef has personal preferences (always finish with butter). Each layer adds detail; specific layers override general ones. The pain without layering: every chef gets one 100-page manual where specifics about tonight's tasting menu drown in general kitchen safety rules. CLAUDE.md tiers give you those layers for code projects.

How It Works

  1. Five tiers load at session start: Managed (org policy) → Local (your machine, .claude/CLAUDE.local.md) → Project (./CLAUDE.md, checked into git) → Directory (src/payments/CLAUDE.md, any subdirectory) → User (~/.claude/CLAUDE.md, your machine only). Tier 1 wins on conflict; tiers below add and refine.
  2. Write the minimum-viable project CLAUDE.md: five sections (What This Project Is, How to Run Things, Conventions, Don't Do These, On Commits), roughly 25 lines. Keep it under 200 lines total; long playbooks go in skills, which load only when invoked.
  3. Use path-specific rules for monorepos: either via frontmatter globs in a single CLAUDE.md, or per-directory CLAUDE.md files. When Claude edits code in packages/api/src/billing/, it gets the union of all CLAUDE.md files in that path tree.
  4. Edit memory in-session without leaving: /memory shows all loaded files and lets you pick one to edit. # at message-start saves a memory line on the fly. @ paths inside CLAUDE.md import other markdown files (up to 5 hops deep).
  5. Avoid the four anti-patterns: don't restate your README, don't embed long tutorials (move to skills), don't add personality instructions ("you are a helpful assistant" is noise), and never commit secrets like API keys or database passwords.

Pseudocode

At session start, Claude Code performs the cascade:

  IF managed-policy exists:
    LOAD managed-policy
  IF .claude/CLAUDE.local.md exists:
    MERGE .claude/CLAUDE.local.md (adds/overrides managed)
  IF ./CLAUDE.md exists in current repo:
    MERGE ./CLAUDE.md (adds/overrides local)
  FOR each directory from current file up to repo root:
    IF CLAUDE.md exists in that directory:
      MERGE that CLAUDE.md (adds/overrides project level)
  IF ~/.claude/CLAUDE.md exists:
    MERGE ~/.claude/CLAUDE.md (adds to everything else)

  FINAL merged instructions are now loaded in this session.
  When editing a file, nearest CLAUDE.md wins on any conflict.

Common Misconceptions

  • Myth: CLAUDE.md should contain everything from the README, plus tips, plus tutorials. Reality: CLAUDE.md should be lean and fast, loaded every turn. Long playbooks and tutorials belong in skills (CC5), which load only when invoked. Keep CLAUDE.md under 200 lines.
  • Myth: When two CLAUDE.md files conflict, the newer/recent one wins. Reality: Tier number wins. Project (tier 3) beats user (tier 5) on any conflict, regardless of recency. Know the cascade order: Managed > Local > Project > Directory > User.
  • Myth: User-level CLAUDE.md (~/.claude/CLAUDE.md) applies to teammates too. Reality: It's your machine only. To share conventions with teammates, move rules to ./CLAUDE.md (project level) and check it into git.

Key Takeaway

CLAUDE.md is not a prompt or a tutorial file — it's a standing instruction that Claude Code loads every session, telling Claude what conventions and rules apply to this project. The five-tier cascade solves "why do different people see different behavior" by letting org policies flow down through team rules, project rules, sensitive-area rules, and personal preferences. Write a lean 25-line project file, use directory-level files for monorepos, and use the # and @ shortcuts to manage memory without leaving your session.

Quick Quiz

Q1. Two CLAUDE.md files conflict: ~/.claude/CLAUDE.md says "always show diffs" and ./CLAUDE.md says "skip diffs for trivial changes." Which wins?

A) User-level file (always show diffs)
B) Project file (skip for trivial) — project tier 3 beats user tier 5
C) They concatenate; both apply
D) Last-loaded wins

Answer: B — The cascade prioritizes by tier number. Project (tier 3) beats user (tier 5). Lower tier number = higher priority.

Q2. You're in a monorepo. packages/billing/CLAUDE.md says "all changes need tests." ./CLAUDE.md says nothing. You edit a file in packages/billing/. What rules apply?

A) Only root CLAUDE.md
B) Only billing CLAUDE.md
C) Both — directory file adds to root rules
D) Neither — CLAUDE.md only loads at repo root

Answer: C — Per-directory CLAUDE.md files are additive. They merge with root. The deeper file can tighten rules without bloating the root file.

Q3. Your CLAUDE.md is 800 lines and Claude responses are getting slow. What's the right fix?

A) Trim everything not strictly required
B) Use /compact more often
C) Move long playbooks into skills; keep only always-on rules in CLAUDE.md
D) Switch to a faster model

Answer: C — CLAUDE.md content loads every turn. Skills load only when invoked. For long playbooks, skills are far cheaper. Trimming helps too, but skills are the structural fix.
