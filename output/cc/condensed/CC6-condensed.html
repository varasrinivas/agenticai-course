CC6: Subagents

Specialist agents in isolated contexts—delegate verbose work, keep your conversation clean and focused.

The Big Idea

Subagents are specialist workers that run in their own context window with their own tools and optional memory. When you need to run a task that produces massive output but returns just a summary—scanning the codebase, auditing for patterns, multi-step research—hand it to a subagent. The subagent's reads, greps, and tool calls stay out of your main conversation. You get clean summaries. It's the architectural equivalent of delegation: stay focused on the high-level conversation while specialists handle the verbose details.

Analogy

Imagine asking a junior architect to verify that your database schema matches the OpenAPI spec. You could read all 47 migration files and 12 endpoint definitions yourself, spending three hours. Better: hand it to the junior, let them work in their own corner, and have them come back with "consistent, except orders.status drifts from OrderStatus." That verdict is gold. Their process (the 47 files they read) doesn't show up in your office.

Subagents are that junior. Each runs in a fresh context, gets a tight prompt and tool allowlist, and returns just the summary.

How It Works

  1. Author the subagent as a Markdown file with YAML frontmatter at .claude/agents/<name>.md. Define its name, description, allowed tools, model, and optional memory scope.
  2. Claude detects when your task matches the subagent's description and spawns it in a fresh context window with just that focused prompt.
  3. Subagent runs in isolation—reads files, greps patterns, edits in a worktree—without those tool calls appearing in your main transcript.
  4. Result returns to you as a clean summary. Your conversation stays high-level; verbose work stays hidden.
  5. Memory persists (optional) across sessions so the subagent learns codebase patterns and gets smarter over time.

Pseudocode

When task matches subagent description:
  create new context window
  inject subagent frontmatter as system prompt
  inject MEMORY.md (first 200 lines) if memory scope set
  enable only tools listed in frontmatter
  submit user task to subagent

While subagent works:
  tool calls don't appear in parent transcript
  if tool_call not in allowed_tools: refuse

When subagent finishes:
  return summary to parent
  if memory: project set: append new learnings to MEMORY.md
  close subagent context
  parent conversation resumes clean

Common Misconceptions

  • Myth: Subagents are just skills with memory. Reality: Subagents run in isolated context windows; their tool calls are invisible. Skills run inline in your conversation. Pick subagent for verbose work you don't want to see; pick skill for reusable logic you might invoke multiple times in one session.
  • Myth: All five built-in subagents (Explore, Plan, general-purpose, statusline-setup, Claude Code Guide) fire automatically. Reality: Only those whose description matches your current task. You can disable any with "deny": ["Agent(Explore)"] in permissions.
  • Myth: Plugin subagents can include hooks and MCP server definitions. Reality: Plugin subagents silently drop hooks, mcpServers, and permissionMode for security. Copy the agent to .claude/agents/ if you need them.

Key Takeaway

Subagents isolate verbose work. A subagent runs in its own context, respects a narrow tool allowlist, and returns just the summary. Use them when a task's internal process would drown your conversation—scanning, auditing, multi-step research, code review. Author one as a Markdown file with 16 frontmatter fields; invoke via natural language, @-mention, or --agent flag. Optional persistent memory makes the subagent learn across sessions.

Quick Quiz

Q1. You want a subagent that learns about your codebase across sessions, with knowledge shareable to your team via git. Which memory: value?

A) user
B) project
C) local
D) global

Answer: B — project stores memory at .claude/agent-memory/<name>/, which goes into git. user is personal-only; local is project but gitignored.

Q2. The parent session runs in bypassPermissions mode. The custom subagent's frontmatter says permissionMode: default. What actually happens?

A) Subagent uses default — frontmatter wins.
B) Subagent inherits bypassPermissions from parent — cannot be overridden.
C) Error — modes conflict.
D) The stricter of the two wins.

Answer: B — If the parent uses bypassPermissions, acceptEdits, or auto mode, that takes precedence and the subagent's permissionMode frontmatter is ignored.

Q3. Subagent vs Skill vs Main—where does "verbose research that produces a 5-line summary" go?

A) Main conversation — you need to see the work.
B) Skill running inline — reusable.
C) Subagent (or skill with context: fork) — verbose work isolated, summary returns.
D) Plan mode in main — describe the work first.

Answer: C — The classic subagent use case: heavy verbose work in isolation, just the summary returned. Either dedicated subagent or a fork-style skill both achieve isolation.
