Session Mastery — Beyond --continue

CC0 covered the basics: --continue, --resume, /rename. Here's the operator-grade toolkit:

CommandWhat it does
claude --continueReopens most recent session in this project
claude --resumePicker showing every saved session
claude --resume <id>Reopens by session ID (scriptable)
claude --from-pr <n>Bootstraps a session from a GitHub PR — pulls diff, comments, sets context
claude --fork-sessionBranches the current session into two parallel timelines
claude --resume -n 5Picker showing only last 5 sessions
/rename "name"Inside session, give it a memorable name
/branchFork the current session into two timelines from this point
/rewindRoll back to a prior turn — pretend the bad turn never happened

Pro pattern: /branch for "let me try a different approach"

You're 12 turns into a refactor and want to try a different design without losing your current state. /branch forks the session: now you have two timelines from this point. Try approach A in one, approach B in the other, keep whichever wins.

Picker shortcuts

Inside the --resume picker: type to filter, arrow keys to move, Enter to open. Use /rename liberally so the picker actually helps. A picker with 47 unnamed sessions is useless; with 47 named sessions, it's a search index for your own thinking.

Extended Thinking UX — Triggers & Budget

For complex tasks, extended thinking lets Claude reason longer before responding. Five ways to invoke it; one way to budget it.

TriggerHowWhen
Always-onalwaysThinkingEnabled: true in settings.jsonYou always want max-quality, latency be damned
Per-session/effort high or /effort maxSwitching gears mid-session for a hard task
One-shotInclude word "ultrathink" in your promptJust this one tricky turn
Per-skilleffort: max in skill frontmatter, or include "ultrathink" in skill bodyOne specific workflow needs deep thought every time
UX toggleOption+T (macOS) / Alt+T (Windows/Linux)Quickly flip on for next turn
See thinkingCtrl+O — verbose mode toggleYou want to see the reasoning, not just the answer

Budget

Set MAX_THINKING_TOKENS environment variable (e.g. 32000) to cap how much Claude can reason. Higher = better answers on hard problems, more tokens spent. Default is moderate; turn up for genuine architecture decisions, down for chatty tasks.

When extended thinking helps vs hurts

Helps: ambiguous architectural decisions, debugging non-obvious failures, designing schemas, writing complex regex, security review.
Hurts: simple file edits, formatting, doc fixes — you pay tokens and latency for no quality gain. Match the trigger to the task; don't leave alwaysThinkingEnabled on for everything.

Worktrees — Parallel Sessions on the Same Repo

Git worktrees let you check out multiple branches simultaneously into different directories — same repo, multiple working copies. Claude Code's --worktree flag spins up a session in a temporary worktree:

# Open a session in an isolated copy of the current branch
$ claude --worktree

# Or branch off main, isolated
$ claude --worktree --branch main

# Subagents can use the same primitive via frontmatter:
# isolation: worktree

Why isolated worktrees beat just opening two terminals

  • Two Claude sessions on the same files would race each other — race conditions on edits, confusing test runs.
  • Worktree = independent file system view. Each session edits its own copy.
  • Auto-cleaned: if a worktree-isolated session makes no changes, the worktree is deleted on exit.

.worktreeinclude — copy gitignored files in

Worktrees only get tracked files by default. Your .env, node_modules, build artifacts — gone. Drop a .worktreeinclude at repo root to specify gitignored files that should be copied or symlinked into worktrees:

.env.local
.env.development
.vscode/settings.json

For larger artifacts (node_modules, .cache), use worktree.symlinkDirectories in settings.json:

{
  "worktree": {
    "symlinkDirectories": ["node_modules", ".cache", ".next"],
    "sparsePaths": ["packages/api", "packages/web"]
  }
}

sparsePaths uses git sparse-checkout to only materialize specific directories — useful for huge monorepos where you only need to work on one package.

Two-Claude Review — Shift-Left Bug Catching

Everyday Analogy

Why don't engineers self-review their own code in PRs? Because they wrote it — they have all the context, all the assumptions, all the rationalizations. They know why this looks weird, so it doesn't look weird. A second pair of eyes (a teammate's) sees the code without the author's reasoning, which is exactly the perspective that catches bugs.

Same problem with one Claude session generating and reviewing. The reviewing turn has the generation reasoning in its context window — it's biased toward agreeing. Two separate Claude sessions, one generates, one reviews, with no shared context, get you the second-pair-of-eyes effect.

The pattern

# Session A: generate
$ cd ~/project
$ claude --agent code-generator
> "Implement the new pricing tier (free/pro/enterprise) as described in PRICING.md.
   Add tests. When done, output a summary of changes."

# Session A produces a PR. Now switch to Session B (different terminal):
$ cd ~/project
$ claude --agent code-reviewer --worktree --branch main
> "Review PR #1234. Look for security issues, edge cases, missed test coverage,
   and consistency with existing patterns. Output: CRITICAL / WARNING / SUGGESTION."

# Session B sees ONLY the PR diff — no generation reasoning.

Bonus: run them in parallel via worktrees, fork mode, or scheduled jobs. The generator finishes, the SubagentStop hook (CC5) auto-spawns the reviewer with the same task description — entirely automated pipeline.

Why this matters

Teams using two-Claude review report fewer bugs reaching production by something like 30-50% — not because Claude is smarter, but because the second instance has none of the first instance's confirmation bias. Cheap second opinion. Run it on every non-trivial PR.

Background Work — /loop and /schedule

Two primitives for "do this without me watching":

/loop — in-session background monitor

Bundled skill (CC3). Reruns a check on a cadence, reports drift. Common uses:

> /loop every 5 minutes: run `pnpm test:e2e:smoke`. Report only when output changes.

> /loop until error rate > 1%: hit /healthz on staging every 30s. Alert on Slack if it spikes.

> /loop until merged: poll PR #123, when checks turn green and reviews approved, post in #releases.

The loop runs in the same session, doesn't block the main conversation, and you can ask it to stop with "/loop stop."

/schedule — cron-style background tasks

For "run this every weekday morning" / "run this nightly" workflows. The agent fires up automatically, runs the task, reports back next time you're online.

> /schedule weekdays at 9am: run yesterday's PR triage report

> /schedule every Monday 10am: clean up branches merged >30 days ago, open a PR with the deletes

> /schedule daily at 6am: pull latest main into all my long-lived feature branches, report conflicts

Picking the right primitive

NeedUseNotes
Watch a value during a session/loopSame session, doesn't survive shutdown
Recurring task over weeks/months/schedule or RoutinesPersists across restarts
Triggered by repo eventsGitHub ActionsUse Claude Code in headless mode
Triggered by external systemWebhook + headless claude -pGeneric glue
UI-driven backgroundDesktop notifications hookNative toast on macOS/Linux/Windows

Headless Mode — -p, JSON, Pipes

Claude Code can run as a Unix utility. -p (or --print) takes a prompt, runs to completion, prints the result, exits.

# Simple text response
$ claude -p "Summarize the last 5 commits in this repo"

# Structured JSON output
$ claude -p "List exported functions in src/api.ts" --output-format json

# Schema-constrained JSON — you define the shape Claude must return
$ claude -p "Analyze this PR" --output-format json --json-schema '{
  "type": "object",
  "properties": {
    "summary": {"type": "string"},
    "risk": {"type": "string", "enum": ["low","medium","high"]},
    "issues": {"type": "array", "items": {"type": "string"}}
  },
  "required": ["summary", "risk"]
}'

# Pipe input/output
$ git diff main | claude -p "Summarize this diff in 3 bullets"

$ claude -p "Generate test cases for this fn" < src/utils.ts > tests/utils.test.ts

Useful flags

  • -p <prompt> — non-interactive, prints result, exits.
  • --output-format json — structured response, parseable.
  • --json-schema <json> — force the response shape.
  • --no-session-persistence — don't write transcript to disk (CI-friendly).
  • --append-system-prompt <text> — add custom instructions for this run.
  • --permission-mode dontAsk — don't prompt; only pre-approved tools work.
  • --dangerously-skip-permissions — only inside disposable containers.

GitHub Actions Integration — Claude in Your Pipeline

Claude Code runs in GitHub Actions same as locally. The pattern: every PR triggers a workflow that uses Claude Code to review, suggest, or block.

# .github/workflows/claude-review.yml
name: Claude PR Review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p "Review this PR (compare HEAD to origin/main).
                     Look for: bugs, security issues, missing tests,
                     style violations against CLAUDE.md.
                     Output JSON with: summary, severity, findings[]." \
            --output-format json \
            --permission-mode dontAsk \
            --no-session-persistence \
            > review.json

      - name: Post review as PR comment
        run: |
          BODY=$(jq -r '.summary' review.json)
          gh pr comment ${{ github.event.pull_request.number }} --body "$BODY"
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}

Hardening for CI

  • Strict permission mode. --permission-mode dontAsk + a tight allow list in .claude/settings.json. CI runners shouldn't have unbounded shell.
  • Sandbox on. CI runners are ephemeral but mistakes can still leak secrets. sandbox.enabled: true with allowlisted domains.
  • No session persistence. --no-session-persistence — nothing to clean up between runs.
  • Two-Claude review. Run a generator job + reviewer job. Reviewer doesn't see generator's reasoning. (CC7's #4 use case.)
  • Token narrowing. The ANTHROPIC_API_KEY should be a CI-specific key, rate-limited, with cost caps. Don't share with dev keys.
Cost discipline

A naive review-on-every-PR job can rack up significant token spend. Three controls: (1) only run on non-draft PRs, (2) use --model haiku for the first-pass triage, escalate to Sonnet only for non-trivial findings, (3) skip if PR diff exceeds a size threshold — very large PRs need human review anyway.

Image Input, Voice, Plugins — The Last 10%

Image input

Drag an image into the terminal session, or pipe one with cat screenshot.png | claude. Claude reads the image with vision: "What's in this UI screenshot?", "Why does this graph look weird?", "Convert this hand-drawn architecture diagram to Mermaid."

Voice — /voice

Configure with /voice or in settings:

{
  "voice": {
    "enabled": true,
    "mode": "hold",
    "autoSubmit": true
  }
}

mode: "hold" = push-to-talk. "tap" = tap-to-toggle. autoSubmit: true sends when you stop talking. Useful for hands-busy debugging on the couch.

Plugins — share your setup

Plugins package skills, subagents, hooks, and MCP server configs into a single distributable. Install with /plugin install <name>. Browse marketplaces in settings (extraKnownMarketplaces). Anything you build for your team can ship as a plugin so other teams get it with one command.

Plugin caveats from earlier modules: plugin subagents drop hooks, mcpServers, permissionMode silently. Plugin skills are namespaced as plugin:skill. Managed admins control allowlists via strictKnownMarketplaces and blockedMarketplaces.

Desktop notifications — the Notification hook (CC5)

{
  "hooks": {
    "Notification": [
      {
        "matcher": "permission_prompt",
        "hooks": [
          {
            "type": "command",
            "command": "osascript -e 'display notification \"Claude needs you\" with title \"Claude Code\"'"
          }
        ]
      }
    ]
  }
}

For Linux: notify-send. For Windows: powershell -Command "..." with toast notification. Now your laptop pings when Claude needs an answer — you don't have to keep checking.

Hands-On Lab — Two-Claude Review on a Real PR

You'll set up a complete two-Claude review pipeline: a generator session implements a small feature in a worktree, then an isolated reviewer session evaluates the diff with no shared context. End state: a checked-in workflow you can rerun on every future change.

Prerequisites

  • A real repo with passing tests and a non-trivial codebase. (If you don't have one, git clone https://github.com/expressjs/express works for the exercise.)
  • The code-reviewer subagent from CC4 at .claude/agents/code-reviewer.md. If you skipped that lab, scroll up to CC4 step "Your First Custom Subagent" first.

Step 1 — Open the generator session in a worktree

$ cd ~/your-repo
$ claude --worktree --branch main

Worktree gives this session its own filesystem copy. Edits won't touch your main working tree.

Step 2 — Generate a small feature

Pick something self-contained — a /healthz endpoint, a CLI flag, a date helper. Type:

> In plan mode: add a /healthz endpoint that returns
   { status: "ok", uptime_seconds: <process.uptime()> }.
   It should have a unit test. Show me the plan; don't write code yet.

Review the plan. If it looks right, drop into default mode (Shift+Tab) and:

> Proceed. Implement the plan. Run the tests. Commit when green.

Claude implements, tests, and commits. Note the branch name in the worktree (something like claude-XXXX).

Step 3 — Open the diff for the reviewer

From the worktree session, push the branch and open a PR:

> Push this branch and open a PR titled "feat: add /healthz endpoint".
   Don't include the implementation reasoning — PR body should describe what changed
   and why, in plain user-facing terms.

Note the PR number. Exit this session (Ctrl+D or /exit).

Step 4 — Open a fresh reviewer session in a NEW worktree

$ cd ~/your-repo
$ claude --worktree --branch main --agent code-reviewer

Critical: this is a different process with no shared context. The reviewer agent has only the system prompt from your CC4 subagent file and the PR diff — no clue why each line was written.

Step 5 — Run the review

> Use --from-pr to load PR #<number> and review it. Output:
   - CRITICAL: must fix before merge
   - WARNING: should fix
   - SUGGESTION: consider improving
   For each, cite the file and line. Don't implement anything.

Read the review. Did it catch anything the generator missed? Common findings: missing input validation, missing error case in tests, hard-coded magic numbers, missing JSDoc/types, race condition in async path.

Step 6 — Apply fixes and re-review (optional)

If the reviewer found issues:

  • Switch back to the generator worktree
  • claude --resume the generator session
  • Tell it: "The reviewer flagged these issues. Apply the fixes."
  • Push to the same branch
  • From the reviewer worktree, re-run the review — verify the issues are resolved

Step 7 — Codify the pattern in CI

Drop this at .github/workflows/two-claude-review.yml so every PR gets the second pair of eyes automatically:

name: Two-Claude Review
on:
  pull_request:
    types: [opened, synchronize]
    branches: [main]

jobs:
  reviewer:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }

      - run: npm install -g @anthropic-ai/claude-code

      - name: Two-Claude review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p "Review PR #${{ github.event.pull_request.number }}.
                     Use the code-reviewer agent. Compare HEAD to origin/main.
                     Output JSON: {summary, severity, findings:[{file,line,severity,note}]}." \
            --agent code-reviewer \
            --output-format json \
            --json-schema '{
              "type":"object",
              "properties":{
                "summary":{"type":"string"},
                "severity":{"type":"string","enum":["clean","minor","major","blocker"]},
                "findings":{"type":"array","items":{"type":"object"}}
              },
              "required":["summary","severity"]
            }' \
            --permission-mode dontAsk \
            --no-session-persistence \
            > review.json

      - name: Comment on PR
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          SEVERITY=$(jq -r '.severity' review.json)
          SUMMARY=$(jq -r '.summary' review.json)
          gh pr comment ${{ github.event.pull_request.number }} \
            --body "**Two-Claude Review** — severity: \`$SEVERITY\`\n\n$SUMMARY\n\n<details><summary>Findings (JSON)</summary>\n\n\`\`\`json\n$(cat review.json)\n\`\`\`\n</details>"

      - name: Block merge if blocker
        run: |
          SEVERITY=$(jq -r '.severity' review.json)
          if [ "$SEVERITY" = "blocker" ]; then
            echo "Reviewer flagged a blocker. Fix before merge."
            exit 1
          fi

Commit, push, and watch the next PR get a Claude review comment automatically.

Step 8 — (Optional) Add /loop while the reviewer runs

If you start the reviewer locally and want to keep working in another session, the /loop bundled skill keeps you informed:

> /loop until PR #<number> has the review comment posted by github-actions:
   poll the PR every 30s. When the comment lands, summarize the severity and findings.

Knowledge Check

1. You want to design two completely different approaches to a refactor in parallel without losing your current state. What's the right primitive?

A
Open a second terminal and run claude there.
B
claude --resume with a new approach.
C
/branch to fork the session into two timelines from the current point.
D
/clear and start over.
Correct. /branch forks the session in place. Pair with --worktree if you need separate file systems too.
Look again. /branch forks at the current point. Two terminals would race on files; --resume with new approach loses the diverging-from-this-point structure.

2. CI workflow needs to call Claude Code once and get structured JSON back to drive subsequent steps. Which flags?

A
claude --interactive --json
B
claude -p "<prompt>" --output-format json --json-schema "<schema>" --permission-mode dontAsk --no-session-persistence
C
claude --resume CI --headless
D
claude --watch --json-out
Correct. All four flags matter: -p for non-interactive, --output-format json for structure, --json-schema to force the shape, --permission-mode dontAsk + --no-session-persistence to keep CI clean.
Look again. Headless CI = -p + --output-format json + --json-schema + --permission-mode dontAsk + --no-session-persistence.

3. A worktree starts fresh without your .env.local, so the dev server fails. Cleanest fix?

A
git add .env.local — commit it.
B
Add .env.local to .worktreeinclude.
C
Set worktree.symlinkDirectories: [".env.local"].
D
Run cp .env.local /tmp/worktree/ manually.
Correct. .worktreeinclude is the file-list mechanism. symlinkDirectories is for directories (node_modules, .cache). Don't commit secrets.

4. /loop vs /schedule — you want to "rerun a smoke test every 5 minutes during a deploy and ping me if it breaks." Which?

A

B

C

5. Two-Claude review — what's the actual benefit over having one Claude session generate AND review?

A
Faster — runs in parallel.
B

C

D

Correct. Same Claude, same model, two contexts. The reviewer evaluates the diff with no idea why each line was written. That's the second-pair-of-eyes effect.

Module Summary

  • Session toolkit: --continue, --resume, --from-pr, --fork-session + in-session /rename, /branch, /rewind.
