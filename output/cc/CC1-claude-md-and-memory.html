CC1: CLAUDE.md & Memory

How Claude Code remembers things across sessions, repos, and machines — the configuration cascade, path-specific rules, and the new Auto Memory feature where Claude writes its own notes.

Learning Objectives

  • Identify the 5 tiers of CLAUDE.md and which one wins on conflict.
  • Write a Minimum-Viable CLAUDE.md for a new repo in 5 minutes.
  • Use path-specific rules to make a single instruction file fit a monorepo.
  • Distinguish CLAUDE.md (you write) from Auto Memory (Claude writes).
  • Avoid the four config anti-patterns that quietly degrade Claude's behavior.
Memory in Claude Code is layered. The cascade explains why one team's CLAUDE.md "doesn't apply" inside another teammate's session.

The 5-Tier CLAUDE.md Cascade

Everyday Analogy

Think of how a chef inherits cooking style: the world has general culinary norms (don't cross-contaminate), the restaurant has a house style (we plate French), the kitchen station has its own rules (the grill chef preheats to 500°F), tonight's special has its own twist, and the chef has personal preferences (always finish with butter). Each layer adds detail; specific layers override general ones for the same dish.

The pain without layering: every chef on every shift gets one giant 100-page manual. Specifics about tonight's tasting menu drown in general kitchen safety rules. Updates are impossible — change one line, retrain everyone.

Same for Claude Code: machine-wide instructions (e.g. "always show diffs") shouldn't have to live in every repo. Repo-specific instructions ("this codebase uses pnpm, not npm") shouldn't leak to other projects. The cascade gives you those layers.

Claude Code reads up to five instruction sources at session start, then merges them in this priority order:

CLAUDE.md Sources — Highest Priority First
TierPathWhat goes here
1. Managedmanaged-settings dir / OS policyOrg-mandated rules: PII redaction, license gates — admins only.
2. Local.claude/CLAUDE.local.mdGitignored. "Skip auth check on my dev box."
3. Project./CLAUDE.md or .claude/CLAUDE.mdArchitecture decisions, conventions, run commands. Checked into git.
4. Directorysrc/payments/CLAUDE.md (any subdir)Tighter rules for sensitive areas: "no Bash here, all changes need tests."
5. User~/.claude/CLAUDE.mdYour personal style: "always show diffs," "prefer functional style."

Higher tiers add to lower tiers. Conflicts on the same instruction are resolved by tier 1 (Managed) winning, then 2, 3, 4, 5. Directory-level files trump root-project files when Claude is working inside that directory — so src/payments/CLAUDE.md overrides anything more permissive in ./CLAUDE.md when you're editing payment code.

Why it matters

This is the answer to "why does Claude follow rule X on my machine but not my teammate's?". Answer: that rule lives in your user CLAUDE.md (tier 5), not in the project file. Move it to ./CLAUDE.md and check it in, or accept it's a personal preference.

The Minimum-Viable CLAUDE.md

Forget exhaustive specs. The smallest CLAUDE.md that actually changes Claude's behavior covers five short sections:

# CLAUDE.md — my-saas-app

## What this project is
Multi-tenant SaaS for invoice processing. Node 20 backend + React frontend + Postgres.

## How to run things
- `pnpm install` — install deps (we use pnpm, not npm)
- `pnpm dev` — start backend (port 3001) and frontend (5173) together
- `pnpm test` — vitest, must pass before any commit
- `pnpm typecheck` — tsc --noEmit, must pass before any commit

## Conventions
- All money in cents (integers), never floats
- Use Zod schemas for every API boundary (see `src/schemas/`)
- Errors: `throw new HttpError(400, 'reason')`, never `throw 'string'`
- Database access via Drizzle ORM only — no raw SQL except in `src/db/migrations/`

## Don't do these
- DO NOT write to `src/generated/*` — that's codegen output
- DO NOT add new dependencies without asking; `pnpm-lock.yaml` is sacred
- DO NOT commit without running `pnpm typecheck && pnpm test` first

## On commits
- Conventional commits: `feat:`, `fix:`, `chore:`, `refactor:`
- Reference Linear ticket: `feat(billing): add proration [ENG-123]`

Five sections. Twenty-five lines. This file changes Claude's behavior more than any clever prompt. Notice what it does NOT include: prose about "you are a helpful assistant," step-by-step tutorials, or content that's already in the README.

Keep it under 200 lines

CLAUDE.md content lives in every prompt's context, every turn. A 1,000-line CLAUDE.md eats your context budget and slows responses. Move long-form content into skills (CC3) — those load only when invoked.

Path-Specific Rules — One File, Many Rules

Monorepos and large codebases need different rules in different folders. Two ways to solve it:

Option A: Frontmatter globs — sectioned in one file

A single root CLAUDE.md can use frontmatter to scope sections. The instructions only load when Claude is working with matching files:

---
globs:
  - "src/api/**"
---

# API conventions
- Every endpoint returns `{ok: true, data}` or `{ok: false, error}`
- All inputs validated with Zod
- Add OpenAPI annotations in `src/api/openapi.ts`

Option B: Per-directory CLAUDE.md — the cleaner monorepo pattern

Drop a CLAUDE.md in any subdirectory. Claude Code automatically traverses up from the working file and merges all CLAUDE.md it finds:

my-monorepo/
  CLAUDE.md                # global conventions
  packages/
    api/
      CLAUDE.md            # API: Fastify + Zod
      src/
        billing/
          CLAUDE.md         # billing: extra strict, all changes need tests
    web/
      CLAUDE.md            # web: React + Tailwind

When Claude edits a file in packages/api/src/billing/, it gets the union of all three CLAUDE.md files in scope. Sensitive areas can tighten the rules without making the root file longer.

What just happened?

You learned the two scoping patterns. Option A works when most rules are global with a few exceptions. Option B works when sub-projects have substantially different conventions. Mix them freely.

/init & AGENTS.md Compatibility

Don't write CLAUDE.md from scratch. Run /init in any repo and Claude inspects package.json, README.md, the directory tree, and the existing tooling, then proposes a starter CLAUDE.md you can edit.

$ claude
> /init

[Claude reads package.json, README, src/]
[Claude proposes a draft CLAUDE.md]
[You review, edit, accept]
→ CLAUDE.md written to current directory

To force a fresh init even if a CLAUDE.md exists, set CLAUDE_CODE_NEW_INIT=1 before invoking /init.

AGENTS.md — the cross-tool standard

The Agent Skills open standard defines AGENTS.md as the cross-tool equivalent of CLAUDE.md. Claude Code reads AGENTS.md too — with CLAUDE.md taking precedence when both exist. If your repo already has an AGENTS.md, you don't need to duplicate. If you write CLAUDE.md, also keep AGENTS.md in sync if you want other AI tools (Codex, Gemini Code Assist) to honor the same conventions.

Excluding noisy CLAUDE.md files

If a dependency's node_modules/some-pkg/CLAUDE.md shows up and pollutes your context, set claudeMdExcludes in settings.json:

{
  "claudeMdExcludes": ["node_modules/**", "vendor/**", ".terraform/**"]
}

Auto Memory — Claude Writes Its Own Notes

This is the new bit. CLAUDE.md is what you write for Claude. Auto Memory is what Claude writes for itself. Different file, different lifecycle, different purpose.

Technical Definition

Auto Memory (Claude Code v2.1.59+) is a built-in memory system where Claude writes its own notes during a session. The notes live at ~/.claude/projects/<project>/memory/ in two layers: an index file MEMORY.md and topic-specific files like debugging.md or api-conventions.md. Claude reads them at the start of every session for that project; you can browse them with /memory.

CLAUDE.md vs Auto Memory — when to use which

Two Memory Systems — Different Purposes
PropertyCLAUDE.mdAuto Memory
Who writes itYou (the developer)Claude (during sessions)
What it containsConventions, rules, "always do X"Discovered patterns, surprises, "this debugged-once-and-took-2-hours" notes
ScopePer repo (or user / managed)Per project, your machine only
Loaded intoEvery prompt (always)Session start (only)
Best for"This codebase uses pnpm""The CI build fails when X is set; root cause was Y"
StorageRepo (git)~/.claude/projects/<p>/memory/

The auto-memory directory layout

~/.claude/projects/my-saas-app/memory/
  MEMORY.md              # index: list of files + 1-line description each
  debugging.md           # "saw error X, root cause was Y"
  api-conventions.md     # "endpoints use snake_case in DB, camelCase in JSON"
  build-quirks.md        # "vitest needs --pool=forks on macOS"
  preferences.md         # "user prefers Tailwind utility classes over @apply"

Controls

  • /memory — open the auto-memory browser; view, edit, delete entries.
  • autoMemoryEnabled: false in settings.json — turn it off entirely.
  • autoMemoryDirectory: "/custom/path" — relocate storage.
  • CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 — per-invocation kill switch.
Security note

Auto Memory is on by default and stores discovered project context on your local machine. Never commit it to git. If you work on confidential code (medical, financial, classified), check whether your team policy allows local LLM-written project notes — if not, set CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 in your shell rc file. Auto Memory does NOT round-trip to Anthropic between sessions; it's local on disk.

What just happened?

You now know two memory systems instead of one: CLAUDE.md (you author, lives in repo, loaded every turn) and Auto Memory (Claude authors, lives on your machine, loaded at session start). Most teams use both: CLAUDE.md for the durable "always do X" rules, Auto Memory for the volatile "remember that weird debugging session" notes.

Four CLAUDE.md Anti-Patterns That Quietly Hurt

What NOT to Put in CLAUDE.md
Anti-patternWhy it hurtsDo this instead
Restating your READMEDoubles context cost for zero new infoReference: "see README for setup"
Long step-by-step tutorialsLoaded every turn, drowns the real rulesMove to a skill (CC3); loaded only when invoked
Personality/tone instructions"You are a helpful assistant" is noise; Claude is already helpfulJust write rules and conventions
Secrets / API keysRepo-checked CLAUDE.md ends up in commits and on screensUse .env, mention which env var, never the value
CLAUDE.md tells Claude what conventions to follow. Time to wire up a real repo.

Hands-On Lab — Configure a Real Repo in 8 Minutes

Pick any repo you have writable access to. (If you don't have one handy, git clone https://github.com/anthropic-ai/anthropic-cookbook — a real public repo with enough surface to make this exercise feel real.) Open a terminal in it.

Step 1 — Generate a starter CLAUDE.md with /init

$ cd ~/your-repo
$ claude
> /init

Claude reads package.json, README, and the directory tree, then proposes a draft. Read it carefully. Most starter drafts are ~70% right, ~30% wrong (it guesses at conventions you haven't written down). Edit before saving.

Step 2 — Tighten the draft to the Minimum-Viable shape

Cut the draft down to these five sections only (delete everything else):

  • What this project is — one paragraph.
  • How to run things — install / dev / test / typecheck commands.
  • Conventions — 3-5 bullets, project-specific only.
  • Don't do these — 2-3 anti-patterns specific to this repo.
  • On commits — conventional-commits style if you use it.

Aim for <25 lines total. Save and exit.

Step 3 — Add a directory-level rule

Pick a sensitive subdirectory (e.g. src/auth/, src/payments/, migrations/). Drop a CLAUDE.md there with stricter rules:

$ cat > src/auth/CLAUDE.md <<'EOF'
# Auth module — tighter rules

## Don't
- DO NOT change token expiration without consulting #security
- DO NOT add new auth endpoints without writing tests first

## Required
- Every change here needs a corresponding test in tests/auth/
- Run `pnpm typecheck` before claiming a fix works
EOF

Step 4 — Verify the cascade

Inside Claude Code, ask it what conventions are in effect when working in src/auth/:

> What conventions apply when I edit src/auth/login.ts? List them by source file.

Claude should cite both the root CLAUDE.md and src/auth/CLAUDE.md. If it only cites the root, the directory file isn't being picked up — check the path.

Step 5 — Add a personal rule via user-level CLAUDE.md

Create or edit your user-level file:

$ mkdir -p ~/.claude
$ cat > ~/.claude/CLAUDE.md <<'EOF'
# My personal preferences

- Always show me a diff before applying file edits
- Prefer functional style over classes when both work
- When showing test output, show only the failures, not all passes
EOF

Restart your session (or open a new one) and confirm it's loaded:

> What's in my user-level CLAUDE.md?

Step 6 — Set up Auto Memory

Auto Memory is on by default in v2.1.59+. Check it works:

> /memory

The auto-memory browser opens. If it's empty, that's expected — Claude hasn't logged anything yet. Force it to write something:

> Note this for future sessions: this codebase uses pnpm@9.1, not npm.
   Save it to your auto-memory under a topic file called "build-quirks".

Run /memory again; you should see build-quirks.md with that note. Open a fresh session in this repo and ask "What package manager does this repo use?" — Claude should reference the auto-memory.

Step 7 — Verify the no-secrets rule

Open your CLAUDE.md and confirm there are zero hardcoded secrets, API keys, or connection strings. Reference env vars by name only:

# OK
The Stripe key is in the `STRIPE_SECRET_KEY` env var.

# NOT OK
The Stripe key is `sk_live_abc123...`

Step 8 — Commit and verify with a teammate (optional)

$ git add CLAUDE.md src/auth/CLAUDE.md
$ git commit -m "docs(claude): set up project + auth conventions"
$ git push

Have a teammate pull, open Claude Code in the repo, and ask: "What's special about the auth module conventions?" If they get the directory-level rules, the cascade works for everyone. If they don't, your project file is at the wrong path or the directory file got gitignored.

Lab complete — what you should have

Three CLAUDE.md files (root + directory + user-level), live Auto Memory entry, and a teammate-verifiable cascade. The whole thing committed in one PR. Total time: under 10 minutes for a small repo, ~20 for a large one.

Knowledge Check

1. Two CLAUDE.md files have conflicting rules: ~/.claude/CLAUDE.md says "always show diffs" and ./CLAUDE.md says "skip diffs for trivial changes." Which wins?

A
The user-level file (always show diffs) — user > project.
B
The project file (skip for trivial) — project (tier 3) beats user (tier 5).
C
They concatenate — both apply.
D
Last-loaded wins.
Correct. Project beats user. The cascade order is Managed > Local > Project > Directory > User. Lower-numbered tiers win on conflict.
Look again. Project (tier 3) beats user (tier 5) — lower tier number = higher priority.

2. You're working in a monorepo. packages/billing/CLAUDE.md says "all changes need tests." ./CLAUDE.md says nothing about tests. You edit a file in packages/billing/. What rules apply?

A
Only root CLAUDE.md (the deeper one is ignored).
B
Only the billing CLAUDE.md (replaces root).
C
Both — the directory-level file adds tests-required to the root rules.
D
Neither — CLAUDE.md only loads at repo root.
Correct. Per-directory CLAUDE.md merges with root. The deeper file can tighten rules for sensitive areas without bloating the root file.
Look again. Per-directory CLAUDE.md files are additive — they merge with parent files when Claude works inside that directory.

3. Your CLAUDE.md is 800 lines and Claude responses are getting slow. What's the right fix?

A
Trim everything that's not strictly required.
B
Use /compact more often.
C
Move long-form playbooks (e.g., "how to run a release") into skills (CC3); CLAUDE.md keeps only the always-on rules.
D
Switch to a faster model.
Correct. CLAUDE.md content loads every turn. Skills load only when invoked. For long playbooks, skills are far cheaper. Trimming helps too (option A) but skills are the structural fix.
Look again. The right structural answer is to move long-form content into skills, which load only when invoked. CLAUDE.md should hold always-on rules.

4. CLAUDE.md vs Auto Memory: which one would you use for "this CI test is flaky on macOS only when DOCKER_HOST is unset"?

A
Auto Memory — Claude discovers it during a debugging session and writes it to build-quirks.md for next time.
B
CLAUDE.md — commit it so the team sees it.
C
Both — copy it into both files.
D
Neither — one-off observations don't belong anywhere.
Correct. Auto Memory is for discovered, machine-specific, emergent observations. CLAUDE.md is for durable team conventions. (If the flakiness is a real team issue, you might also document it in CLAUDE.md once confirmed.)
Look again. Auto Memory is the right home for one-off discoveries. CLAUDE.md is for durable team-level conventions.

5. A teammate complains: "I don't see any of the conventions you claimed to set up in CLAUDE.md." What's the most likely cause?

A
You wrote them in ~/.claude/CLAUDE.md (user-level, your machine only) instead of ./CLAUDE.md (project-level, checked into git).
B
Claude has a bug.
C
Their model is different.
D
Auto Memory is conflicting.
Correct. User-level CLAUDE.md (tier 5) lives only on your machine. To share with teammates, move rules to project-level ./CLAUDE.md and check it in.
Look again. User-level CLAUDE.md is your-machine-only. Anything teammates need to see lives in ./CLAUDE.md at the project root, committed to git.

Module Summary

  • 5 tiers, lower number wins: Managed > Local > Project > Directory > User.
  • Minimum-viable CLAUDE.md: 5 sections, <25 lines, project-specific rules only.
  • Path-specific rules via frontmatter globs (single file) or per-directory CLAUDE.md (cleaner for monorepos).
  • /init bootstraps a draft. AGENTS.md is the cross-tool standard; CLAUDE.md takes precedence when both exist.
  • Auto Memory: Claude's own notes, on your machine, separate from CLAUDE.md. Browse with /memory; disable with autoMemoryEnabled: false.
  • Don't put: README content, long playbooks (use skills), tone/personality instructions, secrets.
