A·05 Technical AI Questions
Technical · Panel
How would you use LLMs to extract structured clinical information from unstructured provider documentation?
The Pipeline
  • Ingestion — receive provider docs via HL7/FHIR or direct API
  • PHI de-identification — NLP entity extraction and scrubbing before LLM sees any data
  • Structured extraction — LLM extracts ICD-10 codes, CPT codes, clinical indicators, dates, severity flags → structured JSON
  • Criteria matching — RAG retrieval against InterQual criteria corpus; LLM highlights matched/unmatched criteria
  • Confidence scoring → auto-approve / AI-assisted review / escalate
Key Design Choice
RAG over fine-tuning for criteria matching — InterQual criteria update annually. Fine-tuning each update cycle is expensive. RAG indexes the updated criteria corpus; no model retraining required.
Technical · Panel
How do you prevent AI hallucination in a clinical decision support context?
Defence in Depth
  • RAG-based grounding — LLM can only reference retrieved InterQual criteria + source documents; speculation is architecturally constrained
  • Citation requirement — every recommendation must cite specific criteria matched + clinical evidence from provider docs
  • Confidence thresholds — low-confidence outputs route to human review, never auto-processed
  • Contradiction detection — secondary check catches outputs violating ICD-10 coding logic or InterQual hard stops
  • Human-in-the-loop — AI can hallucinate an approval; only humans issue denials
Architectural Principle
"AI can hallucinate an approval. Only humans can issue a denial. That single rule shapes the entire system architecture."

B·03 Clinical Concepts Glossary
Inpatient StatusMedicare Part A. Physician expects ≥2 midnight stay. Higher reimbursement to hospital. $1,500–$5,000+ more than observation per claim.
Observation StatusOutpatient classification. Medicare Part B. Lower reimbursement + higher patient cost-sharing. AI flag: obs-to-IP conversion opportunity.
Two-Midnight RuleCMS rule: inpatient if physician expects ≥2 midnights AND documents that expectation. Case Intelligence CSS score aims to prevent misclassification.
Medical NecessityClinical justification for a service. Must be documented, defensible, evidence-based. InterQual criteria are the standard. AutoReview auto-populates documentation.
Admission ReviewFirst UM review at time of admission. AutoReview 2026 automates 98% of day-one condition-specific admission reviews.
Continued Stay ReviewDaily/periodic review while admitted. Does patient still meet inpatient criteria? AutoReview 2026 automates 58% of these. LLM reads evolving EHR data in real-time.
Physician AdvisorMD/DO doing second-level UM reviews. Reviews cases failing first-level screening. Conducts peer-to-peer calls. Case Advisor provides LLM-extracted evidence + citations.
CSS ScoreCase Stratification Score. LLM trained on patient cases + UR data + claims data. Predicts inpatient admission likelihood [0–1]. Drives routing decision.
Exception-Based UMAI handles routine majority; humans handle exceptions only. 98%/58% automation = reviewers focus on the genuinely hard cases.
Length of Stay (LOS)AI predicts initial LOS and updates as patient data evolves. Enables proactive discharge planning — SNF/rehab/home health arranged before patient is medically ready.
ICD-10 / CPT CodesICD-10: diagnosis codes. CPT: procedure codes. LLM extraction of these from unstructured clinical notes is a core AI task in AutoReview and Auth Accelerator.
Clinical Concordance% of AI decisions matching expert clinical reviewer decisions. Target: 95%+. North-star quality metric. If drops: model drift or criteria change.
FHIR / HL7Healthcare interoperability standards. FHIR required by CMS-0057 for PA transparency APIs. InterQual Exchange provides criteria via FHIR APIs.
B·04 AI Architecture Answers
Architecture
What AI architecture powers Case Intelligence's CSS score?
Optum Published + Design Thinking
  • Training data: Historical inpatient admission outcomes labelled against ICD-10 codes, vital signs, ED triage notes, chief complaint, prior utilisation, claims patterns
  • Feature engineering: Structured features (age, vitals, labs, codes) + unstructured features via LLM embedding of clinical notes
  • Model type: Likely an ensemble — gradient boosting on structured + transformer embeddings on text → meta-model
  • Ops: Score updates in real-time as new EHR data arrives during the visit
  • Routing: High CSS → first-level admission review; Low CSS → observation pathway; Medium CSS → physician advisor
Frame It
"The hard part isn't the model — it's the real-time data pipeline from EHR, calibration across different hospital systems, and bias testing to ensure the score isn't systematically miscalibrated for any demographic group."
Architecture
How does InterQual AutoReview extract clinical data from an EHR and map it to InterQual criteria?
The AutoReview Pipeline
  • RPA layer — navigates EHR via API to collect structured data: medications, vitals, lab results, diagnoses, physician orders
  • AI/NLP layer — LLM/NLP processes unstructured clinical notes to extract indicators relevant to InterQual criteria
  • Criteria mapping engine — rules + ML match extracted indicators to specific InterQual criteria data points; pre-populates review form
  • Confidence score — high + criteria met = auto-complete; low or unmet = pre-populated draft for human
Key Insight
"The auto-completed review contains embedded clinical data at every criteria point — so when the payer sees it, the evidence is right there, reducing denials because documentation is complete and consistent."
Architecture
How do you prevent the CSS score from encoding racial or socioeconomic bias?
Bias Framework
  • Training data audit — historical admission data can encode past biases. Audit for differential outcomes by race, ethnicity, insurance type, ZIP code
  • Fairness metrics — precision, recall, AUC evaluated separately across demographic subgroups. Alert if performance gap exceeds threshold
  • Debias proxy variables — ZIP code and insurance type correlate with protected attributes; use causal modelling to remove spurious correlations
  • Post-deployment monitoring — track actual inpatient rates by demographic group. Disparate impact vs pre-AI baseline → halt and recalibrate
Power Statement
"In healthcare AI, a biased model doesn't just hurt accuracy metrics — it can worsen health inequities at scale. That's a line I won't let a system I own cross."

C·05 Delivery Interview Questions
Delivery · HM
How do you set reliable delivery estimates for AI features when model training is non-deterministic and clinical validation adds unpredictable cycle time?
Three-Layer Approach
  • Separate engineering vs AI quality milestones — engineering is estimable with normal story-pointing; AI quality is range-bounded, not point-estimated
  • Time-box model development — "in 6 weeks we'll have a model at X% concordance; if it meets clinical threshold, we ship. If not, go/no-go conversation." Preserves commitment discipline.
  • Clinical validation in critical path from day one — plan for 6–10 weeks (clinical validation 4–6 weeks + shadow mode 4 weeks). Any time saved is a bonus, never the plan.
Practical Tool
Two-track sprint board — engineering track (predictable, commit to dates) and AI quality track (time-boxed experiments). Stakeholders see both clearly.
Power Statement
"Engineering I commit to. AI quality I time-box. The uncertainty is honest, the expectation is clear."
Delivery · Panel
Walk me through handling a production incident in the AutoReview system during peak PA review hours.
Response Timeline
  • T=0: First question — "Is this causing incorrect approvals or incorrect denials?" Different clinical risk profiles require different escalation paths
  • T+15 min: Activate feature flag — route all reviews to manual mode. Clinical operations continue; AI bypassed. Communicate to clinical operations lead immediately
  • T+30 min: Clinical SME assesses any decisions made during failure window. HIPAA breach assessment if PHI handling involved
  • T+4 hrs: Root cause identification — model drift? Data feed corruption? Criteria update not regression-tested?
  • T+24 hrs: Incident report: root cause + impact + corrective AND preventive actions. Regulatory team loop-in if PA decisions materially affected
Power Statement
"The clinical fallback must always work. If the AI layer fails and the fallback fails too, that's an architectural failure I own."
Delivery · Panel
Product wants continued-stay automation from 58% to 80% in 2 quarters. Engineering says 4 quarters minimum. How do you handle this?
Four-Step Approach
  • Step 1 — Diagnose the commercial driver — customer contract deadline vs competitive response vs internal aspiration? Each requires a different response.
  • Step 2 — Decompose the estimate transparently — model dev (8 wks) + clinical validation (6 wks) + shadow mode (4 wks) + staged rollout (4 wks) = 22 weeks minimum. Clinical validation cannot be shortcut.
  • Step 3 — Propose 3 concrete options — (A) partial delivery to 65–70% in 2Q, (B) additional ML engineers to parallelise, (C) phased: 80% for high-volume conditions first, extend to remainder in Q3–Q4.
  • Step 4 — Make a clear recommendation and defend it — never say "it depends."
Power Statement
"I'm not the obstacle to ambition — and I won't commit to dates that damage clinical quality. Both failures are mine to own."
