Module 07 · Track 3 — SDLC

The Implementation Loop

Design artifacts don't write themselves into code — but with Gemini CLI they get surprisingly close. This module teaches you the implementation rhythm: scaffold from spec, build feature by feature using @ context, generate commit messages from staged diffs, run a code review before every merge, and refactor cleanly without losing business logic. Every pattern here uses the docs/ artifacts you built in M05 and M06.

What You'll Learn

  • Scaffold a complete project directory structure from your PRD and OpenAPI spec
  • Build features incrementally using @src/ and @docs/ context together
  • Use multiple @ mentions to keep new code consistent with existing patterns
  • Generate conventional commitsA commit message standard where each message follows the format: type(scope): description. Types include feat, fix, refactor, test, docs, chore. Tools like semantic-release and conventional-changelog parse these to auto-generate changelogs and version bumps. by piping git diff --cached through Gemini
  • Run a structured code review prompt that catches security, error handling, and TypeScript issues
  • Refactor route handlers to thin controllers with service layer extraction

Scaffolding from Spec

Analogy — The General Contractor

Before any interior work begins on a building, the general contractor lays out the floor plan: rooms, doors, electrical conduit paths, and plumbing rough-in. Nothing is finished yet — just the skeleton that tells every subcontractor where their work goes. Scaffolding your project from spec does exactly this: empty directories, stub files with correct imports, and placeholder functions that make the build pass before a single line of real logic is written.

The pain without scaffolding: every developer invents their own file layout, exports are inconsistent, and the first PR review is half about file placement. The mapping to Gemini CLI: your PRD and OpenAPI spec already contain all the structural information — Gemini extracts it into a directory tree so everyone starts from the same layout.

Gemini CLI prompt
gemini "@docs/prd.md @docs/api-contracts/openapi.yaml Scaffold the project structure for a Hono + TypeScript backend. Create a directory tree with these layers: src/routes/ (one file per resource), src/services/ (business logic), src/schemas/ (Zod validation), src/db/ (Prisma client + migrations), src/middleware/ (auth, error handler), src/jobs/ (pg-boss workers). For each file, generate a stub with correct imports and exported function signatures but no implementation. Show the complete directory tree output."
WHAT: Gemini reads the OpenAPI spec to identify resources (tasks, teams, users), then creates one file per resource-layer combination.
WHY: Starting from a spec-derived scaffold means every stub file already knows its function signatures from the OpenAPI operationId fields. No naming debates.
GOTCHA: Gemini may generate directory-creation commands (mkdir -p) alongside the stubs. Review the output before pasting — don't run commands you haven't read.

Implementing POST /api/tasks

Gemini CLI prompt
gemini "@src/ @docs/api-contracts/openapi.yaml Implement the POST /api/tasks endpoint. Requirements: 1) Zod validation using CreateTaskSchema from src/schemas/task.schema.ts, 2) Prisma insert via task.service.ts createTask(), 3) Return 201 with the created Task object, 4) Return 400 for validation errors with structured error body, 5) Return 500 with a safe error message (no stack traces in response). Use Hono context typing throughout."
src/routes/tasks.ts — POST /api/tasks
import { Hono } from 'hono'
import { zValidator } from '@hono/zod-validator'
import { CreateTaskSchema, StatusUpdateSchema } from '../schemas/task.schema'
import { createTask, updateTaskStatus, listTasks } from '../services/task.service'
import type { AppEnv } from '../types'

export const tasksRouter = new Hono<AppEnv>()

// CHUNK 1 — POST /api/tasks
// WHAT: Validate request body, insert task, return 201
// WHY: Centralised validation prevents invalid data reaching the DB
// GOTCHA: zValidator returns 422 by default — we override to 400 to match OpenAPI spec
tasksRouter.post(
  '/',
  zValidator('json', CreateTaskSchema, (result, c) => {
    if (!result.success) {
      return c.json(
        { code: 'VALIDATION_ERROR', message: 'Invalid request body', errors: result.error.flatten() },
        400
      )
    }
  }),
  async (c) => {
    // CHUNK 2 — Extract auth context injected by Clerk middleware
    // WHAT: Get authenticated user's ID and team from JWT claims
    // WHY: Every task must be associated with the caller's team at creation time
    const { userId, teamId } = c.get('auth')
    const body = c.req.valid('json')

    try {
      // CHUNK 3 — Service call with error boundary
      // WHAT: Delegate DB write to service layer; never import prisma directly in routes
      // WHY: Routes should be thin — business logic belongs in services, not HTTP handlers
      const task = await createTask({ ...body, teamId, createdBy: userId })
      return c.json(task, 201)
    } catch (err) {
      // CHUNK 4 — Safe error response
      // WHAT: Log full error server-side; return only a safe message to the client
      // GOTCHA: Never expose err.message to the client — it may contain SQL or stack traces
      console.error('[POST /tasks]', err)
      return c.json({ code: 'INTERNAL_ERROR', message: 'Failed to create task' }, 500)
    }
  }
)
WHAT: A complete Hono route handler with Zod validation, typed auth context, service delegation, and safe error handling.
WHY: The four CHUNK annotations mirror the prompt requirements exactly — this is what Gemini generates when you give it annotated code from the same file as context.
GOTCHA: zValidator from @hono/zod-validator returns 422 by default. The custom callback overrides this to return 400 to match the OpenAPI spec. Without the callback, your spec and runtime disagree.
One endpoint is implemented. Now you add the next one — and the challenge is keeping the new code consistent with what you already built.

Multi-file Consistency with @ Mentions

When Gemini implements endpoint #2, it doesn't automatically know how you implemented endpoint #1 — unless you tell it. Loading existing source files as context is the difference between a codebase that reads like one person wrote it and one that looks like a contractor switched every three files.

Technical Definition — Pattern Reference

A pattern referenceAn existing source file loaded into the prompt context specifically to serve as a style and structure guide. When Gemini sees an existing implementation, it mirrors the same import style, error handling pattern, naming conventions, and export format — without being explicitly instructed on each. is an existing file loaded as context not for its content, but for its conventions. When you include @src/routes/tasks.ts while asking Gemini to implement GET /tasks, it infers: use the same import order, the same zValidator pattern, the same error shape, and the same typed auth context.

Using Existing Code as Style Reference

Gemini CLI prompt
gemini "@src/routes/tasks.ts @src/schemas/task.schema.ts @docs/api-contracts/openapi.yaml Implement the GET /api/tasks endpoint. Requirements: 1) Query params: optional status filter (enum) and assigneeId (uuid), 2) Return paginated results: { tasks: Task[], total: number }, 3) Use the same error handling and auth pattern as the POST endpoint already implemented in @src/routes/tasks.ts, 4) Add the Zod query param schema to task.schema.ts, consistent with CreateTaskSchema style."
WHAT: Three @ mentions: existing route (for pattern), existing schema (for consistency), OpenAPI spec (for contract).
WHY: Phrase 3 ("same error handling and auth pattern as the POST endpoint") is the key instruction. Without it, Gemini may choose a different error format for GET vs POST.
SDLC Pattern — The Three-File Context

For every new endpoint, load exactly: 1) @src/routes/{resource}.ts (existing route file), 2) @src/schemas/{resource}.schema.ts (existing schemas), 3) @docs/api-contracts/openapi.yaml (contract). This three-file pattern is the consistent context budget for the Implementation track — small enough to stay fast, large enough to keep code consistent.

Code is written and consistent. Now let's generate commit messages that tell the story of what changed — automatically, from the diff itself.

Commit Messages from git diff

Commit messages written by a developer who just finished three hours of implementation are almost always low quality: "fix stuff," "update route," "WIP." Gemini reads the actual diff and writes a message that explains what changed and why — in a format that semantic-release can parse.

# Stage your changes first
git add src/routes/tasks.ts src/services/task.service.ts src/schemas/task.schema.ts

# Pipe the staged diff to Gemini
git diff --cached | gemini -p "Write a conventional commit message for these changes. Format: type(scope): description (max 72 chars). Add a body explaining the why (not the what). Types: feat, fix, refactor, test, docs, chore. Be specific about what changed."
# Stage your changes first

# Pipe the staged diff to Gemini
git diff --cached | gemini -p "Write a conventional commit message for these changes. Format: type(scope): description (max 72 chars). Add a body explaining the why (not the what). Types: feat, fix, refactor, test, docs, chore. Be specific about what changed."
WHAT: git diff --cached outputs only staged changes. Piping it to gemini -p sends the diff as the prompt body.
WHY: The -p flag sets the system prompt. The diff is the user message. Gemini sees exactly what's changing — no summarization needed.
GOTCHA: On large diffs (>500 lines), context budget becomes a concern. Prefix with git diff --cached -- src/routes/tasks.ts to scope the diff to a single file.

What Just Happened?

Gemini read the actual diff — the changed files, line additions, and removals — and produced a commit message that names the specific files, explains the error handling rationale, references the PRD section, and links the GitHub issue. This is the commit message that would take 10 minutes to write manually, generated in 5 seconds from the diff alone.

Tip — One-liner Commit Workflow

Combine the generate-and-commit steps in one pipeline (review the output before committing):

$msg = git diff --cached | gemini -p "Write a conventional commit message only, no explanation."
Write-Host "Commit message: $msg"
# Review, then:
git commit -m $msg
msg=$(git diff --cached | gemini -p "Write a conventional commit message only, no explanation.")
echo "Commit message: $msg"
# Review, then:
git commit -m "$msg"
Code is committed. Before opening a PR, run the code review loop — Gemini catches four categories of issues that human reviewers miss when tired.

Code Review Loop

The most valuable code review happens before you open a PR — when you're still the only one who has seen the code and can fix it without embarrassment. Gemini's review is not a replacement for human code review; it's a pre-flight check that eliminates the predictable issues so human reviewers can focus on architecture and product decisions.

Gemini CLI prompt — post-implementation review
gemini "@src/routes/tasks.ts Review this file for: 1) Correctness — does the implementation match the OpenAPI spec in @docs/api-contracts/openapi.yaml? 2) Error handling — are all failure modes caught? 3) Security — check for SQL injection risk, missing auth checks, and information leakage in error responses. 4) TypeScript best practices — any implicit any, missing return types, or unsafe type assertions. Format each finding as: [SEVERITY: CRITICAL|MEDIUM|LOW] [CATEGORY] — file:line — issue — recommendation."

Review Findings — Sample Output

Gemini Code Review — Numbered Findings
1
SECURITY
src/routes/tasks.ts:38 — The teamId in the task creation body is taken directly from c.get('auth').teamId but there is no check that the authenticated user is actually a member of that team. A user could spoof a different teamId in the JWT if middleware is misconfigured. Recommendation: In task.service.ts createTask(), add a DB lookup to verify the user is a member of the teamId before insertion.
2
ERROR HANDLING
src/routes/tasks.ts:45 — The Prisma insert is wrapped in try/catch, but a Prisma unique constraint violation (duplicate task title within a team, per PRD §5 NFR-03) will be caught as a generic 500 error. Recommendation: Import Prisma from @prisma/client, check for err instanceof Prisma.PrismaClientKnownRequestError && err.code === 'P2002', and return 409 with code: "DUPLICATE_TASK_TITLE".
3
TYPESCRIPT
src/routes/tasks.ts:18 — const { userId, teamId } = c.get('auth') — the return type of c.get('auth') is inferred as any because AppEnv in src/types.ts doesn't type the 'auth' variable. Recommendation: Add Variables: { auth: { userId: string; teamId: string } } to the AppEnv type definition.
4
CORRECTNESS
openapi.yaml vs tasks.ts:51 — The OpenAPI spec defines the 201 response schema as Task which includes createdAt and updatedAt as ISO strings. Prisma returns these as Date objects. Hono's c.json() serializes them correctly, but the types won't match if a consumer does type-level checks. Recommendation: Add a response serializer that explicitly converts Date → string for the Task response shape.
Why It Matters

Finding #1 (auth bypass) is a security vulnerability. Finding #2 (unhandled Prisma error) is a correctness bug that appears in production. Both are invisible to the naked eye during implementation — they require cross-referencing the service layer with the middleware contract, which is exactly what Gemini does when you load all relevant files as context.

🔒

Checkpoint — Zero CRITICAL Findings Policy

Before every commit, run the code review prompt. Do not commit with any CRITICAL findings unresolved. MEDIUM findings should be fixed before PR open. LOW findings can be tracked as tech debt tickets but should not block the PR.

Routes are reviewed and correct. After a few features are in, the routes get fat — time to extract services and keep the codebase maintainable.

Refactoring — Extract Service Layer

Technical Definition — Thin Routes

The thin controller patternA design principle where HTTP route handlers (controllers) contain only: request parsing, validation, service call, and response formatting. All business logic (database queries, calculations, side effects) lives in a separate service layer. This makes routes testable without HTTP, and services testable without HTTP. keeps route handlers responsible only for HTTP concerns: parsing the request, calling a service, formatting the response. When you find Prisma queries, business rules, or conditional logic directly in a route handler, it's time to extract it. Routes that call services are easy to unit test; routes that contain business logic are not.

Gemini CLI prompt
gemini "@src/routes/ Refactor all route handlers to extract business logic into @src/services/. Rules: 1) Routes keep only: request parsing, service call, response formatting. 2) All Prisma queries move to service files. 3) Services must not import from Hono — they receive plain objects, return plain objects. 4) Show the before/after for tasks.ts → task.service.ts extraction. Preserve all error handling."

Before / After — Route Extraction

BEFORE — Fat Route (Anti-pattern)
tasksRouter.post('/',
  zValidator('json', CreateTaskSchema),
  async (c) => {
    const { userId, teamId } = c.get('auth')
    const body = c.req.valid('json')
    try {
      // Business logic in route — BAD
      const existing = await prisma.task.findFirst({
        where: { teamId, title: body.title }
      })
      if (existing) {
        return c.json({ code: 'DUPLICATE_TASK_TITLE' }, 409)
      }
      const task = await prisma.task.create({
        data: { ...body, teamId, createdBy: userId }
      })
      // Side effect in route — BAD
      await notifySlack(task)
      return c.json(task, 201)
    } catch (err) {
      return c.json({ code: 'INTERNAL_ERROR' }, 500)
    }
  }
)
AFTER — Thin Route + Service
// routes/tasks.ts — thin route
tasksRouter.post('/',
  zValidator('json', CreateTaskSchema),
  async (c) => {
    const { userId, teamId } = c.get('auth')
    const body = c.req.valid('json')
    try {
      const task = await createTask(
        { ...body, teamId, createdBy: userId }
      )
      return c.json(task, 201)
    } catch (err) {
      if (err instanceof DuplicateTaskError) {
        return c.json({ code: 'DUPLICATE_TASK_TITLE' }, 409)
      }
      console.error('[POST /tasks]', err)
      return c.json({ code: 'INTERNAL_ERROR' }, 500)
    }
  }
)

// services/task.service.ts — all logic here
export async function createTask(data: CreateTaskInput) {
  const existing = await prisma.task.findFirst({
    where: { teamId: data.teamId, title: data.title }
  })
  if (existing) throw new DuplicateTaskError(data.title)
  const task = await prisma.task.create({ data })
  await notificationService.scheduleSlackNotify(task)
  return task
}
WHAT: All Prisma calls, the duplicate-check logic, and the Slack side effect move to the service. The route becomes 12 lines from 22.
WHY: createTask() can now be unit-tested with a mock Prisma client — no HTTP setup, no Hono instance. The route test just verifies it calls the service correctly.
GOTCHA: The refactored version uses a typed DuplicateTaskError class instead of checking Prisma error codes in the route. Create this in src/errors.ts and throw it from the service — routes catch named errors, not DB internals.
SDLC Connection — Refactoring Before M08

In Module 08 (Testing), you will write unit tests for task.service.ts functions. If your business logic is still in the routes, you'll need a full HTTP test harness for every test. Extract services now — it makes your test suite 10x faster and more focused.
