Generating a Production Dockerfile

Analogy — The Shipping Container Spec

Before containerization, shipping goods was chaos: each ship's hold was a different shape, each port had different equipment, and you never knew if a crate would fit. The shipping container solved this by standardizing the box — not the contents. Docker does the same for software: the Dockerfile is the spec that defines exactly what goes into the container, no matter which server or cloud provider the container runs on.

The pain without a well-crafted Dockerfile: container images that are 2GB instead of 200MB (because build tools are bundled into prod), applications running as root (security nightmare), and no health check endpoint so the orchestrator never knows when the app crashed. The mapping: Gemini reads your src/ and package.json to produce a Dockerfile that knows your actual entry point, your correct Node version, and which files to exclude.

Technical Definition — Multi-Stage Build

A multi-stage buildA Docker build technique where a single Dockerfile has multiple FROM instructions. Each stage produces intermediate artifacts. The final stage copies only the artifacts it needs (e.g., compiled JS) from earlier stages, discarding build tools, dev dependencies, and source files. Result: dramatically smaller production images. uses multiple FROM instructions in one Dockerfile. Stage 1 (the "builder") installs all dependencies and compiles TypeScript. Stage 2 (the "runner") starts from a clean base image and copies only the compiled output — no TypeScript compiler, no devDependencies, no source maps in production. A typical Node.js app goes from a 1.2GB builder image to a 120MB production image this way.

Generated: Dockerfile
# ============================================================
# STAGE 1: Builder — install deps + compile TypeScript
# ============================================================
FROM node:20-alpine AS builder

WORKDIR /app

# Copy dependency manifests first (layer cache optimization)
COPY package.json package-lock.json ./
RUN npm ci --include=dev

# Copy source and compile
COPY tsconfig.json ./
COPY src ./src
RUN npm run build

# Remove devDependencies before copying to final stage
RUN npm prune --omit=dev

# ============================================================
# STAGE 2: Runner — minimal production image
# ============================================================
FROM node:20-alpine AS runner

# Security: create non-root user
RUN addgroup --system --gid 1001 appgroup && \
    adduser --system --uid 1001 --ingroup appgroup appuser

WORKDIR /app

# Copy only production artifacts from builder
COPY --from=builder --chown=appuser:appgroup /app/dist ./dist
COPY --from=builder --chown=appuser:appgroup /app/node_modules ./node_modules
COPY --from=builder --chown=appuser:appgroup /app/package.json ./package.json

# Switch to non-root user
USER appuser

# Expose application port
EXPOSE 3000

# Health check — Cloud Run and ECS use this to determine readiness
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD node -e "require('http').get('http://localhost:3000/health', r => { process.exit(r.statusCode === 200 ? 0 : 1) })"

# Start the application
CMD ["node", "dist/index.js"]
WHAT: Stage 1 builds everything; stage 2 copies only dist/ and production node_modules. No src/, no TypeScript compiler, no test files.
WHY (non-root user): Containers that run as root can write to the host filesystem if there's a container escape vulnerability. Running as UID 1001 limits blast radius.
WHY (health check): Cloud Run waits for the first successful health check before routing traffic. Without it, a container that starts but crashes internally will receive real requests.

What Just Happened?

The .dockerignore pattern !.env.example is worth noting — it excludes all .env.* files (which contain secrets) but explicitly includes .env.example (which contains only variable names with no values). This is the correct way to document required environment variables without leaking secrets into the image.

Why It Matters

Multi-stage builds typically reduce production image size by 70–85%. A 1.2GB development image becomes 150MB. At 10 deploys per day across a team, this saves gigabytes of registry transfer bandwidth and cuts cold-start times from 12 seconds to under 3 seconds on Cloud Run.

Generating a GitHub Actions Workflow

Analogy — The Assembly Line Spec

A CI/CD pipeline is a manufacturing assembly line: raw material (a git push) enters one end, and a deployed application exits the other. Each station on the line does one job — lint, test, build, package, deploy — and refuses to hand off to the next station if its job fails. The YAML file is the blueprint for that assembly line.

The pain without automated CI: developers forget to run tests before pushing, Docker images are built locally with inconsistent Node versions, and deployment is a manual SSH session that nobody wrote down. The mapping: Gemini writes the YAML that enforces the full pipeline every time, using your actual registry and Cloud Run service name.

The Prompt + Complete Workflow

Gemini CLI prompt
Generate a GitHub Actions workflow for this Node.js service:
Pipeline stages: lint → test → build Docker image → push to Artifact Registry → deploy to Cloud Run.
Use OIDC authentication (no long-lived GCP keys).
Trigger on push to main branch. Cache node_modules between jobs.
WHAT: OIDC authentication means GitHub Actions gets a short-lived token from Google Cloud via Workload Identity Federation — no JSON key file stored as a secret.
GOTCHA: OIDC requires a one-time setup of Workload Identity Federation in your GCP project. If you haven't done this, use google-github-actions/auth@v2 with a service account key as a fallback.
Generated: .github/workflows/deploy.yml
name: Build, Test, and Deploy

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

env:
  PROJECT_ID: ${{ secrets.GCP_PROJECT_ID }}
  REGION: us-central1
  REGISTRY: us-central1-docker.pkg.dev
  IMAGE: ${{ secrets.GCP_PROJECT_ID }}/task-api/task-api
  SERVICE_NAME: task-api

jobs:
  # ============================================================
  # JOB 1: Lint
  # ============================================================
  lint:
    name: Lint
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm run lint

  # ============================================================
  # JOB 2: Test
  # ============================================================
  test:
    name: Test
    runs-on: ubuntu-latest
    needs: lint
    env:
      DATABASE_URL: ${{ secrets.DATABASE_URL_TEST }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'
      - run: npm ci
      - run: npm test
      - name: Upload coverage report
        uses: actions/upload-artifact@v4
        if: always()
        with:
          name: coverage-report
          path: coverage/

  # ============================================================
  # JOB 3: Build Docker Image and Push
  # ============================================================
  build-push:
    name: Build and Push Docker Image
    runs-on: ubuntu-latest
    needs: test
    permissions:
      contents: read
      id-token: write   # Required for OIDC

    steps:
      - uses: actions/checkout@v4

      - name: Authenticate to Google Cloud via OIDC
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.WIF_PROVIDER }}
          service_account: ${{ secrets.WIF_SERVICE_ACCOUNT }}

      - name: Configure Docker for Artifact Registry
        run: gcloud auth configure-docker ${{ env.REGISTRY }} --quiet

      - name: Build Docker image
        run: |
          docker build \
            --tag "${{ env.REGISTRY }}/${{ env.IMAGE }}:${{ github.sha }}" \
            --tag "${{ env.REGISTRY }}/${{ env.IMAGE }}:latest" \
            .

      - name: Push Docker image
        run: |
          docker push "${{ env.REGISTRY }}/${{ env.IMAGE }}:${{ github.sha }}"
          docker push "${{ env.REGISTRY }}/${{ env.IMAGE }}:latest"

  # ============================================================
  # JOB 4: Deploy to Cloud Run
  # ============================================================
  deploy:
    name: Deploy to Cloud Run
    runs-on: ubuntu-latest
    needs: build-push
    permissions:
      contents: read
      id-token: write

    steps:
      - name: Authenticate to Google Cloud
        uses: google-github-actions/auth@v2
        with:
          workload_identity_provider: ${{ secrets.WIF_PROVIDER }}
          service_account: ${{ secrets.WIF_SERVICE_ACCOUNT }}

      - name: Deploy to Cloud Run
        uses: google-github-actions/deploy-cloudrun@v2
        with:
          service: ${{ env.SERVICE_NAME }}
          region: ${{ env.REGION }}
          image: ${{ env.REGISTRY }}/${{ env.IMAGE }}:${{ github.sha }}
          flags: '--min-instances=1 --max-instances=10 --memory=512Mi'
          env_vars: |
            NODE_ENV=production

      - name: Smoke test deployed service
        run: |
          URL=$(gcloud run services describe ${{ env.SERVICE_NAME }} \
            --region=${{ env.REGION }} --format='value(status.url)')
          curl --fail --retry 3 --retry-delay 5 "${URL}/health"
WHAT: Four sequential jobs — each needs: the previous. If lint fails, tests don't run. If tests fail, the image isn't built. If the image isn't pushed, no deploy happens.
WHY (smoke test): The final step calls the deployed service's /health endpoint. If the deployment succeeded but the container immediately crashes, the pipeline fails here instead of silently succeeding.
GOTCHA: The image is tagged with both :${{ github.sha }} and :latest. Deploy using the SHA tag, not latest, so rollbacks are always to a deterministic build.

Environment Variable Management

Environment variablesKey-value pairs injected into a process at runtime from outside the application code. Used to configure database URLs, API keys, feature flags, and other values that differ between environments (development, staging, production) without modifying the code itself. are the invisible layer between your code and your infrastructure. Hardcoding them is a security incident waiting to happen; not documenting them is an onboarding nightmare.

Gotcha — Never Commit .env Files

The .gitignore must exclude .env and .env.local but include .env.example. Gemini will add this to your .gitignore if you ask — but double-check it before your first commit. One accidental git add .env and you're rotating credentials and auditing access logs for hours.

Generating Operational Runbooks

Analogy — The Pilot's Emergency Checklist

Commercial pilots don't troubleshoot engine failures from memory — they reach for a checklist. Not because they're incompetent, but because stress degrades decision-making and checklists are faster than recall. An operational runbook is that checklist: a pre-written procedure for the incidents you know will happen, written before the incident, when you're calm and have time to think.

The pain: a 2am production incident with no runbook means the on-call engineer is free-styling, making it up, escalating everything, and writing it down afterward. The mapping: Gemini can draft the runbook from your existing service configuration before anything breaks.

Gemini CLI prompt

# Task API Operational Runbook

## 1. Deploy

**Normal deploy (via CI/CD — preferred)**
1. Merge PR to `main`. GitHub Actions builds and deploys automatically.
2. Monitor pipeline: `gh run list --branch main --limit 3`
3. Confirm deployment: `gcloud run services describe task-api --region us-central1`
4. Smoke test: `curl https://task-api-xxxx.run.app/health`

**Manual emergency deploy**
```bash
gcloud run deploy task-api \
  --image us-central1-docker.pkg.dev/PROJECT/task-api/task-api:SHA \
  --region us-central1 \
  --min-instances 1
```

---

## 2. Rollback

1. List available revisions:
   `gcloud run revisions list --service task-api --region us-central1`

2. Route all traffic to previous stable revision:
   ```bash
   gcloud run services update-traffic task-api \
     --region us-central1 \
     --to-revisions REVISION_NAME=100
   ```
3. Verify: check error rate in Cloud Monitoring drops below 0.1%.
4. Open post-mortem issue within 24 hours.

---

## 3. Scale

**Scale up during traffic spike**
```bash
gcloud run services update task-api \
  --max-instances 50 \
  --region us-central1
```

**Scale down after spike (cost control)**
```bash
gcloud run services update task-api \
  --max-instances 10 \
  --region us-central1
```

---

## 4. Incident: Service Returning 500s

**Severity**: P1 — immediate response required
**Detection**: error rate > 1% in Cloud Monitoring

1. Check recent deployments: `gcloud run revisions list --service task-api --region us-central1 --limit 3`
2. View live logs: `gcloud logging read "resource.type=cloud_run_revision AND severity>=ERROR" --limit 50 --format json`
3. If errors started after a deploy → **rollback immediately** (see Section 2)
4. If no recent deploy → check database health: `psql $DATABASE_URL -c "SELECT 1"`
5. Check for dependency issues: `gcloud run services describe task-api` (look for OOM kills in events)
6. Escalate to on-call DBA if DB connection errors persist > 5 minutes

---

## 5. Incident: Memory OOM Kills

**Detection**: Container restart count increasing in Cloud Run metrics

1. Check current memory limit:
   `gcloud run services describe task-api --format='value(spec.template.spec.containers[0].resources.limits.memory)'`
2. Increase memory limit:
   ```bash
   gcloud run services update task-api \
     --memory 1Gi \
     --region us-central1
   ```
3. Capture heap snapshot before restarting to diagnose leak:
   `curl https://task-api.run.app/debug/heapdump > heap-$(date +%s).heapsnapshot`
4. Open memory leak investigation ticket — do not keep the memory limit elevated indefinitely.

Gemini's Structured Analysis

Gemini analysis output
## Root Cause

**Prisma connection pool exhaustion** (error code P2024).

The log shows 49 identical `P2024` errors in 8 seconds. Your Prisma client is
configured with a connection pool limit of **5 connections**. A traffic spike
or a slow query that held connections open caused all 5 slots to be occupied,
and new requests could not acquire a connection within the 5000ms timeout.

**Why 5 connections is too low for Cloud Run:**
Cloud Run can scale to multiple container instances. If you have 3 instances
each with a 5-connection pool, you're hitting the database with up to 15
concurrent connections during a spike — plus any background jobs. The DB
server's max_connections limit may also be involved.

---

## Immediate Fix (minutes)

1. Increase Prisma pool size in the active Cloud Run revision:
   ```bash
   gcloud run services update task-api \
     --update-env-vars DATABASE_URL="postgresql://...?connection_limit=20&pool_timeout=10" \
     --region us-central1
   ```
   This redeploys with a larger pool without a code change.

2. Monitor: error rate should drop below 0.1% within 2 minutes.

---

## Long-Term Fix (next sprint)

1. **Externalize connection pooling** — Use PgBouncer or Cloud SQL Proxy's
   built-in connection pooler. This decouples your app's pool from Postgres's
   `max_connections` limit.

2. **Add per-request timeout context** in your service layer:
   ```typescript
   // Prevent slow queries from hogging connections
   const task = await prisma.$transaction(
     async (tx) => tx.task.findUnique({ where: { id } }),
     { timeout: 3000 }
   );
   ```

3. **Add connection pool metrics** to your Cloud Run service using
   `@prisma/instrumentation`. Alert when `pool_wait_duration_avg` exceeds 500ms.

4. **Load test before the next traffic event** using k6 or Artillery with
   realistic concurrency levels to validate the new pool size holds.

---

## Secondary Finding

The 503 responses with 5017ms and 5032ms latency suggest the pool timeout is
configured at 5000ms. Users experienced full 5-second hangs before getting a
503. Lower `pool_timeout` to 2000ms so users fail faster with a clean error
instead of waiting.
Why It Matters

The Prisma error code P2024 is documented, but understanding that it means "pool exhausted" and connecting that to Cloud Run's horizontal scaling behavior requires combining knowledge from three different domains: Prisma internals, Cloud Run's concurrency model, and PostgreSQL connection limits. Gemini holds all three simultaneously and diagnoses in seconds what would take a senior engineer 20 minutes to piece together at 3am.

Knowledge Check

1. What is the primary benefit of a multi-stage Dockerfile for a Node.js TypeScript service?

A
It allows running multiple services (database + app) in a single container
B
The builder stage compiles TypeScript; the runner stage copies only compiled output — removing the TypeScript compiler, devDependencies, and source files from the production image, reducing size by 70–85%
C
It enables running the same container on Windows and Linux without modification
D
It speeds up build time by skipping dependency installation on repeat builds

2. Why does the generated CI workflow tag Docker images with :${{ github.sha }} instead of just :latest?

A
Because Cloud Run does not support the :latest tag
B
To avoid caching issues in the GitHub Actions environment
C
SHA tags are immutable — rolling back to a specific SHA guarantees you get the exact build from that commit, while :latest is mutable and could point to a different image by the time a rollback is needed
D
SHA tags compress better in Artifact Registry, reducing storage costs

3. What is OIDC authentication in GitHub Actions and why is it preferable to storing a GCP service account JSON key as a secret?

A
OIDC is faster than JSON key authentication at runtime
B
OIDC tokens are short-lived and scoped to the specific job — if a token is leaked it expires in minutes. A JSON key never expires unless manually rotated, making it a permanent credential if stolen.
C
OIDC does not require any setup in Google Cloud
D
JSON keys are deprecated by GitHub Actions and no longer supported

4. The log analysis shows Prisma error P2024. What is the root cause and the correct immediate fix?

A
A database credential rotation — restart Cloud Run with new DATABASE_URL
B
A memory leak — scale up container memory to 2Gi
C
Connection pool exhaustion — the pool limit of 5 is too small for the concurrency level. Immediate fix: increase connection_limit in the DATABASE_URL query string and redeploy
D
The database server is down — restore from latest backup

5. Why should the .env.example file be committed to git, while .env must not be?

A
Because .env files are too large to store in git
B
.env.example contains only variable names with safe placeholder values — it's documentation. .env contains real secrets that would be permanently exposed in git history if committed, even if later deleted.
C
Node.js only reads .env.example in production; .env is for local development only
D
GitHub Actions cannot read .env files, only .env.example

6. When Gemini audits package.json for dependency vulnerabilities, what additional capability does enabling web search provide?

A
It can run npm install to verify packages install correctly
B
It can read the full source code of each dependency to find hidden bugs
C
It can fetch current versions and CVE records from npm and vulnerability databases rather than relying on training data that may be months out of date
D
It automatically creates pull requests in your GitHub repository to apply the upgrades
