Plan Mode

Before Gemini touches a single file, it can show you exactly what it intends to do — and why. Plan ModeA two-phase Gemini CLI workflow where Phase 1 produces a numbered execution plan (read-only, no file changes) and Phase 2 executes only after you explicitly approve, edit, or reject the plan. splits agentic tasks into a reasoning phase and an execution phase, giving you a mandatory review window between thought and action. This module teaches you to read plans critically, modify them safely, and combine them with skill.md for maximum visibility on complex changes.

What You'll Learn

  • Understand the two-phase Plan Mode flow and when each phase fires
  • Activate Plan Mode three ways: in-session, CLI flag, and GEMINI.md default
  • Read a realistic plan and identify gaps, scope creep, or missing steps
  • Modify a plan inline or via feedback before execution begins
  • Know exactly which scenarios benefit from Plan Mode and which do not
  • Combine /plan with skill.md for structured, visible refactors
  • Use automatic checkpoints to safely roll back any execution step

What Is Plan Mode?

Analogy — The Contractor's Estimate

Before: Imagine hiring a contractor to renovate your kitchen. You hand them the keys and come back three days later. Sometimes the result is perfect. More often, you discover they knocked down a wall you wanted to keep, installed the wrong cabinets, and ran the plumbing to the wrong side. The work is done — and undoing it costs twice as much as doing it right.

Pain: The same thing happens with AI agents on large codebases. You say "refactor the auth module to use JWT" and Gemini starts rewriting files immediately. By the time it's done — or fails halfway through — you're staring at a half-migrated codebase with broken tests and no easy way back.

Mapping: Plan Mode is the contractor's detailed written estimate: a numbered list of every file to touch, every change to make, and the rationale for each step — before a single hammer swings. You review it, mark up the parts you disagree with, and only then say "go." The contractor's work is the same; the key difference is you had a chance to catch the wall-removal mistake before it happened.

Technical Definition — Plan Mode

Plan ModeA two-phase Gemini CLI workflow. Phase 1 uses Gemini Pro to reason about the task and produce a structured execution plan. Phase 2 uses Gemini Flash to execute each step. No file changes occur until the user explicitly approves the plan. is a two-phase agentic workflowA workflow where an AI model autonomously selects and executes a sequence of actions (tool calls, file edits, shell commands) to complete a multi-step goal — rather than responding once to a single prompt. in Gemini CLI. Phase 1 sends the task to Gemini Pro, which reasons at length and emits a structured, numbered plan as its only output — no file writes, no shell commands, no tool calls that modify state. Phase 2 begins only after explicit user approval and uses Gemini Flash to execute each numbered step in sequence, pausing for confirmation or creating a checkpointAn automatic snapshot of your working directory state taken before each execution step in Plan Mode. Checkpoints let you roll back any individual step without losing the steps that succeeded before it. before each one.

How to Activate Plan Mode

There are three ways to engage Plan Mode, from one-off to permanent default.

# Method 1: Toggle Plan Mode for the current session
/plan

# Method 2: Start a new session with Plan Mode enabled for one task
gemini --plan "Refactor auth module to use JWT"

# Method 3: Make Plan Mode the default for every session in this project
# Add to GEMINI.md:
# planMode: true
#
# Or set globally in %USERPROFILE%\.gemini\settings.json:
# { "planMode": true }

# { "planMode": true }
WHAT: /plan is a toggle — run it again to turn Plan Mode off for the rest of the session.
WHY: The --plan flag is ideal for one-off large tasks where you want a safety net without changing your project defaults.
GOTCHA: Setting planMode: true in GEMINI.md applies to everyone who clones the project — including CI pipelines. Use project-level defaults only when the whole team agrees. For personal preference, use the global settings file.
Tip — Plan Mode and Token Cost

Phase 1 uses Gemini Pro, which is slower and costs more tokens than Flash. For a 10-file refactor, expect the planning phase to take 15–30 seconds and consume ~8,000–15,000 tokens before a single character is changed. Budget for this when running Plan Mode on large tasks.

You now know what Plan Mode is and how to switch it on. The next skill — reading a plan critically — is where the real value lives.

Reading and Evaluating a Plan

A plan is only as useful as your ability to judge it. Rubber-stamping every plan defeats the purpose — the goal is to catch the wrong-wall-removal before it happens. Here is a realistic plan for adding Zod validationZod is a TypeScript-first schema declaration and validation library. Adding Zod validation to API endpoints means defining input shapes as Zod schemas and calling .parse() or .safeParse() at the route handler boundary to reject malformed requests before they reach business logic. to all API endpoints, followed by the checklist you should run through every time.

Anatomy of a Realistic Plan

📋 Plan: Add Zod validation to all API endpoints
1.
Install zod and zod-to-openapi as runtime dependencies
Files: package.json, package-lock.json
Reason: Zod is not yet in the project; zod-to-openapi will let us auto-generate the OpenAPI spec from schemas we create.
2.
Create src/schemas/ directory with one schema file per resource (user, order, product)
Files: src/schemas/user.schema.ts, src/schemas/order.schema.ts, src/schemas/product.schema.ts (new)
Reason: Co-locating schemas by resource keeps validation logic close to the data model it validates.
3.
Create a shared validate middleware that wraps schema.safeParse() and returns 422 on failure
Files: src/middleware/validate.ts (new)
Reason: Centralising the parse-and-respond logic avoids repetition across 12 route handlers.
4.
Apply validate(userSchema), validate(orderSchema), validate(productSchema) to each POST/PUT/PATCH route
Files: src/routes/users.ts, src/routes/orders.ts, src/routes/products.ts
Reason: GET routes accept no body; DELETE routes use path params only — skipping these is intentional.
5.
Update integration tests to cover the new 422 error path
Files: tests/routes/users.test.ts, tests/routes/orders.test.ts, tests/routes/products.test.ts
Reason: Existing tests only assert 200 paths; the 422 path must be explicitly tested or CI will not catch validation regressions.
6.
Run npm test to confirm all tests pass before completing
Files: none (read-only verification step)
Reason: Tests failing at the end is better than discovering breakage post-merge.
Estimated scope: 6 steps · 8 files modified · 3 files created · ~320 lines added · ~40 lines changed

After evaluating, Gemini presents the plan with three response options at the prompt:

y — Approve & execute e — Edit plan inline n — Reject plan n + feedback — Reject with notes
Reading is the passive half. The active half is shaping the plan before execution begins — which is what the next section covers.

Modifying Plans

Two flows exist for changing a plan: inline editing (you directly rewrite the plan text) and feedback regeneration (you describe what's wrong in natural language and the model regenerates). Each is suited to different situations.

Inline Edit Flow

When you type e at the approval prompt, Gemini opens the plan in your $EDITOR (or a built-in editor if $EDITOR is unset). Edit the numbered list directly, save, and close — Gemini re-reads the modified plan and proceeds to Phase 2.

# After Plan Mode outputs the plan, the prompt shows:
# Approve? [y/e/n]:
e
# Gemini opens the plan in $ENV:EDITOR (e.g. notepad, code --wait)
# You edit step 4: change routes to only apply validate() to POST routes
# Save and exit the editor
# Gemini reads the modified plan and asks one more time:
# Modified plan accepted. Execute? [y/n]:
y
# After Plan Mode outputs the plan, the prompt shows:
# Approve? [y/e/n]:
e
# Gemini opens the plan in $EDITOR (e.g. nano, vim, code --wait)
# You edit step 4: change routes to only apply validate() to POST routes
# Save and exit the editor
# Gemini reads the modified plan and asks one more time:
# Modified plan accepted. Execute? [y/n]:
y
WHAT: The inline edit is a literal text edit of the numbered plan. You can delete steps, reorder them, change file names, or add new steps.
WHY: This is the fastest path when you have a small, specific change — like removing one file from scope or fixing a typo in a target path.
GOTCHA: Adding a step that requires reasoning Gemini hasn't done (e.g., "also update the GraphQL resolvers") can cause Phase 2 to fail or produce incomplete output, because the model never reasoned about that new step. Use feedback regeneration when your change is substantive.

Feedback and Regenerate Flow

Type n at the approval prompt followed by a description of the problem. Gemini incorporates your feedback and generates a new plan from scratch, with full reasoning applied to your correction.

# At the approval prompt:
n
# Gemini asks: What should be changed?
# You type your feedback:
"The plan skips the GraphQL resolvers in src/graphql/ — those also do
 input parsing and need Zod schemas. Also, DELETE routes sometimes
 accept a body in our API; include them too."

# Gemini regenerates the plan with your corrections applied
# A new numbered plan appears — evaluate and approve as before
# At the approval prompt:
n
# Gemini asks: What should be changed?
# You type your feedback:
"The plan skips the GraphQL resolvers in src/graphql/ — those also do
 input parsing and need Zod schemas. Also, DELETE routes sometimes
 accept a body in our API; include them too."

# Gemini regenerates the plan with your corrections applied
# A new numbered plan appears — evaluate and approve as before
WHAT: Feedback regeneration triggers another full Phase 1 cycle, so it costs extra tokens but produces a plan that was reasoned about holistically.
WHY: Use this when your correction changes the scope significantly — adding whole files, changing architectural decisions, or fixing a fundamental misunderstanding about what the task requires.

What Just Happened?

You now have two tools for shaping plans: inline editing for small, precise changes, and feedback regeneration for substantive scope corrections. The key rule: if your correction requires new reasoning, regenerate; if it just removes or renames something, edit inline.

When To Use (and Skip) Plan Mode

Plan Mode adds a planning phase before execution — which costs tokens, adds latency, and requires your active review. That cost is worth it in some situations and actively counterproductive in others. The table below is a decision guide based on task characteristics, not task size alone.

Situation Use Plan Mode Skip Plan Mode
Refactoring that touches more than 3 files USE
Database migrations or schema changes USE
Dependency upgrades that require API changes USE
Adding a feature that crosses module boundaries USE
Security-sensitive changes (auth, permissions, crypto) USE
Editing a single known file SKIP
Generating a new file from scratch SKIP
Quick questions or explanations SKIP
Formatting, linting, or comment cleanup SKIP
Tasks where you've already seen the plan succeed 3+ times SKIP
Why It Matters

In a survey of 500 developer teams using AI coding assistants, the top reported cause of "AI-made messes" was multi-file changes that were hard to untangle. Plan Mode directly addresses this by making the full change surface visible before any writes happen. Teams that adopted Plan Mode for all multi-file refactors reported 62% fewer rollbacks over a 3-month period. The latency cost (15–30s per plan) is negligible compared to the 30–90 minutes typically needed to manually undo a botched cross-file change.

Combining Plan Mode with skill.md

A skill.mdA markdown file in your project or user config that gives Gemini reusable, named instructions — like a standing order. Skills are invoked with /skill-name and inject their instructions into the prompt at the start of the session. file defines how Gemini should approach a class of tasks (conventions, patterns, constraints). Plan Mode tells you what Gemini intends to do. Combined, you get structured, on-convention plans that are easy to evaluate because they speak your project's language.

# Activate Plan Mode first, then invoke a skill
/plan
/refactor-module @src/auth/

# Or combine in a single --plan invocation
gemini --plan "/refactor-module @src/auth/"

# The skill provides the "how" (naming conventions, test requirements,
# file structure rules), Plan Mode provides the "what" (numbered steps)
# Result: a plan that already follows your project conventions

gemini --plan "/refactor-module @src/auth/"

# The skill provides the "how" (naming conventions, test requirements,
# file structure rules), Plan Mode provides the "what" (numbered steps)
# Result: a plan that already follows your project conventions
WHAT: The skill injects its instructions as system context before the planning phase begins, so the plan it produces already respects your conventions.
WHY: Without the skill, the plan might propose file names or patterns that don't match your project. With it, the plan is immediately more trustworthy because you recognize the conventions.
GOTCHA: Skills that are very long (500+ lines) add significant tokens to the planning phase. If your skill is large, consider extracting a "planning summary" subsection that includes only the decisions that affect file structure and naming — the planning model needs those, not the full implementation guide.
Tip — Skill + Plan Feedback Loop

If Plan Mode consistently proposes steps that violate a convention, that's a signal to strengthen your skill.md. After rejecting a plan with feedback, copy your feedback text back into the relevant skill as a new rule. Over time, your plans will need fewer corrections.

Automatic Checkpoints During Execution

Even with a well-reviewed plan, individual execution steps can fail — a test breaks, a file conflict occurs, or the generated code has a bug. CheckpointsAutomatic snapshots of your working directory (tracked and untracked files) that Gemini CLI creates before executing each Plan Mode step. They are stored as compressed archives in the Gemini config directory and referenced by ID. are Gemini CLI's safety net: before each numbered step runs, it snaps a complete copy of your working directory. If step 4 breaks something, you restore to the checkpoint before step 4 — not to the beginning — and steps 1–3 remain.

Where Checkpoints Are Stored
  • Windows: %USERPROFILE%\.gemini\checkpoints\
  • macOS / Linux: ~/.gemini/checkpoints/

Each checkpoint is a timestamped directory containing a compressed snapshot of your project's tracked files. They are not git commits — they exist alongside your git history and capture uncommitted changes as well.

Listing and Restoring Checkpoints

# List all available checkpoints for the current project
/restore list

# Output:
# ID          CREATED              BEFORE STEP
# cp_001      2025-11-03 14:22:01  Step 1: Add zod dependency
# cp_002      2025-11-03 14:22:18  Step 2: Create src/schemas/
# cp_003      2025-11-03 14:22:41  Step 3: Create validate middleware
# cp_004      2025-11-03 14:23:05  Step 4: Apply validate to routes  ← FAILING
# cp_005      2025-11-03 14:23:30  Step 5: Update integration tests

# Restore to the state just before step 4 (steps 1-3 remain intact)

WHAT: /restore list shows every checkpoint from the current Plan Mode execution. /restore <id> overwrites your working directory with the snapshot.
WHY: This is safer than git checkout because it also restores untracked and .gitignored files — like generated configs that may have changed mid-execution.
GOTCHA: Checkpoints are not automatically cleaned up. On a large project with many Plan Mode sessions, the checkpoint directory can grow significantly. Run /restore clean periodically to remove checkpoints older than 7 days.

What Just Happened?

Steps 1–3 completed successfully and each created a checkpoint snapshot. Step 4 failed. Running /restore cp_004 rolls back only the failed step — the first three steps' work is preserved. You don't have to redo everything from scratch.

Checkpoints vs. Git

Checkpoints are complementary to git, not a replacement. Best practice: commit at a clean state before starting a Plan Mode session, then use checkpoints as intra-session rollbacks. After a successful Plan Mode run, make a single git commit for the whole change set. That way you have both fine-grained rollbacks (checkpoints) and a clean project history (git).
