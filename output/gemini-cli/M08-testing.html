AI-Assisted Testing

Writing tests is the part of the SDLC developers skip most often — not because it's hard, but because it's slow. This module shows you how to use Gemini CLI to generate comprehensive test suites in seconds, find the coverage gaps you'd miss at 5pm on Friday, diagnose failing tests with surgical precision, and practice real TDD where Gemini writes the tests first and you write the implementation.

What You'll Learn

  • Generate complete Vitest unit test files with AAA pattern, happy paths, edge cases, and error conditions
  • Ask Gemini to identify edge cases you missed after reviewing an existing test file
  • Paste a failing test output and get a root-cause diagnosis plus a targeted fix
  • Scan an entire src/ + tests/ directory for coverage gaps, ranked by severity
  • Generate Playwright and Supertest integration tests from your actual source code
  • Run the full TDD red–green–refactor loop with Gemini writing tests before you write code

Generating Unit Tests from Source

Analogy — The QA Partner Who Read Your Code

Imagine pairing with a QA engineer who has already read every line of your service file before the sprint planning meeting. They don't ask "what does this method do?" — they hand you a list of test cases covering the happy path, three null-input variants, a concurrency edge case, and the error thrown by the database library you're using.

The pain without AI: you write tests from memory, miss the edge cases you didn't think of while implementing, and find out about them in production. The mapping: Gemini has read task.service.ts via @src/services/task.service.ts — it knows your method signatures, return types, dependencies, and the errors each dependency can throw. The test file it generates is based on your actual code, not a hypothetical.

Technical Definition — Arrange-Act-Assert (AAA)

The AAA patternA test structure where each test is split into three phases: Arrange (set up the system under test and its dependencies), Act (call the code being tested), and Assert (verify the output or side effect). AAA tests are easier to read because the intent is immediately clear from the structure. is the standard unit test structure: Arrange sets up mocks, fixtures, and preconditions; Act calls the function under test with a single input; Assert checks exactly one observable outcome. One assertion per test is the ideal — it makes failures trivially easy to diagnose.

VitestA fast unit testing framework built on top of Vite. Uses the same `describe`/`it`/`expect` API as Jest but runs tests natively in ESM with zero config. Supports mocking (`vi.fn()`, `vi.mock()`), coverage via V8 or Istanbul, and TypeScript out of the box. is the test runner used in this module — it's Jest-compatible but faster and natively TypeScript-aware. The same prompts work for Jest by substituting jest.fn() for vi.fn().

The Prompt + Full Output

Give Gemini the service file and a clear instruction about the test framework and patterns you want:

Gemini CLI prompt
@src/services/task.service.ts Generate comprehensive unit tests using Vitest.
Cover happy paths, edge cases, and error conditions.
Use the Arrange-Act-Assert pattern. Mock all external dependencies.
Include tests for: createTask, updateTask, deleteTask, getTaskById, listTasksByUser.
WHAT: The @ mention injects the entire service file so Gemini sees your real method signatures, TypeScript types, and injected dependencies.
WHY: Without the source file, Gemini invents method signatures. With it, the generated tests import the real types, call methods with the real parameter shapes, and mock the real database client.
GOTCHA: Gemini may import from paths that don't match your project structure. Always check that import paths in the generated file resolve correctly before running vitest.

What Just Happened?

Gemini injected the full task.service.ts source, inferred the dependency injection pattern (Prisma client passed to constructor), generated a vi.mock() at the module boundary, and produced one describe block per method with multiple it cases each covering a different scenario. The AAA comments are explicit — each test is a specification, not just a passing assertion.

Why It Matters

Teams using AI-generated test scaffolding report 3–5x faster time-to-first-green for new services. The value isn't the generated test itself — it's the conversation it starts. Running the file immediately surfaces method signatures that need tightening, exception types that aren't exported, and dependencies that aren't injectable.

You have a test file. Now let's find the cases that aren't in it yet.

Finding Edge Cases You Missed

Analogy — The Second Pair of Eyes

After you write code for hours, you develop a mental model of the happy path so strong that you literally cannot see the edge cases anymore. Your brain auto-completes the "title is always a string" assumption and you forget to test undefined, '', a 10,000-character string, or a SQL injection payload.

The pain: edge-case bugs reach production because reviewers also have the happy-path bias by the time the PR lands. The mapping: Gemini has no mental model of your system — it reasons about code categorically, not experientially. It will notice the null-input gap because it has seen thousands of null-dereference bugs in its training data.

What Gemini Flags

Tests are written. Now they're failing. Let's diagnose them.

Diagnosing Failing Tests

Analogy — The Stack Trace Translator

A failing test output is like an error message in a foreign language: it contains the truth, but you can't read it quickly. The file name, the assertion message, the diff between expected and received — together they point to a root cause, but finding it requires switching between the test file, the source file, and the mock setup simultaneously.

The pain: 20-minute debugging sessions for 2-minute bugs because you're context-switching between too many files at once. The mapping: Gemini receives the test output and the source file simultaneously — it can cross-reference the assertion diff against the implementation in one step.

The Diagnosis Prompt

Paste the raw test runner output, then combine it with the source file:

Gemini CLI prompt — failing test diagnosis
"""
FAIL src/services/task.service.test.ts
  TaskService > deleteTask > throws ForbiddenException when non-owner tries to delete

  AssertionError: expected function to throw ForbiddenException but received Error: Not authorized

  - Expected: ForbiddenException
  + Received: Error

  ❯ TaskService.deleteTask src/services/task.service.ts:87
  ❯ src/services/task.service.test.ts:112
"""
@src/services/task.service.ts The above test is failing.
Diagnose the root cause and provide the exact fix.
WHAT: The triple-quote block pastes the raw Vitest failure output; the @ mention gives Gemini the source so it can see the implementation at line 87.
WHY: The test assertion expects ForbiddenException but the service throws a generic Error. Without seeing the source, you'd need to mentally trace to line 87. Gemini sees it directly.

Gemini's structured diagnosis output:

Gemini diagnosis output
## Root Cause
The service throws `new Error('Not authorized')` at line 87 of `task.service.ts`,
but the test expects `ForbiddenException` from `../exceptions`.

The two are different classes. `ForbiddenException extends Error`, so it IS an
Error — but the reverse is not true. Your ownership check uses the wrong
exception class.

## Current Code (line 84–89)
```typescript
if (task.userId !== requestingUserId) {
  throw new Error('Not authorized');  // ← wrong class
}
```

## Fix
```typescript
import { ForbiddenException } from '../exceptions';  // ensure import exists

if (task.userId !== requestingUserId) {
  throw new ForbiddenException(
    `User ${requestingUserId} cannot delete task ${taskId}`
  );
}
```

## Why This Matters
Throwing the typed exception class lets your global error handler map it to HTTP
403 automatically. A generic `Error` would fall through to the 500 handler,
leaking internal stack traces to clients.

What Just Happened?

Gemini identified three things at once: the exact mismatched exception class, the exact line number, and the downstream consequence (wrong HTTP status code). This is the pattern to internalize: the diagnosis is always more valuable than just the fix, because it explains why the test was right to fail.

Individual tests are covered. Now let's zoom out and look at the entire codebase for structural gaps.

Analyzing Coverage Gaps Across the Codebase

Unit tests tell you if individual functions work. Coverage analysis tells you which functions have no tests at all — the dark corners where bugs live longest.

Gemini CLI prompt
@src/ @tests/ Analyze test coverage gaps.
Which code paths in src/ have no corresponding tests in tests/?
List by file, include: gap description, severity (HIGH/MEDIUM/LOW), and recommended test approach.
WHAT: Both directories are injected. Gemini maps source files to test files, identifies files with no test counterpart, and identifies untested methods in partially-covered files.
GOTCHA: Gemini cannot run vitest --coverage — it analyzes structurally (file names, exports vs. tested symbols), not instrumentally. For true line coverage, run vitest run --coverage and paste the lcov summary into Gemini for prioritization advice.

Checkpoint

Use the severity table as a sprint backlog. Address HIGH items before merge, MEDIUM items in the following sprint, and LOW items opportunistically. The auth.ts gap is almost always the most dangerous — authentication logic with no tests is an incident waiting to happen.

Unit tests cover the service layer. Now let's test the full HTTP surface with integration tests.

E2E and Integration Tests

Unit tests mock everything. Integration testsTests that exercise multiple layers of the application together — for example, an HTTP request that hits a real route handler, which calls a real service, which talks to a test database. They're slower than unit tests but catch wiring errors that mocks cannot detect. exercise the real HTTP layer, real routing, real middleware — only the external database is swapped for a test instance. SupertestAn npm package that wraps your Express/Fastify/Koa app in a test HTTP client. You make real HTTP requests (GET, POST, etc.) in your tests without starting a server on a port — the requests go directly through the app's request handler. does this for Express/Fastify APIs.

Gemini CLI prompt
@src/routes/tasks.ts @src/app.ts @src/middleware/auth.ts
Generate Supertest integration tests for all task routes.
Cover: auth failure (401), forbidden (403), success (200/201), and validation errors (400).
Use a test Prisma client pointing to DATABASE_URL_TEST.

import { app } from '../../src/app';
import { prisma } from '../../src/lib/prisma';
import { generateToken } from '../../src/utils/auth';
import { describe, it, expect, beforeAll, afterAll, beforeEach } from 'vitest';

// ---- Test setup ----
let ownerToken: string;
let otherToken: string;
let taskId: string;

beforeAll(async () => {
  // Seed two users in the test DB
  const owner = await prisma.user.create({
    data: { email: 'owner@test.com', password: 'hashed' },
  });
  const other = await prisma.user.create({
    data: { email: 'other@test.com', password: 'hashed' },
  });
  ownerToken = generateToken(owner.id);
  otherToken = generateToken(other.id);
});

  // Clean up test data
  await prisma.task.deleteMany();
  await prisma.user.deleteMany({ where: { email: { contains: '@test.com' } } });
  await prisma.$disconnect();
});

// ===== POST /tasks =====
describe('POST /tasks', () => {
  it('201 — creates task with valid body and auth', async () => {
    const res = await request(app)
      .post('/tasks')
      .set('Authorization', `Bearer ${ownerToken}`)
      .send({ title: 'Integration test task', priority: 'HIGH' });

    expect(res.status).toBe(201);
    expect(res.body.id).toBeDefined();
    expect(res.body.title).toBe('Integration test task');
    taskId = res.body.id; // save for subsequent tests
  });

  it('400 — returns validation error when title is missing', async () => {
    const res = await request(app)
      .post('/tasks')
      .set('Authorization', `Bearer ${ownerToken}`)
      .send({ priority: 'HIGH' }); // no title

    expect(res.status).toBe(400);
    expect(res.body.error).toMatch(/title/i);
  });

  it('401 — rejects request with no token', async () => {
    const res = await request(app)
      .post('/tasks')
      .send({ title: 'Ghost task' });

    expect(res.status).toBe(401);
  });

  it('401 — rejects request with expired token', async () => {
    const expiredToken = 'eyJhbGciOiJIUzI1NiJ9.expired.signature';
    const res = await request(app)
      .post('/tasks')
      .set('Authorization', `Bearer ${expiredToken}`)
      .send({ title: 'Ghost' });

    expect(res.status).toBe(401);
  });
});

// ===== GET /tasks/:id =====
describe('GET /tasks/:id', () => {
  it('200 — owner can read their own task', async () => {
    const res = await request(app)
      .get(`/tasks/${taskId}`)
      .set('Authorization', `Bearer ${ownerToken}`);

    expect(res.status).toBe(200);
    expect(res.body.id).toBe(taskId);
  });

  it('403 — other user cannot read another user's task', async () => {
    const res = await request(app)
      .get(`/tasks/${taskId}`)
      .set('Authorization', `Bearer ${otherToken}`);

    expect(res.status).toBe(403);
  });

  it('404 — returns 404 for nonexistent task', async () => {
    const res = await request(app)
      .get('/tasks/nonexistent-uuid')
      .set('Authorization', `Bearer ${ownerToken}`);

    expect(res.status).toBe(404);
  });
});

// ===== DELETE /tasks/:id =====
describe('DELETE /tasks/:id', () => {
  it('403 — other user cannot delete owner's task', async () => {
    const res = await request(app)
      .delete(`/tasks/${taskId}`)
      .set('Authorization', `Bearer ${otherToken}`);

    expect(res.status).toBe(403);
  });

  it('204 — owner can delete their own task', async () => {
    const res = await request(app)
      .delete(`/tasks/${taskId}`)
      .set('Authorization', `Bearer ${ownerToken}`);

    expect(res.status).toBe(204);

WHAT: Supertest wraps the Express app directly — no port needed. Each test sends a real HTTP request through real middleware and real route handlers.
WHY: These tests catch auth middleware bugs, route parameter parsing errors, and HTTP status code mismatches that unit tests (which mock the router) cannot detect.
GOTCHA: Integration tests require a test database. Set DATABASE_URL to a separate test DB in your CI environment, never your development DB. Use vitest --pool=forks to prevent parallel tests from sharing state.

TDD Workflow — Tests First

Analogy — The Acceptance Criteria That Run

In traditional project management, acceptance criteria are written in English and checked manually. TDD converts those criteria into executable code — the test is the acceptance criteria, and the bar is green when you're done. You don't build until the tests define what "done" means.

The pain without TDD: you implement, then test, and the tests become documentation of what the code does rather than what it should do — which is backwards. The mapping: Gemini writes tests from your feature description before any implementation exists, giving you a precise contract to code against.

Step 1 — Write the tests first:

Gemini CLI prompt — TDD step 1
I need to implement a `RateLimiter` class with these requirements:
- Takes `maxRequests` (number) and `windowMs` (milliseconds) in constructor
- `check(userId: string): boolean` — returns true if under limit, false if over
- `reset(userId: string): void` — clears the user's request count

Gemini outputs a complete test file for an implementation that doesn't exist yet. Then you create src/utils/rate-limiter.ts and make the tests pass:

Generated: tests/unit/rate-limiter.test.ts (tests before implementation)
import { describe, it, expect, vi, beforeEach, afterEach } from 'vitest';
import { RateLimiter } from '../../src/utils/rate-limiter';

describe('RateLimiter', () => {
  beforeEach(() => {
    vi.useFakeTimers();
  });
  afterEach(() => {
    vi.useRealTimers();
  });

  it('allows first request for a new user', () => {
    const limiter = new RateLimiter(5, 60_000);
    expect(limiter.check('user-1')).toBe(true);
  });

  it('allows requests up to the limit', () => {
    const limiter = new RateLimiter(3, 60_000);
    expect(limiter.check('user-1')).toBe(true);
    expect(limiter.check('user-1')).toBe(true);
    expect(limiter.check('user-1')).toBe(true);
  });

  it('blocks the request that exceeds the limit', () => {
    const limiter = new RateLimiter(3, 60_000);
    limiter.check('user-1');
    limiter.check('user-1');
    limiter.check('user-1');
    expect(limiter.check('user-1')).toBe(false); // 4th request blocked
  });

  it('tracks limits independently per user', () => {
    const limiter = new RateLimiter(2, 60_000);
    limiter.check('user-a');
    limiter.check('user-a');
    // user-a is at limit, user-b is not
    expect(limiter.check('user-a')).toBe(false);
    expect(limiter.check('user-b')).toBe(true);
  });

  it('resets window after windowMs elapses', () => {
    const limiter = new RateLimiter(2, 1000);
    limiter.check('user-1');
    limiter.check('user-1');
    expect(limiter.check('user-1')).toBe(false); // blocked

    vi.advanceTimersByTime(1001); // advance past window

    expect(limiter.check('user-1')).toBe(true); // allowed again
  });

  it('reset() clears the user count immediately', () => {
    const limiter = new RateLimiter(2, 60_000);
    limiter.check('user-1');
    limiter.check('user-1');
    limiter.reset('user-1');
    expect(limiter.check('user-1')).toBe(true);
  });
});

Why It Matters

TDD with Gemini creates a design pressure feedback loop: if the tests are hard to write, the API is hard to use. Teams using this pattern consistently find that their function signatures improve — fewer optional parameters, clearer error contracts, more explicit return types — because the tests expose design problems before implementation calcifies them.
