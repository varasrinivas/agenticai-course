From Script to Agent — The Problem Agents Solve

Before we explore ReAct and design patterns, let's see the exact problem that agents solve. We'll take a real task from Domain C (UCC public records): "Find the total lien exposure for Acme Corporation." This single question requires searching name variations, checking multiple states, filtering terminated filings, deduplicating, and summarizing. Here are two approaches side by side.

Approach A: Traditional Python Script

# script_approach.py — The traditional way
import json

def find_lien_exposure(company_name):
    # Step 1: Hardcoded name variations — YOU must think of every variant
    name_variants = [
        company_name,
        company_name.upper(),
        company_name.replace("Corporation", "Corp"),
        company_name.replace("Corporation", "Corp."),
        company_name.replace("Corporation", "Corporation Inc"),
    ]

    # Step 2: Hardcoded state list — YOU must know which states matter
    states = ["NY", "CA", "TX", "FL", "IL", "DE"]

    # Step 3: Rigid loop — searches everything, reasons about nothing
    all_filings = []
    for state in states:
        for name in name_variants:
            results = search_database(name, state)
            all_filings.extend(results)

    # Step 4: Hardcoded filter — YOU define what "active" means
    active_filings = [
        f for f in all_filings
        if f["status"] == "ACTIVE"
        and f["lapse_date"] > today()
    ]

    # Step 5: Deduplication — YOU handle every edge case
    seen_ids = set()
    unique_filings = []
    for f in active_filings:
        if f["filing_number"] not in seen_ids:
            seen_ids.add(f["filing_number"])
            unique_filings.append(f)

    # Step 6: Rigid report format
    total_count = len(unique_filings)
    states_found = set(f["state"] for f in unique_filings)
    return {
        "company": company_name,
        "total_active_filings": total_count,
        "states": list(states_found),
        "filings": unique_filings
    }
# PROBLEMS: misses "ACME CORP DBA ROADRUNNER SUPPLIES",
# misses filings in OH/PA/GA, can't adapt to follow-ups,
# every new edge case = code change + redeploy

Approach B: Agent with Claude

# agent_approach.py — The agent way
import anthropic, json

client = anthropic.Anthropic()
tools = [
    {"name": "search_filings",
     "description": "Search UCC filings by debtor name in a specific state",
     "input_schema": {"type": "object",
        "properties": {"debtor_name": {"type": "string"}, "state": {"type": "string"}},
        "required": ["debtor_name"]}},
    {"name": "get_filing_details",
     "description": "Get full details for a specific filing",
     "input_schema": {"type": "object",
        "properties": {"filing_number": {"type": "string"}},
        "required": ["filing_number"]}}
]

def find_lien_exposure(question):
    messages = [{"role": "user", "content": question}]
    while True:
        response = client.messages.create(
            model="claude-sonnet-4-20250514", max_tokens=4096,
            system="You are a UCC filing research agent. Search thoroughly.",
            tools=tools, messages=messages
        )
        if response.stop_reason == "end_turn":
            return response.content[0].text  # Final answer

            if block.type == "tool_use":
                result = execute_tool(block.name, block.input)
                messages.append({"role": "assistant", "content": response.content})
                messages.append({"role": "user", "content": [
                    {"type": "tool_result", "tool_use_id": block.id,

                ]})

When Scripts Are Better

Agents are not always the answer. Scripts win when the task needs no reasoning:

  1. File format conversion (CSV → JSON) — 100% deterministic, zero ambiguity
  2. Data validation against a fixed schema — the rules never change
  3. Batch record insertion — speed matters more than flexibility (scripts are 100x faster)
  4. Cron jobs with fixed logic — same input = same output, every time
  5. Simple CRUD operations — adding an LLM adds cost with zero benefit
Key Insight

An agent is a script that replaced the hardcoded decision logic with an LLM. Instead of you writing every if/else and every loop condition, Claude reasons about what to do next. Your code provides the tools (what the agent can do). Claude provides the logic (what the agent should do). The tool-use loop you wrote (15 lines) replaces hundreds of lines of decision logic — but you still write the tools. The agent does not magically connect to databases or APIs. You provide the hands. Claude provides the brain.

Five Anti-Patterns to Avoid

Knowing what not to do is as important as knowing the patterns themselves. These are the five most common mistakes teams make when building agent architectures — each one wastes money, time, or both.

  • ❌ Over-Engineering: Multi-Agent When Single Agent Suffices
    Building a Supervisor + 3 Workers system when a single agent with 3-4 tools would handle the job. More agents means more API calls, more coordination overhead, and more failure modes.
    ✅ Fix: Start with the simplest pattern that works. Upgrade to multi-agent only when a single agent's context window or tool count becomes a bottleneck.
  • ❌ ReAct Without Max Iterations (Infinite Loop)
    Running a ReAct loop with no iteration cap. A confused agent will call the same tool repeatedly with identical parameters, burning tokens and money until your API budget is exhausted.
    ✅ Fix: Always set max_iterations (typically 5-15). Add a token budget cap as a second safety net. Log iteration counts to detect patterns.
  • ❌ Plan-then-Execute for Exploratory Tasks
    Using Plan-Execute when you don't know the steps yet. The plan will be wrong, the agent will follow it rigidly, and you'll get garbage results from a confidently-executed bad plan.
    ✅ Fix: If the steps depend on what you discover along the way, use ReAct (P2). Save Plan-Execute (P3) for tasks where the decomposition is clear upfront.
  • ❌ Parallel Fan-Out Without Error Handling
    Launching 50 parallel tasks and treating any single failure as a total failure. One flaky API response kills the entire batch, and you lose the results from the 49 that succeeded.
    ✅ Fix: Use Promise.allSettled() (JS) or asyncio.gather(return_exceptions=True) (Python). Collect partial results and report which tasks failed separately.
  • ❌ Pipeline Without Intermediate Validation
    Running a 4-stage pipeline where Stage 1's bad output propagates through Stages 2-4 unchecked. By the time you see the final output, the garbage has been transformed three times and is unrecognizable.
    ✅ Fix: Validate output at each stage boundary. If Stage 1 produces invalid data, stop the pipeline and report the error — don't send garbage downstream.
Rule of Thumb

When in doubt, start simple. A single ReAct agent with good tools and proper stop conditions handles 80% of real-world tasks. Only add complexity (more patterns, more agents) when you have evidence the simple approach isn't working — not because the architecture diagram looks more impressive.

What Is an Agent?

Up to this point in the course, you've used Claude in a fairly direct way: you send a message, Claude responds, maybe it calls a tool, and you get an answer. That's powerful, but it's still fundamentally you driving each step. In this module, we cross a major threshold — we hand the steering wheel to Claude and let it decide what to do, when to do it, and when it's done.

Everyday Analogy

Before agents: Imagine interacting with a vending machine. You press a button (send a message), the machine drops a snack (sends a response), and the transaction is done. You can't say "I want something healthy under 200 calories" — you pick from fixed options. That's how a chatbot works: one input, one output, done.

The pain: Real tasks aren't one-step. "Book me a flight to Tokyo under $800" requires searching multiple airlines, comparing dates, checking your calendar, maybe adjusting dates to find a better price. No single API call answers that — it takes a sequence of decisions based on intermediate results.

The mapping: An agent is like a personal assistant. You state a goal — "find me flights to Tokyo under $800" — and the assistant figures out the steps: search flights, check your calendar, compare options, maybe search again with different dates. They use tools (airline websites, your calendar), adapt their plan based on what they find, and report back when they're done or stuck. That's an AI agent: a system where Claude operates in a loop, choosing actions and reacting to results until the goal is met.

Technical Definition

An AI agentA system where an LLM operates in an autonomous loop — reasoning about what to do, taking actions via tools, observing results, and iterating until a goal is achieved or a stop condition triggers. is a system where a large language model operates in a loop. In each pass through the loop, the model autonomously decides which action to take — like calling a search API or running a calculation. It then observes the result and decides what to do next. This cycle repeats until the goal is achieved or a safety condition stops the loop.

The key word is autonomously. Unlike single-turn chat (you ask, Claude answers) or even multi-turn chat (you go back and forth), an agent runs multiple iterations without you prompting each one. Your code calls Claude, Claude says "I need to call this tool," your code executes the tool, sends the result back to Claude, and Claude decides what to do next — all inside a loop that your code orchestrates.

How is this different from the tool-use loop you built in M05-M06? In those modules, you defined the workflow. In an agent, Claude decides the workflow. It chooses which tools to call, in what order, with what parameters, based on what it learns at each step. Your code provides the tools and the loop — Claude provides the brains.

Why It Matters

The shift from chatbot to agent is the shift from "answer this question" to "achieve this goal." A customer support chatbot can answer "what's your return policy?" — but an agent can process the return: look up the order, check eligibility, generate a shipping label, and email it to the customer. Common Misconceptions

"An agent is just a chatbot with tools, right?" — Not quite. A chatbot with tools still needs you to drive each step. An agent drives itself. The defining feature is the autonomous loop: Claude decides what to do next without waiting for you to ask another question.

"Agents are always better than chatbots?" — No. Agents are more powerful but also more expensive (multiple API calls), slower (sequential tool calls), and harder to control. If a single Claude call answers the question, don't wrap it in an agent loop. Use agents when the task genuinely requires multiple steps with intermediate decisions.

"The agent is the LLM itself?" — The agent is the system, not just the model. It includes your code (the loop, tool definitions, stop conditions), the LLM (Claude, providing the reasoning), and the tools (functions Claude can call). Claude is the brain; your code is the body.

Now you understand the fundamental difference between chatbots and agents. The natural next question is: what does the agent's decision-making process actually look like step by step? That's the ReAct pattern — a structured way for Claude to think, act, and learn from results in a loop.

The ReAct Loop: Reason, Act, Observe

Everyday Analogy

Before ReAct: Imagine a detective who just charges ahead — they grab the first suspect they see, skip examining the crime scene, and don't bother interviewing witnesses. They might solve easy cases by luck, but complex ones? They'll miss critical evidence and follow dead ends for hours.

The pain: Early AI agents had this exact problem. "Action-only" agents would call tools without explaining why. They'd search for the wrong thing, get bad results, and not know how to recover. You couldn't tell why they made a mistake because there was no reasoning to inspect.

The mapping: The ReAct pattern is like a methodical detective. Before following any lead, they stop and Reason: "Based on the fingerprints and the broken window, I should check the neighbor's alibi." Then they Act: interview the neighbor. Then they Observe: "The neighbor was at work — their alibi checks out. So the intruder came from somewhere else." With this new information, they reason again and choose a different lead. This think-then-act-then-learn cycle is exactly how ReAct works.

Technical Definition

ReActReasoning + Acting — a prompting framework where an LLM interleaves chain-of-thought reasoning with tool execution. Introduced by Yao et al. (2022), it outperforms both reasoning-only and action-only approaches. stands for Reasoning + Acting. It's a pattern introduced by Yao et al. in 2022 where an LLM interleaves step-by-step reasoning (chain-of-thought) with tool execution in a structured loop.

Here's how one cycle works. First, the LLM generates a Thought — it reasons about what it knows so far and what it should do next. Then it takes an Action — it calls a specific tool with specific parameters. Finally, it receives an Observation — the tool's output, which becomes new information for the next thought. This cycle repeats until the LLM has enough information to produce a Final Answer.

Why is this better than just letting the model call tools without reasoning? Research shows that ReAct outperforms both "reasoning-only" approaches (where the model just thinks but can't take actions) and "action-only" approaches (where the model calls tools without explaining why). The reasoning step catches errors before they happen, and the structured format makes the entire process auditable.

Why It Matters

ReAct isn't just an academic framework — it's how production agents work. When Claude Code helps you write code, it uses this exact pattern: it reasons about what file to edit, acts by reading or writing the file, observes the result, and decides whether to continue or ask you a question. The "thinking out loud" step is what makes the difference between an agent that stumbles through tasks and one that methodically solves them. In benchmarks, ReAct improves task success rates by 20-30% compared to action-only approaches on multi-step reasoning tasks.

Common Misconceptions

"ReAct requires a special prompting framework or library, right?" — No. Claude's Messages API naturally produces the ReAct pattern. The text blocks are Reason, tool_use blocks are Act, and tool_result messages are Observe. You just need a while loop and tool execution — no LangChain, no CrewAI, no special ReAct prompt template.

"The Reason step is optional — I can skip it to save tokens?" — Technically you can suppress reasoning with instructions like "don't explain, just act." But this defeats the purpose. Without the Reason step, Claude makes worse tool-selection decisions, you lose debuggability, and you can't audit why the agent chose a particular action. The tokens spent on reasoning are an investment in accuracy.

"More iterations = better results?" — Not necessarily. Most well-scoped tasks complete in 2-5 iterations. If your agent routinely needs 15+ iterations, the problem is likely in your tool design (too narrow), your system prompt (too vague), or the task scope (too broad for a single agent). More iterations usually means more cost and more opportunities for the agent to go off track.

Implementing ReAct with Claude's Tool Use

Everyday Analogy

Before the API: Imagine you're writing a recipe that says "taste and adjust seasoning." That's an instruction to iterate: taste the dish (observe), decide what's missing (reason), add the right spice (act), and taste again. You don't specify exactly how many times — you keep going until it tastes right.

The pain: Some frameworks force you to manually parse the model's text output to figure out if it wants to call a tool, extract the tool name and parameters from the text, and format the result. It's fragile — one extra comma breaks the parser.

The mapping: Claude's Messages API makes this effortless. When Claude wants to call a tool, it returns a structured tool_use content block with the tool name and parameters already parsed as JSON. Your code executes the tool and sends the result back as a tool_result message. This structured exchange — not string parsing — is what makes Claude's tool use reliable. The "taste and adjust" loop is just a while loop that checks stop_reason.

Technical Definition

With Claude's Messages API, the ReAct loop is implemented through a simple message exchange. First, you provide tool definitionsJSON schemas that describe the tools Claude can call — each definition includes the tool's name, description, and input parameters with types. Claude uses these to decide which tool to call and generate valid inputs. when calling the API — these tell Claude what tools are available (each tool has a name, a description, and an input schema). Claude's response then contains a mix of two types of content blocks: text blocks (its reasoning) and tool_use blocks (its actions).

Your application checks the response's stop_reasonA field in Claude's API response indicating why the model stopped generating. 'end_turn' means it's done talking. 'tool_use' means it wants to call a tool before continuing. field. If stop_reason is "tool_use", Claude wants to call a tool — your code executes it and sends the result back. If stop_reason is "end_turn", Claude has finished and is delivering its final answer. That's the entire loop: call Claude → check stop_reason → if tool_use, execute tool and call again → if end_turn, you're done.

The beautiful thing is that Claude naturally interleaves reasoning text with tool calls. You don't need to prompt it to "think step by step" (though it can help). The text blocks before each tool_use block are Claude's thoughts — its reasoning about what to do and why. This means Claude's native tool-use IS ReAct, without any special framework or prompting library.

Thought Traces: The Agent's Working Memory

Everyday Analogy

Before thought traces: Imagine a math student who writes only the final answer on their exam — "42." They might be right, but the teacher can't give partial credit, can't identify where they'd go wrong on harder problems, and can't help them improve. If the answer is wrong, nobody knows where the reasoning broke down.

The pain: Early AI systems (and some current ones) worked like this. They'd return an answer without showing their work. When the answer was wrong, debugging was pure guesswork. Was the tool called with bad parameters? Did the model misinterpret the result? Did it ignore relevant information? Without the reasoning chain, you're flying blind.

The mapping: Thought traces are the "show your work" of AI agents. Every text block Claude generates before a tool call is a thought trace — it shows what Claude is thinking, why it chose that action, and what it learned from the last result. When something goes wrong, you can read the trace and pinpoint exactly where the reasoning diverged from what you expected.

Here's how you extract thought traces from Claude's response — it's just filtering the content blocks by type:

1. Improved accuracy: When Claude articulates its reasoning before acting, it catches its own mistakes. 2. Debuggability: When an agent produces a wrong answer, thought traces let you trace the failure to a specific step. Without traces, you'd just see "wrong answer" and have no idea where to start.

3. Thought traces provide that audit trail. That's an auditable decision, not a black box.

Why It Matters

Thought traces aren't a debugging luxury — they're a production requirement. In a healthcare pre-authorization system (Domain A), if an agent denies a claim, the provider has the right to know why. In a B2B order tracking system (Domain B), if an agent escalates an order to a human, the human needs to see what the agent already tried. In the UCC pipeline (Domain C), an agent researching lien risk might reason: "I found 3 filings against Acme Corp, but 2 are terminated — only the 2023 filing is active." That reasoning chain is auditable evidence for the risk assessment. Without thought traces, you'd need to re-investigate from scratch. With traces, the human picks up exactly where the agent left off — saving an average of 5-10 minutes per escalation in customer service workflows.

Common Misconceptions

"Thought traces are just for logging — they don't affect the agent's behavior?" — Actually, the act of generating reasoning text improves Claude's next decision. This is chain-of-thought in action: when Claude writes "Argentina won, so the capital is Buenos Aires," it's committing to that reasoning path, which makes the subsequent tool call more targeted. Suppress the reasoning and accuracy drops.

"I should store the full trace in the conversation context forever?" — No. Thought traces grow linearly with each iteration, consuming more tokens (and money) each round. In long-running agents, consider summarizing older trace entries or storing them externally while keeping only recent iterations in the active context. This is the context management challenge you studied in M08.

Thought traces solve the "why did it do that?" problem. But there's another critical question every agent system must answer: "when does it stop?" An agent without stop conditions is like a researcher with no deadline and an unlimited expense account — it might eventually find the answer, but at what cost?

Stop Conditions: When to Stop Looping

Everyday Analogy

Before stop conditions: Imagine hiring a research assistant and saying "find everything about this topic" with no deadline, no budget limit, and no definition of "enough." They'd research for weeks, rack up thousands of dollars in database access fees, and still feel like there's more to find. You'd get a 200-page report when you needed a 2-paragraph summary.

The pain: AI agents without stop conditions do exactly this — but faster and more expensively. An agent that gets confused can enter an infinite loop, calling the same tool over and over with the same parameters. Each API call costs money. At Claude's pricing, a runaway agent could burn through $50 in a few minutes without producing anything useful.

The mapping: Stop conditions are the guardrails you put around your research assistant: "You have 2 hours and $200. If you find the answer, great — stop early. If you've made 10 searches and found nothing, stop and tell me what you tried. If the same search keeps failing, try a different approach — and if three different approaches all fail, escalate to me." Each of these maps to a specific stop condition in your agent's code.

Technical Definition

An agent needs explicit stop conditionsRules that terminate the agent's loop to prevent infinite iteration and runaway costs. The five standard stop conditions are: natural completion, max iterations, cost/token budget, error threshold, and wall-clock timeout. — rules that terminate the loop and return a result (or a partial result with an explanation). There are five standard stop conditions:

1. Natural completion — Claude returns a response with stop_reason: "end_turn" and no tool_use blocks. This is the happy path: the agent found the answer and is done. This is the only stop condition that means "task succeeded."

2. Max iterations — A hard cap on the number of loop cycles (typically 5-15 for most tasks, up to 25 for complex research). When hit, return the best partial result with a message explaining the limit was reached. This prevents infinite loops.

3. Token/cost budget — Track cumulative tokens (input + output) across all iterations. When you approach the budget, stop and return what you have. Here's why this matters financially: Claude Opus costs ~$15 per million input tokens and ~$75 per million output tokens. A 10-iteration agent sending 4K tokens per round could cost $3-5 for a single question. Set limits that match your use case.

4. Error threshold — Stop after N consecutive tool failures (typically 2-3). If the search API returns errors three times in a row, there's likely a systemic issue (API down, rate limited, bad credentials). Continuing will just burn tokens. Return what you have and explain the tool failure.

5. Wall-clock timeout — A real-time limit (e.g., 30 seconds, 2 minutes). Important for user-facing applications where latency matters. Even if the agent is making progress, a user waiting 5 minutes for a response will leave.

An agent without stop conditions is a liability. Consider: Claude Opus costs roughly $15 per million input tokens. A runaway loop that sends 50 requests with 8K tokens each consumes 400K input tokens ($6) plus output tokens — and produces nothing useful. In a production system handling 1,000 requests/day, even a 1% runaway rate means 10 runaway agents daily, burning $60/day in wasted API calls. Max iterations and cost caps aren't optional safety features — they're core architecture requirements that should be in your agent from day one.

Common Misconceptions

"I'll just set max_iterations=100 to be safe" — That's not safe, that's a $50 budget authorization. A better approach: start with max_iterations=10 for simple tasks, 20 for complex research. Monitor your actual iteration counts in production and adjust based on data.

"If the agent hits the max, it failed" — Not necessarily. A partial result with 8 out of 10 answers found is often valuable. Your stop condition handler should return what the agent gathered so far, not just an error message. Tell the user: "I found 8 results before reaching the iteration limit. Here's what I have."

"Natural completion always means the answer is correct" — No. stop_reason: "end_turn" means Claude thinks it's done. It might be wrong. Stop conditions prevent runaway loops — they don't guarantee correctness. You still need output validation (covered in M17).

In a healthcare pre-auth agent (Domain A), it might look up CPT codes, check clinical criteria, and verify patient history. The ReAct loop is the same; only the tools change. Step 2: The ReAct Loop with Stop Conditions

Now for the heart of the agent — the loop itself. Here's the dilemma: you need a loop that's smart enough to keep going when Claude needs more information, but disciplined enough to stop when things go wrong. The solution is a while loop with five exit doors — any one of them can end the loop, but only "natural completion" means the agent actually succeeded.

Pay attention to the structure: every iteration has the same shape. Check stop conditions first (are we over budget? timed out?). Then call Claude. Then check stop_reason. If "end_turn", we're done — extract the answer. If "tool_use", execute the tools and loop again. That's the entire pattern.

def run_react_agent(
    question: str,
    max_iterations: int = 10,
    max_consecutive_errors: int = 3,
    max_tokens_budget: int = 50000,
    timeout_seconds: float = 60.0,
) -> dict:
    """
    Run a ReAct agent that answers a question using tools.
    Returns a dict with the answer, thought trace, and metadata.
    """
    # --- State tracking ---
    messages = [{"role": "user", "content": question}]
    thought_trace = []       # Log of each Thought/Action/Observation
    iteration = 0
    consecutive_errors = 0
    total_tokens = 0
    start_time = time.time()

    system_prompt = (
        "You are a research assistant that answers questions by "
        "searching for information and reasoning step by step. "
        "Think carefully before each action. Use the knowledge_base "
        "tool first for country data before falling back to web_search. "
        "Use the calculator for any math — never calculate in your head."
    )

    while True:
        # --- Stop condition checks ---

        # 1. Max iterations
        if iteration >= max_iterations:
            return {
                "answer": _extract_partial_answer(thought_trace),
                "stop_reason": "max_iterations",
                "trace": thought_trace,
                "iterations": iteration,
                "total_tokens": total_tokens,
            }

        # 2. Timeout
        elapsed = time.time() - start_time
        if elapsed > timeout_seconds:
            return {
                "answer": _extract_partial_answer(thought_trace),
                "stop_reason": "timeout",
                "trace": thought_trace,
                "iterations": iteration,
                "total_tokens": total_tokens,
            }

        # 3. Token budget
        if total_tokens >= max_tokens_budget:
            return {
                "answer": _extract_partial_answer(thought_trace),
                "stop_reason": "token_budget",
                "trace": thought_trace,
                "iterations": iteration,
                "total_tokens": total_tokens,
            }

        # --- Call Claude ---
        iteration += 1
        try:
            response = client.messages.create(
                model="claude-sonnet-4-6-20250514",
                max_tokens=1024,
                system=system_prompt,
                tools=tools,
                messages=messages,
            )
        except anthropic.APIError as e:
            consecutive_errors += 1
            thought_trace.append({
                "iteration": iteration,
                "type": "api_error",
                "error": str(e),
            })
            if consecutive_errors >= max_consecutive_errors:
                return {
                    "answer": None,
                    "stop_reason": "error_threshold",
                    "trace": thought_trace,
                    "iterations": iteration,
                    "total_tokens": total_tokens,
                }
            continue

        # Track token usage
        total_tokens += response.usage.input_tokens + response.usage.output_tokens
        consecutive_errors = 0  # Reset on successful API call

        # --- Process Claude's response ---
        # Extract thoughts (text blocks) and actions (tool_use blocks)
        for block in response.content:
            if block.type == "text":
                thought_trace.append({
                    "iteration": iteration,
                    "type": "thought",
                    "content": block.text,
                })
                print(f"  [Thought {iteration}] {block.text[:120]}...")

            elif block.type == "tool_use":
                thought_trace.append({
                    "iteration": iteration,
                    "type": "action",
                    "tool": block.name,
                    "input": block.input,
                })
                print(f"  [Action {iteration}] {block.name}({json.dumps(block.input)})")

        # --- Check for natural completion ---
        if response.stop_reason == "end_turn":
            final_text = next(
                (b.text for b in response.content if b.type == "text"),
                "No answer generated."
            )
            return {
                "answer": final_text,
                "stop_reason": "natural_completion",
                "trace": thought_trace,
                "iterations": iteration,
                "total_tokens": total_tokens,
            }

        # --- Execute tool calls and continue the loop ---
        if response.stop_reason == "tool_use":
            # Append Claude's response to message history
            messages.append({"role": "assistant", "content": response.content})

            # Execute each tool call and collect results
            tool_results = []
            for block in response.content:
                if block.type == "tool_use":
                    result = execute_tool(block.name, block.input)

                    # Check for tool errors
                    if result.startswith("Error"):
                        consecutive_errors += 1
                    else:
                        consecutive_errors = 0

                    # 4. Error threshold
                    if consecutive_errors >= max_consecutive_errors:
                        return {
                            "answer": _extract_partial_answer(thought_trace),
                            "stop_reason": "error_threshold",
                            "trace": thought_trace,
                            "iterations": iteration,
                            "total_tokens": total_tokens,
                        }

                    tool_results.append({
                        "type": "tool_result",
                        "tool_use_id": block.id,
                        "content": result,
                    })
                    thought_trace.append({
                        "iteration": iteration,
                        "type": "observation",
                        "tool": block.name,
                        "result": result[:200],
                    })
                    print(f"  [Observe {iteration}] {result[:120]}...")

            # Append tool results as user message
            messages.append({"role": "user", "content": tool_results})


def _extract_partial_answer(trace: list) -> str:

async function runReactAgent(
  question,
  {
    maxIterations = 10,
    maxConsecutiveErrors = 3,
    maxTokensBudget = 50000,
    timeoutMs = 60000,
  } = {}
) {
  // --- State tracking ---
  const messages = [{ role: "user", content: question }];
  const thoughtTrace = [];
  let iteration = 0;
  let consecutiveErrors = 0;
  let totalTokens = 0;
  const startTime = Date.now();

  const systemPrompt =
    "You are a research assistant that answers questions by " +
    "searching for information and reasoning step by step. " +
    "Think carefully before each action. Use the knowledge_base " +
    "tool first for country data before falling back to web_search. " +
    "Use the calculator for any math — never calculate in your head.";

  while (true) {
    // --- Stop condition checks ---

    // 1. Max iterations
    if (iteration >= maxIterations) {
      return {
        answer: extractPartialAnswer(thoughtTrace),
        stopReason: "max_iterations",
        trace: thoughtTrace,
        iterations: iteration,
        totalTokens,
      };
    }

    // 2. Timeout
    if (Date.now() - startTime > timeoutMs) {
      return {
        answer: extractPartialAnswer(thoughtTrace),
        stopReason: "timeout",
        trace: thoughtTrace,
        iterations: iteration,
        totalTokens,
      };
    }

    // 3. Token budget
    if (totalTokens >= maxTokensBudget) {
      return {
        answer: extractPartialAnswer(thoughtTrace),
        stopReason: "token_budget",
        trace: thoughtTrace,
        iterations: iteration,
        totalTokens,
      };
    }

    // --- Call Claude ---
    iteration++;
    let response;
    try {
      response = await client.messages.create({
        model: "claude-sonnet-4-6-20250514",
        max_tokens: 1024,
        system: systemPrompt,
        tools,
        messages,
      });
    } catch (e) {
      consecutiveErrors++;
      thoughtTrace.push({
        iteration,
        type: "api_error",
        error: e.message,
      });
      if (consecutiveErrors >= maxConsecutiveErrors) {
        return {
          answer: null,
          stopReason: "error_threshold",
          trace: thoughtTrace,
          iterations: iteration,
          totalTokens,
        };
      }
      continue;
    }

    // Track token usage
    totalTokens += response.usage.input_tokens + response.usage.output_tokens;
    consecutiveErrors = 0;

    // --- Process Claude's response ---
    for (const block of response.content) {
      if (block.type === "text") {
        thoughtTrace.push({
          iteration,
          type: "thought",
          content: block.text,
        });
        console.log(`  [Thought ${iteration}] ${block.text.slice(0, 120)}...`);
      } else if (block.type === "tool_use") {
        thoughtTrace.push({
          iteration,
          type: "action",
          tool: block.name,
          input: block.input,
        });
        console.log(
          `  [Action ${iteration}] ${block.name}(${JSON.stringify(block.input)})`
        );
      }
    }

    // --- Check for natural completion ---
    if (response.stop_reason === "end_turn") {
      const finalText =
        response.content.find((b) => b.type === "text")?.text ??
        "No answer generated.";
      return {
        answer: finalText,
        stopReason: "natural_completion",
        trace: thoughtTrace,
        iterations: iteration,
        totalTokens,
      };
    }

    // --- Execute tool calls and continue the loop ---
    if (response.stop_reason === "tool_use") {
      messages.push({ role: "assistant", content: response.content });

      const toolResults = [];
      for (const block of response.content) {
        if (block.type !== "tool_use") continue;

        const result = executeTool(block.name, block.input);

        if (result.startsWith("Error")) {
          consecutiveErrors++;
        } else {
          consecutiveErrors = 0;
        }

        // 4. Error threshold
        if (consecutiveErrors >= maxConsecutiveErrors) {
          return {
            answer: extractPartialAnswer(thoughtTrace),
            stopReason: "error_threshold",
            trace: thoughtTrace,
            iterations: iteration,
            totalTokens,
          };
        }

        toolResults.push({
          type: "tool_result",
          tool_use_id: block.id,
          content: result,
        });
        thoughtTrace.push({
          iteration,
          type: "observation",
          tool: block.name,
          result: result.slice(0, 200),
        });
        console.log(`  [Observe ${iteration}] ${result.slice(0, 120)}...`);
      }

      messages.push({ role: "user", content: toolResults });
    }
  }
}

function extractPartialAnswer(trace) {
  const thoughts = trace
    .filter((t) => t.type === "thought")

      "I was unable to complete the research, but here's what I " +
      `found so far: ${thoughts[thoughts.length - 1]}`
    );
  }
  return "The agent was stopped before producing any results.";
}

Step 3: Formatting the Thought Trace

def format_trace(trace: list[dict]) -> str:
    """Format a thought trace into a human-readable timeline."""
    lines = ["=" * 50, "AGENT THOUGHT TRACE", "=" * 50]

    for entry in trace:
        iteration = entry["iteration"]
        if entry["type"] == "thought":
            lines.append(f"\n[Iteration {iteration} — REASON]")
            lines.append(f"  {entry['content']}")
        elif entry["type"] == "action":
            lines.append(f"\n[Iteration {iteration} — ACT]")
            lines.append(f"  Tool: {entry['tool']}")
            lines.append(f"  Input: {json.dumps(entry['input'], indent=4)}")
        elif entry["type"] == "observation":
            lines.append(f"\n[Iteration {iteration} — OBSERVE]")
            lines.append(f"  Tool: {entry['tool']}")
            lines.append(f"  Result: {entry['result']}")
        elif entry["type"] == "api_error":
            lines.append(f"\n[Iteration {iteration} — ERROR]")
            lines.append(f"  {entry['error']}")

    lines.append("\n" + "=" * 50)
    return "\n".join(lines)

  for (const entry of trace) {
    const { iteration } = entry;

        lines.push(`\n[Iteration ${iteration} — REASON]`);
        lines.push(`  ${entry.content}`);
        break;
      case "action":
        lines.push(`\n[Iteration ${iteration} — ACT]`);
        lines.push(`  Tool: ${entry.tool}`);
        lines.push(`  Input: ${JSON.stringify(entry.input, null, 4)}`);

        lines.push(`\n[Iteration ${iteration} — OBSERVE]`);
        lines.push(`  Tool: ${entry.tool}`);

        break;
      case "api_error":
        lines.push(`\n[Iteration ${iteration} — ERROR]`);
        lines.push(`  ${entry.error}`);

Error Handling & Retry Patterns

In a lab, every tool call succeeds on the first try. In production, tool calls fail constantly — APIs time out under load, third-party services return 500 errors, and rate limiters reject bursts of requests. A ReAct agent without error handling will crash on iteration two and return nothing to the user. A production ReAct agent treats failure as a normal part of the loop.

Retry with Exponential Backoff

The simplest recovery strategy: if a tool call fails, wait and try again. But don't retry immediately — that hammers an already-struggling service. Instead, use exponential backoff: wait 1 second after the first failure, 2 seconds after the second, 4 seconds after the third. This gives the upstream service time to recover while keeping your agent moving forward.

Fallback Chains

Sometimes the right answer isn't “try again” — it's “try something else.” A fallback chain defines backup tools for when the primary tool is unavailable. If your web search API is down, fall back to querying a local knowledge base. If a premium data provider is rate-limited, try a free alternative with less detail. The agent keeps reasoning — it just picks a different action.

Graceful Degradation

When all retries and fallbacks are exhausted, don't crash — return what you have. If your agent gathered results from three out of four tool calls before one failed, those three results are still valuable. Attach a note explaining what's missing and why, so the user can decide whether to retry or work with partial data. This is graceful degradation — partial success beats total failure every time.

The Pattern in Pseudocode

FOR each tool_call in react_loop:
    result = None
    FOR attempt in 1, 2, 3:
        TRY:
            result = CALL tool_call.tool(tool_call.input)
            BREAK  # success — exit retry loop
        CATCH error:
            WAIT (2 ^ attempt) seconds   # exponential backoff: 2s, 4s, 8s
            LOG warning: "Tool {tool_call.tool} failed (attempt {attempt}): {error}"

    IF result is None AND fallback_tool EXISTS:
        TRY:
            result = CALL fallback_tool(tool_call.input)
        CATCH error:
            LOG error: "Fallback also failed: {error}"

    IF result is None:
        result = { partial: True, error: "Tool unavailable after 3 retries" }
        # Agent continues with partial results instead of crashing

    APPEND result to observations

Extended Thinking: Letting Claude Reason Longer

Sometimes a ReAct agent faces a step that requires deep, multi-part reasoning — comparing five medical criteria simultaneously, weighing conflicting evidence, or planning a complex sequence of actions. Extended Thinking gives Claude a dedicated scratchpad to work through these hard steps before committing to an answer.

What It Is

When enabled, Claude produces a chain-of-thought reasoning trace before its visible response. This thinking is returned in a separate thinking content block — you can read it for debugging or logging, but the user doesn't see it by default. It's like giving the agent a whiteboard to sketch out its reasoning before speaking.

When to Use It

Enable extended thinking for the Reason phase of complex ReAct iterations — multi-step math, cross-referencing several tool results, or deciding between ambiguous action paths. It shines in planning-heavy tasks where the quality of reasoning directly determines whether the agent picks the right next tool.

When NOT to Use It

Skip extended thinking for simple tool dispatches (“look up this ID”), latency-sensitive paths where every millisecond counts, or iterations where the agent already has a clear action to take. Thinking tokens are billed (at a lower rate), and the extra latency is wasted if the reasoning is trivial. Use it surgically — turn it on for the hard iterations, not every loop cycle.

            return {"answer": step["final_answer"], "trace": trace,

            if '"error"' in result or '"found": false' in result:

            else:
                consecutive_errors = 0

        messages.append({"role": "assistant", "content": response.content})
        messages.append({"role": "user", "content": tool_results})

    return {"answer": "Max iterations reached.", "trace": trace,
