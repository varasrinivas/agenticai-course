The Agent SDK — Beyond the Messages API

Everyday Analogy

The Messages API is like calling someone on the phone. You make a call, they respond, you hang up. If you need a multi-step conversation, you have to manage the entire flow: call, listen, respond, call again, check if they are done, handle errors if the line drops. Every detail is your responsibility.

The pain is real: the agentic loop you built in M12 required you to code the while loop, check stop_reason, send tool results back, handle errors, and manage message history. That is dozens of lines of boilerplate code that every agent developer writes identically.

The Agent SDKAnthropic's official SDK for building agents. Instead of manually coding the agentic loop (Messages API + while loop + tool dispatch), the SDK's query() function manages the entire Reason→Act→Observe cycle automatically. You define tools and process results; the SDK handles the loop. is like hiring a contractor. You describe the job ("fix this leak"), hand over the tools, and the contractor manages the process: they assess the problem, use the right tools, check if the fix works, and report back when done. You defined the goal and the tools; they managed the loop.

Here is what a query() call actually looks like in practice — the entire agentic loop in one function call:

// The SDK call — this is it. No while loop, no stop_reason check, no tool dispatch.
for await (const message of query({
  prompt: "Find all UCC filings for Acme Corp in New York",
  allowedTools: ["search_filings", "lookup_entity", "Task"],
  maxTurns: 15,            // safety net only
  system: "You are a UCC filing analyst..."
})) {
  if (message.type === "assistant") console.log(message.content);
}

Compare this to the 40+ line manual loop from M12. The SDK handles stop_reason checking, tool dispatch, message history, and streaming internally.

Technical Definition

The Agent SDK provides the query() function that automates the agentic loop you coded manually in M12. Here is what it manages for you:

Automatic tool execution: When Claude returns stop_reason: 'tool_use', the SDK automatically dispatches the tool call. It collects the result and sends it back to Claude. Then it checks stop_reason again. You do not write any of this loop logic.

Streaming responses: Results stream via for await (const message of query(...)). This means you can process messages as they arrive, rather than waiting for the entire response to finish.

The agent should terminate naturally via stop_reason: 'end_turn'. If maxTurns fires, something has gone wrong.: A safety cap on loop iterations. Critical distinction: maxTurns is a SAFETY NET, not a control mechanism. The agent terminates naturally via stop_reason. If maxTurns fires, it means something went wrong — the agent could not complete the task within the expected number of steps.

Message types: The SDK emits structured messages as the loop runs. The four types are: assistant (Claude's text responses), tool_use (when Claude wants to call a tool), tool_result (the output from that tool), and system with init subtype (available commands listed at session start).

The SDK manages the loop, but how does it know WHEN to stop? That signal comes from stop_reason — the most important field in the API response for agentic applications.

stop_reason — The Loop Termination Signal

Every time you send a message to Claude and get a response back, that response includes a field called stop_reason. This tiny field is the most important piece of data in the entire agentic loop. It tells you why Claude stopped generating — and that "why" determines what your code should do next.

There are only three possible values, and each one triggers a different action. If stop_reason is 'tool_use', Claude is saying "I need to call a tool before I can continue — please execute it and send me the result." If it is 'end_turn', Claude is saying "I am done — here is the final answer." And if it is 'max_tokens', Claude ran out of space in the output buffer before finishing. Your loop logic boils down to: keep going on 'tool_use', stop on everything else.

Why is this worth a whole section? Because the most common beginner mistake is to ignore stop_reason entirely and instead parse Claude's text output looking for phrases like "I'm done" or "task complete." The problem is that natural language is for humans, not for control flow. Claude might say "All set!", "Here you go", "Done!", or nothing at all. You cannot reliably match every possible phrasing. stop_reason is a machine-readable, consistent signal that never varies. It is the only reliable way to control your loop.

The correct loop pattern: while (response.stop_reason === 'tool_use') { execute_tool(); send_result(); }. When stop_reason is anything other than 'tool_use', the loop ends.

Now you know when to stop the loop. But what happens DURING each tool call? Hooks let you intercept tool calls and enforce rules that prompts alone cannot guarantee.

Hooks — Programmatic Enforcement

Everyday Analogy

Prompts are like asking a teenager to clean their room. You can be very specific, very persuasive, and very firm. But some days, the room will not get cleaned. Prompts are suggestions — probabilistic instructions that the model usually follows but can sometimes ignore.

The pain is catastrophic when it happens on critical business logic: "Do not issue refunds over $500" works 99% of the time. But the 1% where the model issues a $600 refund creates a real financial loss, a compliance violation, and a very difficult conversation with your manager.

HooksCode that runs BEFORE (PreToolUse) or AFTER (PostToolUse) a tool call, outside the model's control. Hooks execute deterministically as programs — they cannot be ignored, overridden, or "convinced" by the model. Use for critical business rules that MUST be enforced. are the lock on the liquor cabinet. They run as CODE, not as suggestions in a prompt. A PostToolUse hook that checks refund amounts runs every single time, deterministically. The model cannot ignore it, override it, or be "convinced" to bypass it. Hooks are 100% reliable enforcement.

Let's build a PostToolUse hook that enforces a $500 refund limit. This is the kind of business rule that absolutely cannot be left to a prompt — a single missed enforcement could mean a compliance violation and a financial loss.

The hook works in three parts, and it is worth understanding why each part exists. First, it reads the tool payload (session metadata, tool name, tool input, and tool response) from stdin as JSON. Claude Code pipes this automatically — you do not need to call any API or parse any logs. Second, it applies the business rule: is the amount over $500? This is a simple if-statement, but that simplicity is the point. Deterministic code does not hallucinate, forget, or get "convinced" to make exceptions. Third, it signals the decision via exit code: exit 0 to allow the result through, or exit 2 with a feedback message printed to stderr to block. Claude Code forwards that stderr text to the model so the agent knows why the call was blocked and can take a different action (like escalating to a human).

# hooks/check_refund_limit.py
# PostToolUse hook — runs AFTER the issue_refund tool.
# Blocks refunds > $500 and redirects to human escalation.
# This is deterministic code, NOT a prompt suggestion.

import json
import sys
from datetime import datetime


def main() -> int:
    """
    Read the PostToolUse payload from stdin, validate against
    the $500 refund limit, and signal allow/block via exit code.

    Exit 0  -> allow (tool result passes through to Claude).
    Exit 2  -> block (stderr message is forwarded to Claude).
    """
    try:
        data = json.loads(sys.stdin.read())
    except json.JSONDecodeError as e:
        print(f"hook: bad stdin payload: {e}", file=sys.stderr)
        return 1  # non-blocking error — Claude continues

    tool_input = data.get("tool_input", {})
    amount = tool_input.get("amount", 0)
    order_id = tool_input.get("order_id", "unknown")

    audit = {
        "timestamp": datetime.utcnow().isoformat(),
        "session_id": data.get("session_id"),
        "order_id": order_id,
        "amount": amount,
    }

    # --- Business Rule: $500 refund limit ---
    # This CANNOT be overridden by the model.
    # A prompt saying "refund $600" will be blocked here.
    if amount > 500:
        audit["event"] = "refund_blocked"
        audit["reason"] = "exceeds_500_limit"
        # Audit log goes to stderr — does NOT confuse Claude because
        # exit 2 forwards stderr as the block message; on exit 0 stderr
        # is just logged. To keep the audit and the block message clean,
        # we print the block message LAST so it is what Claude sees.
        print(json.dumps(audit), file=sys.stderr)
        print(
            f"Refund of ${amount:.2f} for order {order_id} exceeds the "
            f"$500 limit. This request has been escalated to a human "
            f"reviewer for approval. Reference: REF-{order_id}",
            file=sys.stderr,
        )
        return 2  # blocking — Claude sees the stderr message

    # Amount is within limit — allow the refund
    audit["event"] = "refund_allowed"
    print(json.dumps(audit), file=sys.stderr)
    return 0


if __name__ == "__main__":
    sys.exit(main())
// hooks/check_refund_limit.ts
// PostToolUse hook — runs AFTER the issue_refund tool.
// Blocks refunds > $500 and redirects to human escalation.
// This is deterministic code, NOT a prompt suggestion.
//
// Exit 0  -> allow (tool result passes through to Claude).
// Exit 2  -> block (stderr message is forwarded to Claude).

interface HookPayload {
  session_id?: string;
  tool_input?: { amount?: number; order_id?: string };
  tool_response?: unknown;
}

let input = "";
process.stdin.on("data", (chunk) => (input += chunk));
process.stdin.on("end", () => {
  let data: HookPayload;
  try {
    data = JSON.parse(input) as HookPayload;
  } catch (err) {
    console.error(`hook: bad stdin payload: ${err}`);
    process.exit(1); // non-blocking error
  }

  const amount = data.tool_input?.amount ?? 0;
  const orderId = data.tool_input?.order_id ?? "unknown";
  const audit = {
    timestamp: new Date().toISOString(),
    session_id: data.session_id,
    order_id: orderId,
    amount,
  };

  // --- Business Rule: $500 refund limit ---
  if (amount > 500) {
    console.error(JSON.stringify({ ...audit, event: "refund_blocked", reason: "exceeds_500_limit" }));
    console.error(
      `Refund of $${amount.toFixed(2)} for order ${orderId} exceeds ` +
      `the $500 limit. This request has been escalated to a ` +
      `human reviewer for approval. Reference: REF-${orderId}`,
    );
    process.exit(2); // blocking — Claude sees the stderr message
  }

  console.error(JSON.stringify({ ...audit, event: "refund_allowed" }));
  process.exit(0);
});
What Just Happened?

You built a PostToolUse hook that intercepts every issue_refund tool call. If the amount exceeds $500, the hook exits with code 2 and writes a human-readable block message to stderr — Claude Code forwards that stderr to the model as feedback, redirecting the agent to escalate to a human. This runs as external code, so the model cannot bypass it. The hook also logs every decision (allowed or blocked) to an audit trail via stderr.

Per-tool events (PreToolUse, PostToolUse): granular guardrails — refund limits, PII redaction, lint-on-write.

Hooks enforce rules within a session. But what about managing the session itself? Long-running sessions accumulate stale context, and parallel exploration pollutes the main conversation. Session management solves both problems.

Session Management

If you have ever had a long conversation with Claude Code and then started a new session only to realize you lost all that context — that is the problem session management solves. Sessions are how Claude Code persists conversational state across interactions, so you can close your terminal, come back tomorrow, and pick up exactly where you left off.

Under the hood, a session is a stored conversation history. It includes every message you sent, every response Claude gave, and every tool call with its result. When you resume a session, Claude Code loads that entire history back into the context window. This is why long sessions can become problematic. As the history grows, it fills the context window with older information that may no longer be accurate — code you have since changed, files you moved, or bugs you already fixed.

Sessions differ from subagents in an important way. A session belongs to a single user and persists over time (you resume it). A subagent is ephemeral — it is spawned, does its work, returns a result, and its context is discarded. Think of sessions as "saving your place in a book" and subagents as "asking a colleague to look something up for you." They solve different problems.

Here is what session management looks like in practice — the actual terminal commands you would use:

Session forks let a single user explore in parallel. But long-running sessions hit a different problem — the context window fills up, and the SDK has to compact older history to make room. Mismanaging that compaction is one of the top reasons production agents lose state mid-task.

Context Compaction — Don't Let It Surprise You

Every Claude Code or Agent SDK session has a context window. When it fills up, the SDK compacts automatically — summarizing older messages to free up room for new ones. The summary is shorter than the original, but lossy: details, file paths, partial test output, intermediate decisions can vanish into a one-line summary that no longer captures what your agent actually needs.

The top-1% discipline is to never let auto-compaction surprise you. Compact manually, on your terms, while you still have full context to decide what's worth preserving.

Manual at 50% vs Auto at 100%

The Two Rules

Rule 1 — /compact Manually at ~50%

Run /compact yourself when context usage hits roughly half-full, before the SDK forces it on you. At 50% you still have room to write a deliberate summary; at 100% you're triaging in panic. This is the difference between a clean handoff to the next phase and losing your test status mid-debugging.

Rule 2 — Tell Claude What to Preserve in CLAUDE.md

Add a compaction directive to your project CLAUDE.md so every session inherits the same preservation policy:

## When compacting context
Always preserve:
- The list of files modified in this session (with one-line summaries)
- Current test status (pass/fail, last failing test name)
- Any unresolved errors or open questions
- The plan we agreed on (if a plan exists)

- Verbose tool output that's been acted on
- Old file contents (we can re-read if needed)
- Earlier conversation about decisions already made

This single block turns compaction from "Claude guesses what matters" into "Claude follows your preservation contract." It's the cheapest 10 lines you'll ever add to CLAUDE.md.

PreCompact Hook for Critical State

For high-stakes pipelines (long-running migrations, multi-step deploys, debugging sessions where every test failure matters), pair the CLAUDE.md directive with the PreCompact hook event you saw earlier in this module. The hook fires before the compaction runs — use it to dump the modified-files list, current test output, or open task list to a scratchpad file outside the context window. After compaction, the agent can re-read the scratchpad and pick up exactly where it left off, even if the summary lost details.

Compaction handles the length of conversation history. But for multi-agent workflows where different specialists handle different parts of a complex task, you need a different tool: the Task tool and subagent orchestration.

Subagent Orchestration with the Task Tool

So far, everything has run inside a single agent — one Claude instance with one context window handling one task. But some tasks are too complex or too broad for a single agent. Analyzing UCC filings for a company across all 50 states, for example, involves filing search, entity name matching, and risk scoring. Cramming all of that into one agent's context window creates noise, increases the chance of errors, and makes the system hard to debug.

The solution is subagent orchestration: a coordinator agent that breaks a complex request into specialist subtasks and delegates each one to a separate subagent via the Task tool. Each subagent runs in its own isolated context window — it sees only the prompt the coordinator gives it, not the coordinator's full conversation. This isolation is a feature, not a limitation: it keeps each subagent focused and prevents cross-contamination of context between unrelated subtasks.

This differs from session forking in an important way. A session fork copies the entire conversation history and lets a single user explore two approaches. A subagent starts with a blank context and receives only the information the coordinator explicitly passes. Forks are for parallel exploration within one user's workflow. Subagents are for parallel delegation across specialist roles. Use forks when you want shared history; use subagents when you want isolation.

Now let's build a coordinator agent that delegates to subagents via the Task tool. The coordinator has three jobs: receive the user's request, break it into specialist subtasks, and combine the results.

The interesting design decision — and the one that trips up most developers — is what context to pass to each subagent. Since subagents have isolated context windows, they cannot see the coordinator's conversation. If the user said "Analyze Acme Corp in New York, California, and Texas" three messages ago, the subagent does not know about "Acme Corp" or the state list unless you explicitly include them in the Task prompt. Forgetting to pass this context is the single most common bug in multi-agent systems. The fix is simple: when constructing the Task prompt, always ask yourself "does this subagent have everything it needs to do its job without any other information?"

      "Spawn a subagent to handle a specific subtask. " +
      "The subagent has its own isolated context window. " +
      "Include all relevant context in the prompt.",

      type: "object" as const,

async function handleTask(prompt: string): Promise<unknown> {
  const client = new Anthropic();
  try {
    const response = await client.messages.create({
      model: "claude-sonnet-4-6",
      max_tokens: 2048,
      messages: [{ role: "user", content: prompt }],
    });
    const text = response.content
      .filter((b): b is Anthropic.TextBlock => b.type === "text")
      .map((b) => b.text)
      .join(" ");
    return { isError: false, result: text };
  } catch (error) {
    return {
      isError: true,
      errorCategory: "subagent_failure",
      context: String(error),
      isRetryable: true,
    };
  }
}

export async function runCoordinator(query: string): Promise<string> {
  const client = new Anthropic();
  const messages: Anthropic.MessageParam[] = [
    { role: "user", content: query },
  ];

  for (let i = 0; i < 10; i++) {
    let response: Anthropic.Message;
    try {
      response = await client.messages.create({
        model: "claude-sonnet-4-6",
        max_tokens: 4096,
        system: SYSTEM_PROMPT,
        tools: TOOLS,
        messages,
      });
    } catch (error) {
      return `Coordinator error: ${error}`;
    }

    if (response.stop_reason === "tool_use") {
      const toolResults: Anthropic.ToolResultBlockParam[] = [];
      for (const block of response.content) {
        if (block.type === "tool_use" && block.name === "Task") {
          const result = await handleTask(
            (block.input as { prompt: string }).prompt,
          );
          toolResults.push({
            type: "tool_result",
            tool_use_id: block.id,
            content: JSON.stringify(result),
          });
        }
      }
      messages.push({ role: "assistant", content: response.content });
      messages.push({ role: "user", content: toolResults });
    } else if (response.stop_reason === "end_turn") {
      return response.content
        .filter((b): b is Anthropic.TextBlock => b.type === "text")
        .map((b) => b.text)
        .join(" ");
    }
  }
  return "Coordinator reached iteration limit.";
}

Subagents handle delegation. But what happens when neither the agent nor its subagents can handle a request? Correct escalation — knowing WHEN and WHY to escalate — is the final critical pattern.

Escalation Patterns

Escalation is the decision to hand a request from your automated agent to a human reviewer. This sounds simple, but it is one of the most frequently tested topics on the certification exam — because getting it wrong leads to either frustrated customers (under-escalation) or overwhelmed human teams (over-escalation).

The core principle is that escalation decisions should be based on the task, not the customer's mood. Think about it this way: a customer screaming about a password reset still has a simple, well-defined problem that the agent can solve in 30 seconds. Sending that to a human wastes the human's time and makes the customer wait longer. Meanwhile, a perfectly calm customer whose order falls into a scenario your policy does not cover must be escalated — because the agent has no rules to guide its decision, and guessing on policy is dangerous.

Escalation also differs from error handling. An error means something broke (API timeout, invalid input). Escalation means the agent is functioning correctly but has reached the boundary of its authority or knowledge. Understanding this distinction helps you design cleaner systems: errors trigger retries and fallbacks; escalation triggers human routing with structured context.

Technical Definition

Correct escalationThe process of transferring a request from an automated agent to a human reviewer. Correct escalation is based on task complexity and policy gaps, NOT on customer sentiment or anger level. An angry customer with a simple request does NOT need a human. triggers (when the agent SHOULD hand off to a human):

  • Policy gaps: No rule covers this case. The agent cannot determine the correct action.
  • Capability limits: The agent lacks the tools or knowledge to complete the task.
  • Explicit request: The customer says "let me talk to a human."
  • Business thresholds: The action exceeds the agent's authority (e.g., refund over $500).

WRONG escalation trigger: sentiment/anger. An angry customer asking to reset their password does NOT need a human. A calm customer hitting an edge case your policy does not cover DOES need a human. Escalate on TASK COMPLEXITY and POLICY GAPS, not emotions.

When escalating, include structured context: what was attempted, what failed, relevant data, and a suggested next step. "I could not help, please take over" is useless. Here is what a good escalation payload looks like:

// Good escalation context — human has everything they need
{
  "escalation_reason": "business_threshold_exceeded",
  "customer_id": "cust_9281",
  "order_id": "ORD-8847",
  "attempted_action": "issue_refund",
  "blocked_by": "PostToolUse hook: amount $600 exceeds $500 limit",
  "conversation_summary": "Customer purchased item on 2026-03-15, received damaged. Requested full refund of $600.",
  "suggested_action": "Manager approval for over-limit refund",
  "priority": "normal"
}

Compare that to a bad escalation: {"message": "I could not help the customer, please take over."}. The human reviewer now has to start from scratch, re-asking the customer every question the agent already asked. That is wasted time for both the human and the customer.

🎓 Cert Tip — Domain 5.2

Critical anti-pattern: sentiment-based escalation. An angry customer with a simple password reset does NOT need a human. A calm customer hitting a policy gap DOES. The exam tests this distinction directly. Escalate on task complexity and policy gaps, never on sentiment alone.

Common Misconceptions

"Hooks replace prompts entirely, right?" — No. Hooks are for critical business rules that must be enforced 100% of the time (refund limits, PII redaction, compliance checks). Prompts are still the right tool for style, tone, response format, and non-critical preferences. Using hooks for everything adds unnecessary complexity — a hook that enforces "respond in a friendly tone" is overkill and fragile.

"Sessions automatically stay up to date with my codebase." — Not true. A session preserves conversation history, but it does not re-read files that changed since the session started. If you edited main.py after the session began, Claude may still reference the old version from memory. Use /compact or start a fresh session for significant code changes. Scratchpad files (read from disk each time) stay current automatically.

"Subagents share the coordinator's context window." — This is the single most common mistake in multi-agent systems. Subagents have ISOLATED context. They see only what you explicitly include in the Task prompt. If the user told the coordinator "focus on New York filings" three messages ago, the subagent does not know that unless you pass it along.

"The Agent SDK is a completely different API from the Messages API." — Not exactly. The Agent SDK is built ON TOP of the Messages API. Under the hood, query() is making the same client.messages.create() calls you wrote in M12 — it just automates the loop, tool dispatch, and message management. "An angry customer should always be escalated to a human." — This is the exam's favorite trick question. Sentiment is NOT a valid escalation trigger. An angry customer with a simple request (password reset, order status) should be helped immediately by the agent. A calm customer hitting a policy gap (scenario your rules don't cover) MUST be escalated. Escalate on task complexity and policy gaps, never on emotions alone.

Module Summary

  • Agent SDK: query() automates the agentic loop. maxTurns is a safety net, not primary stopping. The SDK manages tool dispatch and message streaming.
  • stop_reason: 'tool_use' = continue; 'end_turn' = stop. Never parse text for completion.
  • Hooks: PreToolUse (before execution) and PostToolUse (after execution) for deterministic enforcement. Prompts = suggestions; hooks = rules.
  • Sessions: Stored as JSONL transcripts under ~/.claude/projects/; --continue for the most recent, --resume <session-id> for a specific one, fork_session for isolated parallel exploration. Watch for stale context.
  • Subagents: Task tool spawns isolated subagents. allowedTools must include 'Task'. Context is NOT inherited — pass explicitly.
  • Escalation: Trigger on policy gaps, capability limits, explicit requests, business thresholds. NEVER on sentiment alone.
