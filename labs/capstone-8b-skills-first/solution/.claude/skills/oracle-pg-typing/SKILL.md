# Oracle → PostgreSQL type mapping

One table per run.

## The rule that governs everything else

**The DDL tells you the declared type. The rows tell you what the column actually holds.
Those are different questions, and the mapping depends on the second one.**

So the procedure is always two reads, never one:

1. `oracle_get_ddl` — the declared type
2. `oracle_sample_rows` — 20 real rows

A mapping decided from the DDL alone is a guess that compiles.

## Step 1 — Run the checker before you reason

```bash
python .claude/skills/oracle-pg-typing/scripts/check_mapping.py --type "NUMBER(9)"
python .claude/skills/oracle-pg-typing/scripts/check_mapping.py --ddl artifacts/ddl/ucc_filing.sql
```

It returns a target type, a reason, and a **confidence**:

| Confidence | Meaning | What you do |
|---|---|---|
| `confident` | Mechanical. No judgement needed. | Accept it. Do not re-derive it. |
| `check_data` | The right answer depends on the values. | Read the sample rows, then decide. |
| `manual` | No good equivalent exists. | Write it to the manual-review queue. Do not invent one. |

Spend your reasoning on `check_data` and `manual`. The checker is faster and more consistent
than you are at "does NUMBER(9) fit in an int" — let it own that, and do not second-guess a
`confident` verdict.

Load `references/type-matrix.md` for the full table, and `references/number-precision.md` for
the NUMBER(p,s) rules. Do not load either speculatively — they are long, and you need the
context for the rows.

## Step 2 — The four traps

These are the ones that produce a migration which passes every structural check and is wrong.

**`DATE` is not `date`.** Oracle `DATE` carries a time component. Mapping it to PostgreSQL
`date` truncates 14:32:07 to midnight. Nothing errors. A checksum computed over the truncated
values agrees with itself. The only thing that finds it is a value-level spot check. Map to
`timestamp(0)`.

**`NUMBER` with no precision is not an integer.** An unconstrained `NUMBER` can carry a scale.
Narrowing it to `integer` truncates silently. Map to `numeric` unless the rows prove otherwise.

**`VARCHAR2(n BYTE)` is not `varchar(n)` for multibyte text.** Oracle counts bytes, PostgreSQL
counts characters. A value that fit in `n` bytes may need more than `n` characters. Check the
rows for non-ASCII before accepting the same width.

**`RAW(16)` is `uuid` only if it holds GUIDs.** Sixteen binary bytes that are a hash are
`bytea`. The DDL cannot tell you which. The rows can.

## Step 3 — Identifier case

Oracle folds unquoted identifiers to UPPER. PostgreSQL folds to lower.

**Lowercase every identifier and do not quote it.** Quoting `"UCC_FILING"` preserves the
uppercase name and forces every hand-written query afterwards to quote it too — forever. This
is a one-way door; get it right on the way through.

---

## Step 4 — The identity idiom

The legacy schema predates Oracle 12c, so identity is a sequence plus a `BEFORE INSERT`
trigger. Convert that pair to `GENERATED BY DEFAULT AS IDENTITY`, and emit a `setval`
equivalent to run *after* the data load — otherwise the first insert after cutover collides
with an existing key.

**Read the trigger before you delete it.** In this schema `TRG_FILING_NORMALIZE_BI` is a
*second* `BEFORE INSERT` trigger on `UCC_FILING` that is not an identity trigger — it
normalizes `filing_number` and defaults `lapse_date`. That is business logic. It must survive
conversion. Deleting it along with the identity trigger is the expensive mistake here.

## Output

For each table write both:

- `artifacts/ddl/<table>.sql` — the PostgreSQL DDL, then apply it with `pg_apply_ddl`
- `artifacts/decisions/<table>.md` — one line per column: Oracle type, PostgreSQL type,
  confidence, and the reason. **Every column gets a line, including the boring ones.** The
  decision log is what makes the migration reviewable by someone who was not here.
