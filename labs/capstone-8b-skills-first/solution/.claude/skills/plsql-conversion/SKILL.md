# PL/SQL → PL/pgSQL

One object per run.

## The output is a conversion **or** a refusal

Most migration tooling treats refusal as failure. Here it is a first-class result, and getting
it wrong in the confident direction is the worst outcome available to you.

**A confident wrong translation is worse than no translation, because it passes review.**
Nobody re-reads a converted package that compiled. They re-read the ones on the manual queue.

Before converting anything, run the scanner:

```bash
python .claude/skills/appsql-rewriting/scripts/find_oracleisms.py --file <source.sql>
```

It prints every construct it recognises and marks the untranslatable ones. If it reports any
construct marked `REFUSE`, stop converting and go to *Refusal* below.

Load `references/construct-catalog.md` for the full construct-by-construct guidance, and
`references/refusal-template.md` when you are writing a refusal. Do not load either unless you
have hit the case — they are long.

## Packages → schemas

PostgreSQL has no packages. Convert a package to a **schema of the same name**, containing one
function per public routine:

```
PKG_RISK_CALC.SCORE_DEBTOR(x)   ->   pkg_risk_calc.score_debtor(x)
```

The call sites in application code then keep working unchanged, which is the whole reason to
pick this shape over flattening to `pkg_risk_calc_score_debtor`.

Two things do **not** survive the move and must be recorded:

- **Package state.** Variables declared in the package body persist for the session in Oracle.
  PostgreSQL functions have no equivalent. If the package holds state between calls, that is a
  redesign, not a translation.
- **The spec/body distinction.** Oracle's package spec is the public interface; anything not in
  it is private. PostgreSQL has no private functions in a schema. Either accept that private
  helpers become callable, or prefix them and revoke `EXECUTE`.

## Refusal

Refuse when the scanner reports an untranslatable construct. In this schema that is
**`PRAGMA AUTONOMOUS_TRANSACTION`**, in `PKG_FILING_MAINT.log_audit`.

The pragma exists so the row commits *even when the caller rolls back* — which is exactly what
an audit log needs. PostgreSQL cannot do it in-process. Dropping the pragma compiles, runs, and
silently inverts the semantics: audit rows now vanish on rollback, which is the opposite of what
an audit log is for. There is no syntax that makes this correct.

The options are `dblink`, a background worker, or writing the audit row outside the transaction
— and **choosing between them is an architecture decision, not a translation decision.** That is
why it goes to a human.

When you refuse, write `artifacts/plsql/<object>.MANUAL_REVIEW.md` following
`references/refusal-template.md`, and continue to the next object. Do not stop the migration.

**A migration that reports 80% automated and 20% needing review is a success. One that reports
100% because you guessed is the expensive kind of failure — nobody finds out until the data is
already wrong in production.**

## Triggers

Oracle fuses the trigger body into the trigger. PostgreSQL splits it: a `FUNCTION ... RETURNS
trigger`, plus a `CREATE TRIGGER` that calls it. Every trigger therefore becomes two objects.

Sort triggers into two kinds before converting, because they have different fates:

| Kind | Example here | Fate |
|---|---|---|
| Identity (`:NEW.id := seq.NEXTVAL`) | `TRG_FILING_BI` | **Delete it.** Replaced by `GENERATED BY DEFAULT AS IDENTITY` in the DDL |
| Business logic | `TRG_FILING_NORMALIZE_BI` | **Convert it.** It normalizes `filing_number` and defaults `lapse_date` |

Both are `BEFORE INSERT` on `UCC_FILING`. Deleting both because "the identity pattern is
handled" is the mistake this schema is built to catch.

## Output

- Converted: `artifacts/plsql/<object>.sql`, then apply with `pg_apply_ddl`
- Refused: `artifacts/plsql/<object>.MANUAL_REVIEW.md` — and **do not** apply anything

Either way, one file per object. A run that produces neither for some object is an incomplete
run, not a successful one.
